## 1. 今天获得的知识与技能

### 今天最重要的一课：小样本会给出任何结论

**背景**：消融实验（ablation，「拿掉一个东西看结果差多少」）里有一组是「把本体的 53 条关系声明清空，看模型还答不答对」。原先录到的数字是**带关系 17/18 = 94%、关系清空 7/18 = 39%**，差距巨大，本来要放进 demo。

**对撞发生了**。另一个会话 16:00 实测同一个 case：**关系清空后 3/3 对，再单独跑 4 次 4/4 对，累计 7 次全通过**——按它的测量，这个实验完全不复现。

崔扬当时的两句追问正中要害：**「我看不懂你的解释，到底这个 case 有没有效？」**「**为什么会和时间有关？不可能同一个问题，有时候 LLM 能回答，有时候不能回答啊！**」

**排查方法值得记：在实验代码之外再套一层探针。** 不信任实验脚本自己的日志，而是在最外层拦住真正发出去的 HTTP 请求体，数里面「本体关系」有几条：

```python
real = llm.chat_json
def probe(system, user, **kw):
    sent.append(len(json.loads(user).get("本体关系", [])))
    return real(system, user, **kw)
llm.chat_json = probe          # 套在最外层，看到的就是请求体里的东西
```

**结果一次性排除了三条备选解释**：载荷键名确实是「本体关系」、每轮只有 1 次模型调用（不存在「多次调用里只有一次被剥到」）；同样的载荷连跑 6 轮出了 3 种不同结果（空/对/空/空/对/对），所以没有提示词缓存；判「空」的三轮选中数是 0、判「对」的三轮是 3，判定与实际选中完全对应，不是判据把「空」误判成「对」。

**所以剥取一次没漏，而抽掉关系后的通过率是真的波动极大。** 合并两边全部数据：带关系 11/12 + 3/3 ≈ **93%**；抽掉 7/20 + 3/6 = 10/26 ≈ **38%**。方向一致、差距不小。

**结论是两边都没错，是样本量不够。** 一方用 7 轮得出「不复现」，另一方用 12 对得出「复现」——**抽掉关系那一组的方差本身很大，所以小样本会给出任何结论**。这个 case 要进演示，轮数得提到几十轮量级，而且**结果文件里必须带上每轮实际发出的关系条数**。

**这一条的通用价值**：「同一个问题，LLM 有时能答有时不能」在崔扬看来是不可能的，但它确实是真的——大模型的输出不是确定性的，同一份载荷会给出不同结果。所以**任何拿模型通过率当证据的实验，单轮和三轮都不算数**。

### 一条反直觉的发现：拿掉的可能不是帮忙的信息，而是劝退的信息

排查中还测了一组「关系清空 + 把 `Exam` / `Session` 的概念描述也精简掉」，预期是通过率掉到接近 0。**实际反而更高。**

原因在 `ontology/tbox.yaml` 里 `Exam` 的描述原文：

> 考试；**独立概念，不从属于小节**。有多种承载形式：exam_session 型寄宿在课程小节上（vote_session.type=10，共用 session_id），daily_exam 型独立存在、不经过小节

**开头那六个字「不从属于小节」在做相反的事。** 而这道题要模型做的正是「从这个小节走到它所属的课程」。精简后 `Exam` 只剩「考试」两个字，模型没了那句顾虑，**反而更敢跨**。

**教训：给模型的概念描述里，一句为了严谨而写的否认，会变成一条阻止它推理的指令。** 描述该写多细不是「越详细越好」，要看它在具体任务上是帮忙还是劝退。

### 实验脚本自己身上的 `except: pass` 是最坏的一种静默降级

剥取关系那段代码里有一个 `except: pass`。**这次探针证明它没触发**，但它是个真口子：哪天载荷形状变了，实验会**静默地变成「两组都带关系」，而结论看起来照样漂亮**。

修法除了改掉这个兜底，还要**把每轮实际发出的关系条数写进结果文件、不只写日志**——理由很实际：这次能一句话排除一个错误推断，靠的就是有这个数；如果当初结果文件里就记着「本轮发出 0 条」，一整轮来回都不必发生。

### 「认不出」不是一个可以自动处理的分类

今天出过一次真实事故：一个会话写了归属脚本，**按关键词判断某处改动属于谁，认不出的默认归自己**，结果把另一个会话未提交的改动卷进了提交 `904ce92`。

**根因不是默认值选错了哪一边，是「认不出」这个状态被当成了一个可以自动处理的分类。正确的动作是停下来问。**

这条可以推广：任何自动分类里，「不确定」都不该被折叠进某一个确定的桶。

### 找「定制/补丁式设计」的机械普查方法

崔扬要求「启用对抗式 review，review 所有可能潜在的定制/补丁似的设计」。做法是先定几个可机械检索的信号，再逐个读上下文判断：

| 信号 | 找什么 | 今天的结果 |
|---|---|---|
| ① | `poc/` `semantic/` 里有没有把具体的指标 / CQ / 关系 id 当字面量用 | 干净 |
| ② | 同一份知识有几个正本 | **五簇确认**（`status eq 1` 那簇是同名不同实体的假阳性，重做带实体上下文的版本后排除） |
| ③ | 阈值有没有出处、列名是不是某句问话的答案 | 干净（唯一阈值 `type=10` 正是当时在收的那条） |
| 判据① | 有没有只服务一个域 / 一句问法的机制 | 四张中文关键词表 → 判定**不是补丁**，见下 |

**四张中文关键词表的判定过程值得记**：它们看起来正是「换个近义词就落空」那个高危形状。但读完上下文后判定不是补丁——两张 loader 关键词表是**加载期校验的判据**，不是问答分流；**失败方向是启动报警（响的），不是静默答错**；而且机制对全部过滤器/指标一律生效，词表只是它的数据，加一个词不用再写一段机制。两处 docstring 自己都写明了「枚举不完」这个局限。

**判据不是「有没有关键词表」，是「它失败时是响的还是静默的」，以及「加一条要不要再写一段机制」。**

### 用 DSL 声明而不是写 SQL，好处到底是什么

崔扬直接问了这个。**结论：SQL 是一段给数据库执行的文本，DSL 是一份能被程序读懂的声明。区别不在写起来谁方便，在于写完之后程序还能不能拿它做别的事。**

**一、一份声明落到多套物理模型。** `session_complete_rate` 只写一遍：

| | 分散原表（本地镜像） | 统一数仓（StarRocks） |
|---|---|---|
| 表名 | `data.data_session_course_completion` | `prove_dw.dwd_session_completion_df` |
| 课程字段 | `group_id` | `course_id` |
| 企业过滤 | **没有**（这条通道不承诺隔离） | `enterprise_id = 2397` |

用 SQL 就是两份文本，而两份文本会各自漂移——这个项目已经栽过：对账脚本和产线路径抄了两份，**46/51 条静默错了很久没人发现**。

顺带，「分散原表没有企业过滤」不是漏了：那条通道的表分属两个数据库实例、一条 SQL 跨不过去，所以它**明确声明自己不承诺隔离**。**这个「能力差异」本身也是声明的一部分。**

**二、横切规则能自动注入到每一条指标。** 映射注册中心登记一次「这张表的企业列是哪一列」，编译器在编译期把过滤写进 SQL，46 条指标一处登记。**如果指标是 SQL 文本这件事做不到**——没法可靠地改写任意 SQL 去插一个 WHERE（有子查询、有 UNION、有 GROUP BY，插哪一层）。现实做法就是让 46 个人各自记得写，而**忘记写不会报错**。

**三、共享的业务限定只声明一次。** 「只看已提交的考试」原先在 17 条指标里各写一遍 WHERE，现在是 `{use: exam_submitted_only}`。四个具名过滤器替掉 26 行重复谓词，每个必须带物理出处（`provenance: {column: megrez_exam_submit.status}`），loader 校验不过就拒绝启动。枚举同理：`enum_value: exam_submit_status.finished` 在加载期解析，**SQL 里不会出现裸的魔数 `3`**。

**四、加载期就能校验**，不用等执行才发现引用不存在。

### 「结构化声明让大模型看懂」的准确含义

**不是让模型读懂声明的内容，而是让程序能从声明里算出几个字段，拿这几个字段约束模型的选择，并在它选错时机械地拦下来。** 模型在这套系统里只做一件事：在一本指标目录里挑一条。它不写 SQL、不碰表。

**真实例子**：问「课程 752468 的 7271640 小节完成情况怎么样」，目录里有两条长得很像的：

```
session_complete_rate         粒度 session  可过滤的维度 [course_id, session_id]
course_complete_user_require  粒度 course   可过滤的维度 [course_id]
```

第二条的同义词里有一个是「**必修小节完成情况**」，和问句字面高度相似——**实测相似度 0.77，比很多正确匹配都高**。分开它们的是「可过滤的维度」：问句点名了小节，而后者只收 `course_id`、结构上筛不到某一个小节。**这一步不是模型的判断，是一次机械判定。**

### 「这条指标接受哪些参数」是数出来的，不是人填的

**关键在于 `param:` 是保留键。** 一个条件的值只有两个来源，写在互斥的两个键上：`value:` 是写死的常量，`param:` 是运行时传进来的。所以答案就是**把声明树走一遍，收集所有 `param` / `params` 键上的值**。**这是遍历，不是解析**——参数在这套语法里只能出现在这一个键位上。代码在 `poc/loader.py` 的 `_locators`。

**关键的一半：间接引用要穿透。** `kp_correct_rate` 自己的 `where` 里没有 `course_id`，可它确实能按课程筛——因为它引用了 `{op: in_scope, scope: course_sessions}`，而 `course_id` 写在那个范围声明那一侧。要穿透的两种引用是 `scope:`（范围声明）和 `use:`（具名过滤器）。

**这条曾经真的坏过，坏法很隐蔽。** 早期这个字段是从 `formula.params`（第一代 SQL 模板的参数表）里挑以 `_id` 结尾的键，而那份参数表已经不参与执行、两套早就漂移：知识点域两条指标经 `in_scope` 收 `course_id` 却报不出来，小节域两条收 `session_id` 也报不出来。

**漏报的后果不是选错，是拒答**——模型照着这个字段判定「这条指标做不到」，整题不答。**它不会像算错数那样被对账拦住，只表现为「这题它答不了」，很难归因。**

### `endswith("_id")` 是用命名约定当机制（崔扬指出，判断成立）

**今天没造成错误**——注册表里 10 个参数名恰好全被分对了——**但它属于「拼错就静默失效」那一类，而且已经在过度收集**：`enterprise_id` 也以 `_id` 结尾，被当成「可过滤的维度」给模型看，而它是租户参数、由编译器自动注入、用户不会在问句里点名它。实测 `kp_correct_rate` 的可过滤维度是 `['course_id', 'enterprise_id', 'session_id']`，那个 `enterprise_id` 就是噪声。

用在四个地方：`poc/loader.py:197`（`_locators`，判错 → 整题拒答）、`poc/chain.py:468`（`unreachable_locators`）、`poc/chain.py:1046`（gates，判错 → 对账找不到该核的列）、`semantic/compiler.py:671`（`_entity_pk`，判错 → 拒绝合法的关系入口或认错主键）。

**风险是结构性的**：逻辑字段名本来就叫 `course`、`learner`、`session`（不带 `_id`），哪天有人拿这种名字登记一个定位参数，会被**静默丢掉、不报错**。

**结构上正确的做法**：定位参数的定义应该是「这个参数绑定的字段指向另一个实体的实例」，而现在字段登记里没这层信息——`course: {column: group_id, type: int}` 和 `delete_status: {column: delete_status, type: int}` 都是 `type: int`，**类型分不出实体引用和状态码，只有名字看起来分得出**。

### 越权时「返回空」和「明确拒答」的区别

**现在的做法**是把「必须属于这个企业」写成 SQL 的过滤条件。有人拿别人企业的考试 ID 来问，SQL 筛完一行不剩，系统照实说「这场考试没有答题数据」。

**这句话是假的。** 那场考试有 **73,985 行答题记录**（实测），只是不属于提问方。真正的原因是「你没权限」，说出口的却是「没有数据」。

类比：去银行查余额，柜员不核对身份、直接拿你给的账号去查，但查询里偷偷加了「并且这个账号的主人得是你」。你报了别人的账号，查出来空的，柜员告诉你「**这个账户没有交易记录**」——听起来像账户是空的，其实是「这不是你的账户」。

**这条最后被崔扬整个否掉了**，见第 3 节。

### 守卫要装在唯一入口，判据是「键在不在」不是「值真不真」

`run_metric` 是唯一取数入口，现在必须有 `enterprise_id` 这个键，没有就抛 `TypeError`。**`enterprise_id: None` 合法**（调用方明确声明没有企业上下文），**键不在**说明压根没考虑过。

**装在入口不装在调用方**，因为装在调用方等于回到「每处都得记得」。这个形状已复发六次，同一个根因：`enterprise_id` 和 `params` 是两个变量，在 `run_params` 那一行才合流，而合流之前有多个自己跑 SQL 的地方。

改调用点时：本地镜像通道的用例显式写 `enterprise_id: None`，**不是随便填一个企业号**——那会让「没有上下文」这个事实消失，而隔离机制正是靠这个事实决定拒答。

### 守卫被兜底吃掉等于没有守卫

加完那道守卫第一次跑，它被 `except Exception` 吃掉了，表现是「及格分没被解析进来」——**一个伪装成数据问题的机制失效**。

同形状的另一例：`except _IsolationError: raise` 那处注释写着「后果良性（主循环那次仍会拒答）」，**而这个函数跑在主循环 try 之前，异常谁都接不到**。注释里写的良性判断没有测试守着，**错了十天没人发现**。

### 批量改名会把数据的键名一起改掉

`re.sub(r"\bparams\b", "run_params", body)` 把 `(m.get("formula") or {}).get("params", {})` 也改了——**那是注册表的键名，不是变量名，正则分不出来**。后果是派生参数解析整段静默空转：不报错、没有 notes、什么都没解析出来。

### 用变异验证打的桩，是打桩的标准收尾

一条打真实大模型的 flaky 测试被打桩，第一版桩数据 3 人各 2 行，序号 `1) 2) 3)` **全被 `reconcile_numbers` 里「按重复次数放行」那条规则放掉了**——序号通道根本没走到。把 `list_rank_allowance` 改成永远返回空集做变异，**测试照样全绿**，才发现是空测试。判据也从「序号在不在证据里」换成「**关掉序号通道之后 gate 必须报违规**」。

**桩的默认失败方式就是把断言弱化成永远为真**，而「测试变绿变快、但它已经不测东西了」比 flaky 更难发现。

### 归因要靠 git diff 内容，不靠 mtime

今天两个会话因为 mtime **互相误判了两次**：一个把 33 秒的窗口错记成常态，另一个把一份 diff 记到了同伴名下。**mtime 只说「几点被写过」，说不出「谁写的、为什么」**；diff 里的注释和它服务的设计目标能对上人。

### 注册表和校验器分两次落盘，中间有个不可加载的窗口

02:00:03 一次全新解释器的 `load_ontology()` 失败，而校验器 `semantic/mapping.py` 的 mtime 是 **02:00:36、晚了 33 秒**。**这类窗口在多人同改一个仓库时会反复出现，表现和「进程旧」一模一样，靠现象分不出来，只能看 mtime。** 当天两个问题还叠着：那个窗口里注册表真的坏，而即便修好了旧服务进程照样失败——**yaml 热重载而 Python 代码不重载**。

### 「我不明白」触发的是规则，不是 skill

这是 my_scripts 那个小会话查清的事。触发的是 `~/.claude/CLAUDE.md` 第 107 行的「自包含解释」**规则**，不是 `/ycui_explain` 那个斜杠命令。两者机制不同：规则是读到触发词后自己改变回答写法；`/ycui_explain` 必须手动敲。`settings.json` 里三个 hook（`Stop`、`PreToolUse`、`PostToolUse`）没有一个监听这类词，**没有任何自动机制**。

## 4. 经验与教训

### 崔扬做的纠正

**「`endswith("_id")` 是用命名约定当机制」** —— 判断成立，正是「拼错就静默失效」那一类。仓库里另一处同样的约定 docstring 早已自认，说明这个形状是已知的、只是没被系统清理。

**「企业的 TBox 应该挂维度」这句他之前就说过、我没记录。** 我当时不但引用了原话，还回了「完全支持，而且这就是 Cube 的 `member:` 设计」，**然后动手实现的却是另一个东西**——靠命名约定把概念和物理列连起来。**口头认了、实现没跟上、也没记到任何地方。**

沉淀：**对方明确给出的设计形态，要么照做，要么说清为什么不照做，不许中间态。** 口头认同不算落实，落实要么在代码里、要么是一条写下来的「为什么不这么做」。

**「我看不懂你的解释，到底这个 case 有没有效？」** —— 这是今天最该记的一次纠正。当时给的是一堆实测数字和机制分析，但**没有回答那个是非问句**。业务方要的是「有效 / 无效 / 还不知道」三选一，然后才是理由。

### 非目标时刻触发的处理原则（今天用了两次）

早盘任务 12:49 触发（目标 8:45）→ **不发 Slack**。板块播报三条同时在 12:57 到达（目标 9:30 / 9:45 / 10:00）→ **只跑一次**。

**判据不是「时间对不对」，而是这份产出在当前时刻还有没有它声称的那个用途。** 「开盘前的方向预测」在开盘三小时后没有用途，而且会被误读成对下午的判断；三条相同的过期播报没有任何额外信息。

改为做一件当时确实有用的事：**核对预测方向与实际开盘**。结果是方向对了（预测低开、实际低开 0.77%，历史均值 −0.47%），**但开盘之后完全反转**（走到 +4.45%）——这正是「跳空后盘中无延续」那条已验证规律的实例。

### 一道会误报的 gate 比没有更坏

原打算加一道新 gate，最后决定不建，**而且理由换了**：不是量出误报太多，是**要堵的口子变小了**——有了成员出口和提示词规则 6b，「声明了派生计算」那条路已经闭合，剩下只有「压根不声明」那一种。

**这个理由比「误报太多」更站得住，因为它说的是必要性变了，不是实现难度。** 而且把这个洞**如实写进既有 gate 的 docstring**，明写「不要以为本 gate 覆盖了它」，**没有偷偷当它不存在**。
