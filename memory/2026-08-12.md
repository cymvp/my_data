## 1. 今天获得的知识与技能

### 用 DSL 声明而不是写 SQL，好处到底是什么

崔扬直接问了这个问题。**结论：SQL 是一段给数据库执行的文本，DSL 是一份能被程序读懂的声明。区别不在写起来谁方便，在于写完之后程序还能不能拿它做别的事。** 下面每条都是这个仓库里跑着的，不是设想。

**一、一份声明落到多套物理模型。** `session_complete_rate` 只写一遍：

| | 分散原表（本地镜像） | 统一数仓（StarRocks） |
|---|---|---|
| 表名 | `data.data_session_course_completion` | `prove_dw.dwd_session_completion_df` |
| 课程字段 | `group_id` | `course_id` |
| 企业过滤 | **没有**（这条通道不承诺隔离） | `enterprise_id = 2397` |

**用 SQL 就是两份文本，而两份文本会各自漂移。** 这个项目已经在别处栽过：对账脚本和产线路径抄了两份，结果 46/51 条静默错了很久没人发现。

顺带一提，「分散原表那条通道没有企业过滤」不是漏了——那条通道的表分属两个数据库实例、一条 SQL 跨不过去，所以它**明确声明自己不承诺隔离**，而不是假装做到了。**这个「能力差异」本身也是声明的一部分。**

**二、横切规则能自动注入到每一条指标。** 租户隔离不属于任何一条指标，但每条都得有。在映射注册中心登记一次「这张表的企业列是哪一列」，编译器在编译期把过滤写进 SQL，**46 条指标、一处登记**。

**如果指标是 SQL 文本，这件事做不到**——没法可靠地改写一段任意 SQL 去插一个 WHERE（有子查询、有 UNION、有 GROUP BY，插哪一层）。现实做法就是让 46 个人各自记得写上这一句，而**忘记写不会报错**。

**三、共享的业务限定只声明一次。** 「只看已提交的考试」原先在 17 条指标里各写一遍 WHERE，现在是 `{use: exam_submitted_only}`。四个具名过滤器替掉 26 行重复谓词，每个必须带物理出处（`provenance: {column: megrez_exam_submit.status}`），loader 校验不过就拒绝启动。枚举同理：`enum_value: exam_submit_status.finished` 在加载期解析成具体值，**SQL 里不会出现裸的魔数 `3`**。

**四、加载期就能校验**，不用等执行到才发现引用不存在。

### 「结构化声明可以让大模型看懂」的准确含义

**不是让模型读懂声明的内容，而是让程序能从声明里算出几个字段，拿这几个字段去约束模型的选择，并且在它选错时机械地拦下来。**

模型在这套系统里只做一件事：在一本指标目录里挑一条。它不写 SQL、不碰表。

**真实例子**：问「课程 752468 的 7271640 小节完成情况怎么样」，目录里有两条长得很像的：

```
session_complete_rate         粒度 session  可过滤的维度 [course_id, session_id]
course_complete_user_require  粒度 course   可过滤的维度 [course_id]
```

第二条的同义词里有一个是「**必修小节完成情况**」，和问句字面高度相似——**实测相似度 0.77，比很多正确匹配都高**。光看名字和同义词，选它很自然。

**分开这两条的是「可过滤的维度」这一列**：问句点名了小节 7271640，而 `course_complete_user_require` 只收 `course_id`、结构上就筛不到某一个小节。程序据此把它挡下、让模型重新选。**这一步不是模型的判断，是一次机械判定。**

### 「这条指标接受哪些参数」是数出来的，不是人填的

这是上一条能成立的前提，否则就只是又一份会漂移的副本。

**关键在于 `param:` 是保留键。** 在这套 DSL 里一个条件的值只有两个来源，写在两个互斥的键上：`value:` 是写死的常量，`param:` 是运行时传进来的。所以答案就是**把声明树走一遍，收集所有 `param` / `params` 键上的值**。

**这是遍历，不是解析**——没有语法歧义，也没有「可能藏在某处」的问题，因为参数在这套语法里只能出现在这一个键位上。代码在 `poc/loader.py` 的 `_locators`。

**关键的一半：间接引用要跟着穿透。** `kp_correct_rate` 自己的 `where` 里只有 `enterprise_id` / `session_id` / `min_answers`，**没有 `course_id`**，可它确实能按课程筛——因为它引用了 `{op: in_scope, scope: course_sessions}`，而 `course_id` 写在那个范围声明那一侧。所以要穿透两种引用：`scope:`（范围声明）和 `use:`（具名过滤器）。

**这条曾经真的坏过，而坏法很隐蔽。** 早期这个字段是从 `formula.params`（第一代 SQL 模板的参数表）里挑以 `_id` 结尾的键，而那份参数表**已经不参与执行**、两套早就漂移：知识点域两条指标经 `in_scope` 收 `course_id` 却报不出来，小节域两条收 `session_id` 也报不出来。

**漏报的后果不是选错，是拒答**——模型照着这个字段判定「这条指标做不到」，整题不答。它不会像算错数那样被对账拦住，只表现为「这题它答不了」，**很难归因**。修法不是把副本补齐，是改成从真正生成 SQL 的那份声明推导，让它只有一个正本。

**反过来看，如果目录里放的是 SQL 文本**：要回答「这条指标能不能筛到某个小节」，只能去解析 WHERE 子句——有子查询、有 UNION、有多层聚合，参数可能藏在任何一层，而且有的指标根本不是一条 SQL（分母跨库取并集）。可靠解析基本做不到，于是现实做法就是人手工填一份表，**那就是又一个正本，一定会漂移**。

### `endswith("_id")` 是用命名约定当机制（崔扬指出，判断成立）

**它今天没有造成错误**——注册表里 10 个参数名恰好全被分对了——**但它属于「拼错就静默失效」那一类，而且已经在过度收集**：`enterprise_id` 也以 `_id` 结尾，于是被当成「可过滤的维度」给模型看，而它是租户参数、由调用方注入、用户不会在问句里点名它。实测 `kp_correct_rate` 的可过滤维度是 `['course_id', 'enterprise_id', 'session_id']`，那个 `enterprise_id` 在目录里就是噪声。

这个约定用在四个地方，判错的后果各不相同：

| 位置 | 拿它判断什么 | 判错的后果 |
|---|---|---|
| `poc/loader.py:197`（`_locators`） | 哪些参数算定位参数、进目录给模型看 | 漏报 → 模型判定做不到 → **整题拒答** |
| `poc/chain.py:468`（`unreachable_locators`） | 问句抽到的参数里哪些要检查够不着 | 同上 |
| `poc/chain.py:1046`（gates） | 证据行里哪一列装的是实体 ID | 对账时找不到该核的列 |
| `semantic/compiler.py:671`（`_entity_pk`） | 一个实体的主键是哪个字段 | 拒绝合法的关系入口，或认错主键 |

**风险是结构性的、不是当前的**：哪天有人登记一个叫 `learner`、`dept`、`kp` 的定位参数（逻辑字段名本来就是这么起的——实体里的字段就叫 `course`、`learner`、`session`，不带 `_id`），它会被**静默丢掉、不报错**。

**结构上正确的做法**：定位参数的定义应该是「这个参数绑定的字段指向另一个实体的实例」，而现在的字段登记里没有这层信息——`course: {column: group_id, type: int}`、`learner: {column: student_id, type: int}`、`delete_status: {column: delete_status, type: int}` 三个都是 `type: int`，前两个是实体引用、第三个是状态码，**类型分不出来，只有名字看起来分得出**。补的是字段级的实体引用声明。仓库里另一处同样的约定（`semantic/compiler.py:664`）docstring 早已自己认了这一点，并写明「彻底的做法是列级概念声明，那是本体本该有的一层、单独立项」。

### 越权时「返回空」和「明确拒答」的区别

崔扬说看不明白，用银行的例子讲清了：

**现在的做法**是把「必须属于这个企业」写成 SQL 的一个过滤条件。于是有人拿别人企业的考试 ID 来问，那条 SQL 筛完一行不剩，系统照实说「这场考试没有答题数据」。

**这句话是假的。** 那场考试有 **73,985 行答题记录**（实测），只是不属于提问方。真正的原因是「你没权限」，说出口的却是「没有数据」。

类比：去银行查余额，柜员不核对身份、直接拿你给的账号去查，但查询里偷偷加了一条「并且这个账号的主人得是你」。你报了别人的账号，查出来空的，柜员告诉你「**这个账户没有交易记录**」——听起来像账户是空的，其实是「这不是你的账户」。

**但这条最后被崔扬整个否掉了**，见第 3 节。

### 守卫要装在唯一入口，而且判据是「键在不在」不是「值真不真」

`run_metric` 是唯一取数入口，现在加了一道守卫：参数表里必须有 `enterprise_id` 这个键，没有就抛 `TypeError`。

**`enterprise_id: None` 合法**——那是调用方明确声明「这次没有企业上下文」，后面由隔离机制决定拒答还是放行；**键不在**说明调用方压根没考虑过，直接报错。

**装在入口不装在调用方**，因为装在调用方等于回到「每处都得记得」。这个形状已经复发六次：`_course_filter` 那次、reconcile 缺 enterprise_id 那次（46/51 静默错）、`/api/exam_stats` 返回 000 那次、`poc/session.py` 与 `chain.py` 两个同名 `_course_of_exam` 一修一漏那次，加上 `_resolve_by_registry`。**同一个根因：`enterprise_id` 和 `params` 是两个变量，在 `run_params` 那一行才合流，而合流之前有多个自己跑 SQL 的地方。**

**改调用点时的正确做法**：42 处调用被拦下 14 处，本地镜像通道的用例显式写 `enterprise_id: None`，**不是随便填一个企业号**——那会让「没有上下文」这个事实消失，而隔离机制正是靠这个事实决定拒答。

### 守卫被兜底吃掉等于没有守卫

加完上面那道守卫第一次跑，它被 `except Exception` 吃掉了。表现是 `test_pass_score_wiring` 报「及格分没被解析进来」——**一个伪装成数据问题的机制失效**。修法是把 `except _IsolationError: raise` 扩成 `except (_IsolationError, TypeError): raise`。

同一形状的另一例：`except _IsolationError: raise` 那处的注释写着「后果良性（主循环那次仍会拒答）」，**而这个函数跑在主循环 try 之前，异常谁都接不到**。注释里写的良性判断没有测试守着，所以它**错了十天没人发现**。

### 批量改名会把数据的键名一起改掉

`re.sub(r"\bparams\b", "run_params", body)` 把 `(m.get("formula") or {}).get("params", {})` 也改了——**那是注册表的键名，不是变量名，正则分不出来**。后果是派生参数解析整段静默空转：不报错、没有 notes、什么都没解析出来。

教训：批量改名前先把键名位置排除掉。

## 4. 经验与教训

### 崔扬做的纠正

**「`endswith("_id")` 是用命名约定当机制」** —— 判断成立，而且正是「拼错就静默失效」那一类。仓库里另一处同样的约定 docstring 早就自己认了，说明这个形状是已知的、只是没被系统性清理。

**「企业的 TBox 应该挂维度」这句他之前就说过，我没记录。** 我当时不但引用了原话，还回了一句「完全支持，而且这就是 Cube 的 `member:` 设计」，**然后动手实现的却是另一个东西**——用逻辑字段名当中介，靠命名约定把概念和物理列连起来。**口头认了、实现没跟上、也没记到任何地方。**

沉淀成一条判断：**对方明确给出的设计形态，要么照做，要么说清为什么不照做，不许中间态。** 口头认同不算落实，落实要么体现在代码里、要么体现在一条写下来的「为什么不这么做」。

**「这个我不明白，你解释清楚」出现了三次**（A3 分批那件事、`param_resolvers` 的 session_id、DDL 快照过期）。三次都是我用系统内部的说法讲了一件外部视角看不到的事。有效的解法一致：**先给一句话结论，再从问题本身讲起，最后配一个生活化的例子**（银行柜员核对身份、考试发旧版数据字典手册）。

### 我今天说错并自己纠正的三处

**一、「重新导出 DDL 快照会让消融对照变弱」——方向说反了**，实际是更干净。核实之后才发现。

**二、「分开这两条指标的是目录里『可过滤的维度』那一列，程序据此挡下」** —— 挡下这件事确实发生了，**但读的不是那一列**：挡它的 `unreachable_locators` 读的是 `formula.params`，而目录里那一列是从 `query` 声明推导的。这个例子里两者恰好一致，所以**结论没错、机制说偏了一处**——而这个偏差牵出了一个真问题（两份不是同一个正本，已在 5 条指标上不一致）。

**三、把 JST 当成北京时间。** 我说「现在是 15:22 北京时间，已经收盘」，实际那是本机 JST 15:22、折算北京是 **14:22，还在交易时段**。后果是我告诉用户「采集已停、要等明天」，而实际上重启后的面板是正常出数的。**本机时区是 JST，比北京快 1 小时，取北京时间必须显式 `TZ='Asia/Shanghai'`。**

### 阻塞式提问会把定时任务挂十几个小时

`/ycui_sync` 的备份脚本在 **JST 8/11 21:30** 跑完，随后我用 `AskUserQuestion` 问「market_pulse 那批未提交的代码要不要一起 commit」，**用户 8/12 13:49 才回答**——commit 时间戳因此比脚本执行晚了十六个小时。

沉淀：**定时任务里问阻塞式问题，等于把这个任务挂起到用户下次看屏幕。** 能先做的部分要先做完（当时 my_data 那侧我确实先同步了），真要问就只问剩下那一件，并且在汇报里写清楚哪些已完成、哪些在等。

### 非目标时刻触发的处理原则

早盘任务在 12:49 BJT 触发（目标 8:45），**判断是不发 Slack**。判据不是「时间对不对」，而是**这份产出在当前时刻还有没有它声称的那个用途**——「开盘前的方向预测」在开盘三小时后没有任何用途，而且会被误读成对下午或明天的判断。

改为在对话里做一件当时确实有用的事：**核对预测方向与实际开盘**。结果是方向对了（预测低开、实际低开 0.77%，历史均值 −0.47%），**但开盘之后完全反转**（中际旭创走到 +4.45%）——这正是「跳空后盘中无延续」那条已验证规律的实例：外盘信息在开盘价里一次性兑现完，之后走什么由当天自己的消息决定。

### 一道会误报的 gate 比没有更坏

peer session 原打算加一道新 gate，最后决定不建，**而且理由换了**：不是量出误报太多，是**要堵的口子变小了**——有了成员出口和提示词规则 6b，「声明了派生计算」那条路已经闭合，剩下只有「压根不声明」那一种。

**这个理由比「误报太多」更站得住，因为它说的是必要性变了，不是实现难度。** 而且它把这个洞**如实写进了既有 gate 的 docstring**，明写「不要以为本 gate 覆盖了它」，**没有偷偷当它不存在**。
