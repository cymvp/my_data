## 1. 今天获得的知识与技能

- **语义层的"绑定机制"——同一份指标声明跑在两套物理模型上**：prove 项目给每个逻辑实体登记两套物理绑定，一套叫 `source`（数据分散在原始各库的原表），一套叫 `warehouse`（统一数仓里的表）。两套绑定的逻辑字段名必须完全一致（加载期强制校验），这样切换数据源时四十多个指标声明一行都不用改，只改映射注册表里指向哪套绑定。为什么重要：这是"语义层与物理存储解耦"是不是真的成立的判据——名字对不上就说明解耦是假的。今天用双跑对账验证了这一点：同一指标在分散原表和统一数仓两套模型上跑，40 个指标数字逐值一致，指标声明改动量 0 行。
- **数据统一后，语义层能力会自然增长（满分指标的例子）**：prove 的 DSL（领域专用查询语言，用结构化 YAML 声明指标怎么算，由编译器翻成 SQL）有一份函数白名单，只放行 SUM/COUNT/MAX 这类，用来防 SQL 注入。考试满分原本锁在题目的 `setup` 文本字段里（形如 `{"score":10}`），要算满分得用 `JSON_EXTRACT` 这类带引号参数的函数，一旦放行白名单就破防，所以只能登记为"不可出数"。数仓的 ETL 脚本是自己写的加工代码、不接受用户输入、没有注入风险，可以放心用 JSON 函数把满分算好存成普通数字列 `dim_exam.full_mark`。难题被挪到了合适的地方解决：查询层受安全约束做不了的事，加工层做一次存下来，查询层直接取结果。
- **本体里 concept / entity / 字段别名 / engine 四个层级的区分**（用户今天反复要求讲清、不许起黑话）：以"学员"为例——`Learner` 是业务**概念**（住在 tbox）；`learner_dim` 是**实体**，说这个概念的数据具体落在哪张表（住在 mapping 的 entities 段）；`learner` 是**字段别名**，某张事实表里"是谁做的"那一列的逻辑名（出现在 8 张事实表的 fields 里，物理列名各不相同，有的叫 umu_id 有的叫 student_id）；`Doris_JP` 是**引擎**，一个物理数据库实例。串起来：概念 Learner 的数据落在实体 learner_dim 上，这个实体的表存在引擎 Doris_JP 里；事实表里的 learner 字段是指向学员的外键列，不是学员本身。八张事实表都把"谁做的"这列的逻辑名统一起成 `learner`，是为了让关系（如"学员属于部门"的 join 路径）能被不同指标复用——关系登记时用裸字段名 `learner` 占位，编译时才绑定到当前查询主实体的那一列。
- **BI 报表表按天切片会导致 count 行数重复计数**：prove 排查"带教任务完成率>1"，复现发现线上 complete 表 1171 行但只有 1162 个不同的（带教者，被带教者，小节）三元组——同一个任务多天各留一行，直接 count 行数就把一个任务算了多次，而分母恰好没重复，比值就 >1。做比率类指标要先确认分子表有没有按时间切片的重复行。

- **术语必须举例讲清，不许自造黑话**：prove 那个 session 用户多次强烈反弹（"你不要自己起黑话""这些名词只有你理解"），要求对 entity/concept/裸字段这类概念用真实例子走一遍、逐字段说清哪些是定义哪些是引用。给用户讲系统时，默认他不熟悉内部名词，每个术语第一次出现就用大白话解释 + 举真实例子，不要从"很懂这个系统"的视角陈述。这条对所有讲解性输出都适用。
- **解耦是不是真的，要用"零改动切换"来证伪，不能靠断言**：prove 的语义层与物理存储解耦，靠的是双跑对账（同指标两套物理模型逐值一致）+ 指标声明改动 0 行来证明，而不是嘴上说"解耦了"。设计"可切换/可迁移"的东西，要设计一个能证伪它的实验（改一处、看是不是真的只改这一处）。
- **静默新建/静默降级是最危险的故障，全链路显示成功、只有终端症状**：csrs 的 dataset 名字对不上会静默新建库（入库成功、按钮变已发布、日志干净，只有"问不出摘要"这一个症状）；prove 的 course_id 未透传会静默降级成企业范围（见 [[2026-07-24]]）。凡是"找不到就新建/找不到就用默认"的兜底逻辑，都要问一句"对不上的时候会不会假装成功"，并把触发条件写成显式校验或报错。
- **实测更正自己写进 spec 的结论**：csrs 那个"必须用 max_completion_tokens"是没实测就写进 spec 的，实测发现两个参数名都能用、真正的坑是 16 下限和不传不报错——当场改正 spec 并说明"这条原先写错了"。凡是要写进 spec/文档当结论的技术细节，先用真实调用验一遍，没验过的标"假设、未验证"（延续 [[2026-07-26]] 的教训）。
- **远程机器地址不能拿仓库注释当依据**：csrs 查库前，即使 slack_apps.yaml 注释里写了 `172.24.201.36`，也要用户明确点头才 SSH 上去——尤其那台看着像跟平时的 dev 机分开的另一台。dev 排障连远程机器的规矩是地址要人确认。
- **自检工具本身会漏报，不能照单念结论**：做 T 自检脚本判"无异常"，但人工读日志发现它漏了 6 分钟卡死（被"信号附近 gap 算弹窗阻塞"的规则一刀切放过）和"出信号却成交被拒"（脚本根本没这个检测项）。自我观测工具也是代码、也有盲区；跑完自检要人工过一遍关键事件，发现漏报就补检测项。这正是用户要的"主动观测、不等我发现问题"的落地方式。
- **改交易参数（档距/中枢/触发）必须用户确认，改观测工具可以主动提**：做 T 网格 A/B 选择交给用户拍板（选了 A 追踪网格），不擅自改；但自检脚本的检测项、看门狗这类观测/运维改动可以主动提议。延续 [[2026-07-24]] 的边界：检测+报告自动化，动实盘参数需人确认。
- **专利答复里"中的至少一个"这类可选表述是创造性论证的硬伤**：全部论证重心在"多维度联合生成"，但权利要求允许只有一个维度的解读，审查员一句"主张的区别不在保护范围内"就能驳回。写权利要求时，论证依赖的核心特征必须落到权利要求的必要技术特征里，不能留在说明书或做成可选项。
