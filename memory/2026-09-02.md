## 1. 今天获得的知识与技能

### 描述逻辑与一阶逻辑：一整天的概念补课，这是今天最大的知识增量

崔扬对着 `2026-09-02-description-logic-tbox-abox.md` 这份文档逐句追问了二十多轮，全部走 `/ycui_explain`。下面是澄清出来的核心概念，**每一条都要能单独讲清，因为它们后面会被反复引用**。

**一阶逻辑里那个点号 `∀x. Teacher(x) → ¬Course(x)`**：点号只是分隔符，把「量词管到哪里」和「被管的那句话」隔开，读作「对任意 x，如果 x 是老师，那么 x 不是课程」。用蕴含符号是因为要表达「凡是……都……」这种条件关系，不是集合包含。

**签名（signature）是三张名字清单**：Σ = (N_C, N_R, N_I)，分别装概念名、关系名、个体名，三个集合互不相交。**签名只有名字、没有任何一句关于名字的话。** 一个名字意味着什么，由约束层（TBox/RBox）的公理给。这个区分崔扬专门追问过——「签名回答『这个名字存在吗、是哪一类』，约束回答『这个名字意味着什么』」。

**一个名字只能是概念或个体之一，不能既是又是。** 这条是硬约束，理由是一阶逻辑的合式规则：实例关系写成 `C(a)`，`a` 占参数位，**参数位不能填谓词符号**。所以：
- 选「鸟」为概念：`鸟 ⊑ 动物` 能写；「鸟是一种分类等级」写不出来（`分类等级(鸟)` 把概念名填进参数位，不合式）
- 选「鸟」为个体：`分类等级(鸟)` 能写；`鸟 ⊑ 动物` 写不出来（个体不能放 `⊑` 两边），「这只麻雀是鸟」也写不出来（个体没有成员）

**「属性挂在哪一层，哪一层就是对象」**：判断一个东西该建成概念还是个体，看属性挂在哪。掌握度挂在「销售话术」本身上、不挂在它的成员上，所以销售话术是个体。辅助检验是继承测试——如果 `销售话术 ⊑ 知识点` 成立，含义是「凡是销售话术都是知识点」，那必须存在一批东西每个都是一份销售话术，说不出来是什么，所以它不是概念。

**`⊑` 和 `→` 的区别**（报销例子）：`⊑` 连的是两个**概念表达式**，`→` 连的是两个**命题**。「出差超过 3 天且住宿发票齐全的员工，享受全额报销」里，前半句是一个概念表达式（由构造子拼成的集合描述），后半句也是，所以用 `⊑`。翻译成一阶逻辑之后才出现 `→`。

**`(∃喜欢.打篮球)(我)` 逐符号翻译**：`∃R.C` 是存在限制构造子，点号前填关系名、后填概念。翻译规则是 `∃y. R(x,y) ∧ C(y)`，代入得 `∃y. 喜欢(我, y) ∧ 打篮球(y)`，读作「存在某场活动 y，我喜欢 y，y 是一场打篮球」。

**为什么不能写 `喜欢(我, 打篮球)`**——这是今天最精彩的一条澄清。**两种写法都合法，但对应两种不同的建模**：

| 「打篮球」建成 | 写法 | 能说的话 | 说不出的话 |
|---|---|---|---|
| **个体** | `喜欢(我, 打篮球)` | 我喜欢打篮球；`球类运动(打篮球)` | 「上周六那场是一次打篮球」——个体没有成员 |
| **概念** | `(∃喜欢.打篮球)(我)` | 我喜欢至少一场打篮球；`打篮球(赛事0906)` | 「打篮球属于球类运动」只能写 `打篮球 ⊑ 球类运动`，含义变成每场篮球赛都是一场球类运动 |

**日常问答里第一种更常用**，GUMO 的学员画像 `〈学员〉〈动作〉〈宾语〉` 就是第一种，宾语是个体。

**描述逻辑为什么可判定、一阶逻辑为什么不可判定**：这一条崔扬要求「举例浅显解释」，答案是：

- **一阶逻辑砍不掉「绕环」的能力**。它允许一句话同时牵住任意多个变量并要求闭环，比如 `∀x∀y∀z. 认识(x,y) ∧ 认识(y,z) → 认识(z,x)`。有了绕环能力就能写出一批规定，合起来等价于「无限拼图能不能铺满平面」——**这个问题 1966 年被 Berger 证明没有算法能解**（域铺砌问题）。
- **描述逻辑只有一种句型**：从一个东西出发，说它沿关系连到的东西是什么样，再往下一层。**每次只能新引入一个变量，且只和上一层那个变量有关系，够不着更上层的。** 所以说不出「z 必须就是 x」。
- **这就是「树模型性质」**：描述逻辑说得出的话，只要有一个满足它的世界，就一定有一个树形的世界也满足它。因为说不出「必须绕回去」，任何环都能剪开摊平成树。
- **树形保证算完的机制叫 tableau + 阻塞（blocking）**：从一个假想个体出发逐层造它必须有的邻居，**当新个体的标签和某个祖先一模一样时停止**（它往下长出的东西会和祖先一样）。阻塞一定会发生，因为标签种类有限——规定里出现的概念片段 n 个，标签最多 2^n 种，最多造 2^n 层必撞重复。
- **代价**：说不出闭环，所以「小节寄宿的课程就是它所属的课程」、「两门课程的讲师是同一个人」这类约束表达不了。**prove 项目里这类约束确实存在**（`examHostedBySession` 那条「一个数字能当两个名字用」就是一种汇合），**但它们没写进本体的约束层，而是写在编译器的 join 条件里**。

### 学员画像用本体建模：一行是一个「事实」个体

这是今天从概念澄清落到实际系统的一步，**对后续统一口径很关键**。

学员画像事实表的一行是「〈学员〉〈动作〉〈宾语〉, in〈取值域〉is〈取值〉」。**一行是一个个体（一条陈述）**，GUMO 叫 SituationalStatement，描述逻辑里对应「把三元以上的关系物化成一个个体」。

**为什么必须物化**：一条画像行有四个成分（学员、动作、宾语、取值），而**描述逻辑的关系只能连两个东西**，所以要造一个个体 `f_001` 代表整行，再用四条二元关系挂上去。物化之后「有属性」这个动作词就成了被挂上去的东西，**所以它是个体，不是关系名**。

一条真实行拆成的事实层断言：

```
事实(f_001)
主语(f_001, 张三)      动作(f_001, 有属性)
宾语(f_001, 职级)      取值(f_001, 技术经理)
valid_from(f_001, "2026-08-01")    source(f_001, "自述")
```

前五条连个体，后两条连字面值。**OWL 把这两种分开叫：连到个体的是对象属性（object property），连到字面值的是数据属性（datatype property）。** 这个区分有出处，直接用。

七列的归类（**这是崔扬点名要的答案**）：

| 类 | 列 | 规范名 | GUMO 里的叫法 |
|---|---|---|---|
| 主干 | learner_id、action、object | 事实的主语、关系、宾语 | mainpart 的 subject、auxiliary、predicate |
| 取值 | scale、value | 事实的**取值域**、**取值** | mainpart 的 range、object |
| 附注 | condition、times、valid_from/to、source、evidence、narrative | **事实的属性** | situational part + explanation part |

**关键结论**：scale 叫「取值域」，有自己的规范名，**不混叫属性**。「学员的属性」这个说法在这套模型里**不出现**——学员身上的一切都通过事实行挂上去，「职级是技术经理」也是一条事实，不是学员表上的一列。`sub_profile` 单独归「注解」，给事实分类、不参与判重、不进逻辑。

**scale 列在逻辑上是冗余的**：`公司职级体系` 是概念，`公司职级体系(技术经理)` 是事实层断言；约束层写 `公司职级体系 ≡ {技术经理, 高级经理, 总监, …}` 把它封闭成枚举。所以事实经「取值」连到技术经理、技术经理属于公司职级体系——**scale 可以从 value 推出来，存它是工程决定（判重键要用），不是模型要求**。

### CSRS 的 LLM 代理有一段可复现的故障形态

**现象**：2026-09-02 00:01:11–00:04:00 UTC（日本时间 09:01–09:04），调 `http://172.24.201.32:8080/v1/chat/completions`，3 个频道 × 3 次重试共 **9 次全部 HTTP 500**，响应体是「request timed out (default is 30 seconds)」。

**最可疑的一点，也是报告的核心发现**：错误文案说等了 30 秒，**实际每次都是 3.0 秒就返回**。把「发出请求」和「收到 500」的时间戳配对，六次能精确配对的间隔全是 **3.01–3.02 秒**，稳得不像巧合。**说明超时不是它自己报的那一层，更像上游连接直接失败。**

**不是大请求打爆的**：三个频道的输入规模分别是 4694 字符（约 2.3k token）、**437 字符（约 0.2k token）**、8203 字符（约 4.1k token）。**那个只有 437 字符的请求同样 500**，所以和请求大小无关。

**事后复测全好**：11:23 用三种大小各测一次——50 字 → 2.0 秒、5 千字 → 1.7 秒、3 万字 → 2.2 秒，全部正常。**是一段短暂抖动，已经恢复。**

### 检索答不了「文档里根本没有」——这是今天最有迁移价值的一条判断

CSRS 合规检查需求的核心难点：需求方定义「合规/知识文档是规则的全集，学员提到未在文档里的知识也算违规」。

**判「学员说的和文档矛盾」是检索问题，判「文档从头到尾没提这件事」是穷举问题。** 检索接口回答的是「最相关的若干条是什么」，回答不了「全库有没有」。**检索漏召和文档真没写，返回结果长得一模一样。**

三条实测事实支撑这个判断：

| 事实 | 位置 |
|---|---|
| 单次检索最多返回约 40 条，`top_k` 填 100 无效 | `csrs/retrievers/fusion_retriever.py:703` |
| 返回结果里 score 被丢掉，判定层无阈值可设 | `csrs/gateway/csrs_service.py:1330-1336` |
| 图检索路 dataset 过滤异常时**放行全部边** | `csrs/retrievers/fusion_retriever.py:426-428` |
| 单次检索 p50 6–10 秒，可持续 4 QPS | 2026-05-29 压测报告 |

**第三条对合规场景最危险**——它意味着某家药企的判定证据可能来自另一家药企的文档。

**一个可用的量化参照点**：现有检索评测在问答类数据集上 Contextual Recall 是 **0.898**，也就是大约每 10 个问题有 1 个相关段落没进上下文。放到合规场景，就是**大约每 10 条本该判「一致」的 claim 有 1 条可能被误判成「无支撑」**。这个数字是问答场景测出来的、不能直接搬，但量级足以说明单靠检索判「没有」风险不小。

### 三个候选方案，以及「方案丙」的核心机制

**方案甲 · 全文直判**：文档入库后用 `/gateway/chunks/retrieve_chunks_by_index` 按序号拉回全部原文和页码，整份塞进 LLM 上下文逐条判。**不存在漏召，「未提及」的结论可信。** 首批客户是医药、绑药品说明书，日本添付文書十几页几万 token 装得下。**一次调用 vs 检索路线的二十次检索加二十次判定，便宜一个量级。**

**方案乙 · 检索加判定**：每条 claim 调一次检索、top_k 放大到 30–50、LLM 对候选判三分类。**代价是「无支撑」的可靠度取决于召回率。** 文档超上下文窗口时才用。**这是被文档规模逼出来的妥协，不是省事的选择。**

**方案丙 · 入库时读成一张表，判定时查表，不再检索**（崔扬专门问了这个）：

- **入库时**：按行业定一套维度（医药是适应症、用法用量、禁忌、疗效数值、安全性、比较声明、警告）；用模型把整份文档读一遍，按维度抽出每条事实，记维度、主语、属性、值、原文、页码；**最关键的一步——文档没写到的维度也要留一行，明确记「本文档未涉及该维度」**。
- **判定时**：定这条 claim 属于哪个维度 → 把那个维度的全部条目取出来（不排序不截断）→ 交给模型判一致/矛盾/无对应条目。

**它和检索的差别**：检索给的是「我翻了 40 条最像的，里面没有治愈率」；查表给的是「疗效数值这一栏一共 3 条，全在这里，没有治愈率」。**前一句是我没找到，后一句是这里就这些。**

**它能撑住大文档的原因**：判定时不看全文、只看一个维度的几条。文档从 15 页涨到 500 页，某维度可能从 3 条涨到 40 条，仍塞得进一次调用。**方案甲在 500 页时塞不下。**

**三条代价**：抽取质量决定一切（清单漏抽一条，那条对应的所有判定都错，所以抽取要单独评测）；维度表要按行业各设计一套（持续的产品配置工作）；**CSRS 现在没有这条链**——cognify 抽的是通用无 schema 三元组，`Node.type` 是自由文本，抽不出带维度带属性带值的清单，要新建。

### claim 抽取是什么，以及「抽一次判两次」

**claim 抽取**是把学员整场发言拆成一条条「可以拿去和文档核对的事实性声明」。它在链路最前面：先抽 claim → 每条去检索文档 → LLM 判定。抽不出 claim 的对话直接判「未涉及，通过」。

**学员原话不能直接核对，三个原因各对一个测试用例**：
- **一条声明散在多轮里**（S1）：第 3 轮说「有效率很高」、第 7 轮说「大概九成吧」，要合成「有效率约 90%」
- **提到敏感内容的话不一定是声明**（S2/S3）：「如果有人说这药能治愈，那不准确」是否定；「治愈率这个我需要确认」没做声明。**排不掉会把学员的谨慎表达判成违规**
- **口语要归一**（D4）：「治愈率大概八成多」要归一成「治愈率约 80% 以上」才能和文档的「82%」比

**「抽一次，判两次」这个结论是崔扬追问后确立的**——他问「要不要按 Product Knowledge 和 Compliance 两类分别抽 claim」，答案是**不要**，三条理由：

1. **分类依赖判定结果，做不到在抽取阶段分。** 拿 D8 走一遍：学员说「对中危患者也有效」，文档写「仅适用于高危患者」。抽取阶段只能看出这是一条关于适应症人群的事实声明，**查不出它是超说明书表达，因为要读了文档才知道文档写的是「仅高危」**。把它当抽取阶段的分类键，等于要求抽取器先知道判定结论，**这是个循环**。
2. **一句话可以两边都 NG。** Taisei 原话：「如果同一发言同时符合两者，则理解为会在 Product Knowledge 和 Compliance 两项中都判定为 NG」。抽取时分桶会强制二选一，把这种情况压掉一个。
3. **上游误差会翻倍。** 抽取是整条链的准确率瓶颈，上游漏抓下游补不回来。分成两套抽取口径等于维护两个门槛，**漏抓的面积变成两倍**。

**该分的是另外两样东西**：**文档按用途分**（一份是产品事实全集、一份是禁止和必须的规则集，同一份文档可以两个用途都挂）；**claim 按主题维度分**（适应症、用法用量、疗效数值、安全性、比较声明——这个分类在抽取阶段就能判、不需要读文档，而且有两个实际用途：决定去文档哪一部分找证据、决定套哪条合规规则。**超说明书那条规则只对适应症类的 claim 生效，对用法用量类不生效**）。

### 范围门（claim scope gate）分两层

解决的问题：「文档没提到就算违规」只能对「文档本来就该覆盖的话题」生效。学员说「糖尿病是慢性病」，说明书没这句话，但不该判违规。

**第一层，按 claim 类型过滤，不用 LLM。** 只有关于本产品/本服务的事实性声明才进文档校验（疗效数值、适应症、用法用量、禁忌、安全性、竞品比较）。直接不进的：疾病常识/行业常识、学员对自己行为的描述（「我下周再来拜访」）、对客户话的复述。**这一层是抽取 prompt 里一个字段加一个白名单，成本最低。**

**第二层，按文档目录判主题是否在范围内，用 LLM。** CSRS 入库时抽了每份文档的目录，`/gateway/documents/toc` 能拿到。把目录和 claim 一起给 LLM，问题变成「这条 claim 的话题落在目录里哪一节」。落到某节 → 进入文档校验（检索时还能带上这一节作提示）；落不到 → 标「文档范围外」，不判违规但在报告里单列供讲师看。

**区分的是两种「文档没写」**：文档「应该写而没写」（药品说明书一定有适应症一节，学员说了个文档没有的适应症 → D14 无支撑）vs 文档「本来就不管这个话题」（产品资料只讲保险条款，学员说了句公司发展历史 → 不该判）。

### roleplay 异议评分的佐证机制：结构上共用类型，缺的是第二份结构化数据

昨天查清了「异议没有语义点覆盖明细这一步」，今天崔扬追问「那异议最后怎么给出评分佐证」。

### 学员画像的数据模型（今天定型的表述）

事实表一行 = 「〈学员〉〈动作〉〈宾语〉, in〈取值域〉is〈取值〉」，**一行是一个「事实」个体**。

**判重键** = (learner_id, action, object, coalesce(scale,''), coalesce(condition,''))，`sub_profile` **不在键里**（"判重跨分类"）。

**两表拆分**：`facts`（fact_id, learner_id, sub_profile, action, object, scale, condition —— 不可变身份）+ `versions`（version_id, fact_id, value, narrative, times, valid_from, valid_to, status, source, method, evidence, idem_key）。facts 上是无条件唯一索引，versions 上是 (fact_id, …) 的部分唯一索引。

**GUMO 的 SituationalStatement 结构**：mainpart = subject / auxiliary / predicate / range / object，其中 **auxiliary 和 range 是可选的**（ch4 p59）——为 RDF 向后兼容，不是因为不重要。**auxiliary = 动作或关系，predicate = 宾语**（这个命名和逻辑里的 predicate 相反，是今天裁决禁用「谓词」的直接原因）。`hasInterest|playing` 那个竖线是 UbisList（§4.5.4），是语法糖，GUMO 的例子实际记了**两条**语句。

## 4. 经验与教训

### 分组和分类必须有出处，没有就说没有

崔扬问「模型层、组织层、治理层的分组有理论依据吗」，**答案是没有——那是我为了词表好查随手分的**。改成有出处的四组（逻辑词/注解词/映射词/项目词），每组注明出处，**并且给「项目词」那一组明确标注「本公司自定，无外部出处」，免得后来的人去文献里找**。

**固化**：写规范类文档时，每个分类维度都要能答「这个分法出自哪里」。答不出就不要写进规范，或者显式标注是自定的。

### 「同一个词在两套体系里指相反的东西」必须当场裁决

GUMO 的 `predicate` 指**宾语**（个体），逻辑的 predicate 指**概念或关系**。这不是叫法不同，是**指向相反**。

**不裁决的后果**：两边继续各说各话，而且看起来在说同一个词，误解不会暴露。**裁决方式是禁用那个词本身**，两边各改叫别的——比「规定它以后只指某一种含义」更干净，因为后者要求所有人记住一个反直觉的约定。

### 检索答不了「没有」，这是接口语义决定的，不是调参能解决的

检索接口的语义是「返回最相关的 top_k」。**「文档里根本没有」需要穷举，两件事在返回结果上长得一模一样。**

**三条判据可以直接复用**：接口有返回条数上限（这里是约 40 条，`top_k` 填 100 无效）；响应不带相关性分数（无法用「top1 分数都很低」做辅助信号）；召回率有实测上限（0.898，即约 10% 漏召）。

**正确的解法是换掉这一步的机制**，不是提高 top_k——要么全文直判（方案甲），要么入库时读成结构化清单（方案丙）。**方案丙那个「文档没写到的维度也要留一行，明确记『未涉及』」的设计是关键**，它把「我没找到」变成了「这里就这些」。

### 分类键不能依赖分类结果，那是循环

崔扬问「要不要按 Product Knowledge 和 Compliance 两类分别抽 claim」，答案是不要。**核心理由：「超出批准范围」这件事，要先把学员的话和文档比对完才知道它超没超。把它当抽取阶段的分类键，等于要求抽取器先知道判定结论。**

**判断方法**：拿一个具体用例走一遍（D8），看抽取阶段**在不读文档的情况下**能不能判出这个分类。判不出就是循环。

**该分的是不依赖判定结果的维度**——claim 的主题（适应症、用法用量、疗效数值…）在抽取阶段就能判，而且有两个实际用途。

### 上游误差会翻倍，所以不要在瓶颈环节分叉

抽取是整条链的准确率瓶颈，**上游漏抓下游补不回来**。分成两套抽取口径等于维护两个门槛，**漏抓的面积变成两倍**。

**这条可以推广**：任何「一处失误全链受损」的环节，都不要在那里做分支。分支要放在下游、放在可以各自独立修的地方。

### 重试策略要看「重试窗口覆盖多长」，不只看「重试几次」

「当天最多试 3 次、每分钟一次」看起来有容错，实际**重试窗口只有 3 分钟**。**一次 3 分钟的抖动就能报销一整天。**

**正确的做法是递增间隔**（1 分 → 5 分 → 15 分 → 30 分），让重试窗口覆盖到几小时，同时避免整天每分钟重试。**判据是：重试窗口要比预期故障时长长一个量级。**

### 报错文案说的和实测对不上时，实测优先，而且那本身是重要线索

代理报「request timed out (default is 30 seconds)」，**实测每次 3.02 秒返回**。六次配对全是 3.0 秒，**稳得不像巧合**。

**这个矛盾本身是最有价值的线索**——它说明超时不是它自己报的那一层，更像上游连接直接失败。**写报告时要把这个矛盾单独列成一节、附上时间戳配对表**，而不是转述它的错误文案。

### 排除法要找最小的反例

判断「是不是大请求打爆的」，不用统计分布，**找那个最小的请求看它有没有失败**就够了——`umu_tss-com` 只有 **437 个字符**、同样 500。一个反例就否掉了整个假设。

### 幂等的任务可以放行，不幂等的必须拦——这个区分今天成立了两次

今天调度器错时触发了十个任务。我放行了 sync、拦下了其余九个。**判据不是「重复执行不好」这种笼统的话，而是每个任务各自的具体伤害**：

| 任务 | 具体伤害 | 处置 |
|---|---|---|
| sync | 无（幂等，几秒钟，晚上那次照跑） | **放行**（事后看：提前推走了当天产物，有益） |
| 尾盘顾问 | 会创建 `/tmp/close_advice_*.txt`，**挤掉 14:45 真正那次的「今日已发」检查** | 拦下（事后看：14:45 那次正常来了） |
| 板块播报 ×3 | 脚本自己发 Slack，**会推三张午休时的重复卡片覆盖今早的真实播报** | 拦下 |
| 本体论精读 | 抓取脚本不是只读的，**会再多下一批原文进欠账** | 拦下 |
| daily-memory | 产出是「当天完整一天」，**会被晚上那次整体重写**，而半天的残本比没有更误导 | 拦下 |
| 日内流水线 | 未收盘，**会写进半天残缺数据污染基准** | 拦下 |

**固化**：判断一个错时触发要不要放行，问「它这一次执行会留下什么副作用，那个副作用会不会伤害正确那一次」。

### 查「查欠账」的工具本身有没有副作用

我为看欠账明细重跑了两次抓取脚本，**每次都下载了新文章**，把欠账从 27 推到 37。

**根因是这个脚本把「查状态」和「改状态」放在同一个入口，没有只读模式。** 用它查状态就必然改状态。

**固化**：**跑任何脚本之前，先问它是只读还是有副作用。** 如果一个工具既报告状态又改变状态，那它的输出只能看一次——**第一次的输出要留住，不要为了看细节重跑。**

### 用错证据来源会得出稳定但错误的结论

我今天多次断言「这个会话跑 2.1.252，重启后才切到 2.1.258」，依据是 `claude --version` 报 2.1.252。**但 `claude --version` 起的是一个新进程**，它报的是「新进程会用哪个版本」，不是「当前进程是哪个版本」。

**当前进程的版本在 `CLAUDE_CODE_EXECPATH` 环境变量里**，那才是权威的。

**固化**：查「当前进程/会话的状态」时，优先用环境变量或 harness 注入的字段，**不要用「起一个新进程去问」的方式**——那问的是另一个东西。

### 「env 启动时读」不是通例，要按项验证

我两次跟崔扬说「改 `CLAUDE_CODE_SUBAGENT_MODEL` 要重启才生效」，理由是「env 是启动时读的」。**实测推翻了**：改完没重启，子 agent 就已经用上 opus-5。

**固化**：把一个通用规律（env 启动时读）套到具体项之前，**如果有便宜的验证方式就验一下**。这次验证只花了一次子 agent 调用。

### 子 agent 自报模型不可信，要用 transcript 的 model 字段

子 agent 自报 `claude-opus-5`，我不采信，去它的 transcript 里提取 `"model"` 字段——**那是 harness 实际发给 API 的 ID**，两个来源对上了才下结论。

**注意**：这个版本的子 agent transcript 写在**单独的 output 文件**里，主会话 jsonl 里搜 `isSidechain` 是 0 条。要提取时只 grep model 字段，不要读全文（会撑爆上下文）。

### 数「有没有被使用」必须解析结构（昨天的教训今天又用上一次）

查 `ycui_deslop` 用过没有，文本搜索数出 4511 次「提及」、**真实调用 0 次**——那 4511 次全是 skill 列表每轮被注入 system prompt 的字符串。

### 崔扬追问的四段式值得内化

他每次贴的是**他看不懂的原话**（通常摘自我上一轮的回复），期望的回答结构是：**原话引用 → 一句话结论 → 讲清楚 → 举个例子**。举例要用生活里的对应物（体检报告、请假单、兴趣调查表、图书馆管理员），**而且例子要能一一对应到概念的每个部件**，不是泛泛类比。

今天有一条例子特别好用：**「打篮球」建成个体还是概念**，用「兴趣调查表里篮球是下拉框选项」vs「填『周六公司篮球赛』」来区分——同一件事，一张表把篮球当条目、一张当类别。

### 我上一条解释不清楚时要明确认领是哪里不清楚

关于 `喜欢(我, 打篮球)` 和 `(∃喜欢.打篮球)(我)`，我上一轮把两种写法并列在一张表里，**没有点明它们是两种建模而不是同一句话的两种翻译**——这是那条解释不清楚的地方，今天明确认领了。
