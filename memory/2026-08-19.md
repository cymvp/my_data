## 1. 今天获得的知识与技能

### 一条设计取向被记进项目 memory：靠建模减少 join，不靠增强 join 能力

崔扬的原话：

> **不用考虑源分散表，只考虑数仓方案。数仓表是依据分析需求进行设计的，所以本身数仓表就是可以通过合理的建模，减少 join 的发生的，这点非常重要，你一定要在设计这个项目的过程中有这个意识。**
>
> **我现在说的是整个项目的 join 的方式，不是只有讲师这一个概念！**

这条已写进项目 memory（`warehouse-first-modeling-over-joins`），连带「设计只考虑统一数仓、不拿分散原表的限制当约束」那一条。**以后不用再提醒。**

**仓库里已有对应机制，叫 `denorm_of`**，写在字段声明上：

```yaml
student_name: { column: learner_name, type: str,
                denorm_of: { via: submissionByLearner, field: name } }
```

它说的是：**这一列是 ETL 冗余进事实表的，它相当于走 `submissionByLearner` 这条关系取对面的 `name`。** 编译器见到对得上的声明，直接读本表这一列，不 join。

**它最要紧的一点是保留了关系那一份正本。** 指标声明照旧写 `attach: [{via: submissionByLearner, field: name}]`，它不知道也不关心事实表上有没有冗余列。**所以「建模消掉 join」不需要改任何一条指标声明**——ETL 加一列、mapping 加一行 `denorm_of` 就完了。现在有 5 处在用。

### 全项目 join 现状（把 45 条可编译指标在数仓通道全跑了一遍编译）

| JOIN 个数 | 指标条数 |
|---|---|
| 0 | **41** |
| 1 | 3 |
| 3 | 1 |

**数仓建模已经把绝大多数取数做成了单表扫描。** 有 join 的 4 条：

| 指标 | JOIN 接什么 | 为了取什么 |
|---|---|---|
| `course_learner_progress` | `dim_learner` | 学员姓名 |
| `session_incomplete_learners` | `dim_learner` | 学员姓名 |
| `course_instructor` | `dim_instructor` | 讲师姓名 |
| `course_department_progress` | `dim_learner`、`dim_department_member`、`dim_department` 三跳 | 部门归属与部门名 |

**前三条的 join 只是为了取一个名字**，按这条取向都该消掉——ETL 补一列姓名、mapping 加一行 `denorm_of`，**指标声明一个字不改，join 自己就没了**。

**第四条不一样，它挡着一个业务口径**：实测 1561 个学员里有 **18 个同时属于多个部门**。把部门冗余成事实表上一列，那 18 个人只能落进一个部门——**这是改语义，不是省一次 join**。要动得先定「一个人算在哪个部门」。

### 今天核出的真缺口：投影免了 join，过滤没免

同一条关系、同一个字段，两种写法编出来的 SQL 差别很大（都是实测）：**当成输出列取（`attach`）不 join，直接读事实表上那一列；当成过滤条件用（`via`）仍然会 join 过去。**

`denorm_of` 这个机制只覆盖了投影侧，没覆盖过滤侧。**这正对着崔扬那条取向，是他今天这轮追问带出来的。**

### `concept: Exam` 是承重机制，不是描述——删掉就起不来

崔扬问 `session: { column: session_id, type: int, concept: Exam }` 里那个 `concept` 是干什么的、算不算定制逻辑。

**结论：它声明「这一列装的是哪个概念的标识」。做了变异验证——把它删掉，系统直接拒绝启动。**

**这一处在纠正一个名字**：答题明细表 `exam_detail` 上那一列物理名叫 `session_id`，**但它装的不是课程小节的 ID，是考试的 ID**；数仓建表时改对了，叫 `exam_id`。`concept: Exam` 把这件事说出来——两个通道物理列名不同，装的是同一种东西。

（原委在 tbox 的 `Exam` 说明里：考试有多种承载形式，`exam_session` 型寄宿在课程小节上、和小节共用同一个 ID，所以历史上这一列随手叫了 `session_id`。）

**五个消费者，分布在三个时刻**：

| 消费者 | 代码位置 | 什么时候 | 读它干什么 |
|---|---|---|---|
| 定位参数推导 | `poc/loader.py` 的 `_locators` | 加载期 | 判定「这条指标能不能按考试收窄」 |
| 概念声明校验 | `poc/loader.py` 的 `concept_declaration_errors` | 加载期 | 用了参数的列必须挂概念，不挂就拒绝启动 |
| 输出列里哪一列装实体 ID | `poc/loader.py` 的 `entity_id_columns` | 回答后对账时 | gates 检查「说的是这个人，数据行里却是另一个人」 |
| 隔离条件注入 | `semantic/compiler.py` 的 `_field_by_concept` | 编译期 | 在实体上找概念是 `Enterprise` 的那一列 |
| `entry_relation` 绑定列校验 | `semantic/compiler.py:809-826` | 编译期 | 参数标识的概念必须等于绑定列的概念 |

**我自己在这条上犯过一个错、被崔扬揪出来**：他问的是「在数据查询过程中起什么作用」，**正确答案是「它在生成 SQL 的过程中不起作用」**，而我一直在讲加载期的事、没把这句话说出来。**判据：被问「在 X 过程中起什么作用」时，如果答案是「不起作用」，要先把这句说出来，再讲它在别处起什么作用。**

### 指标不能定义成 tbox 概念——而且这个仓库为此栽过一次

崔扬提出「小节完成数、课程完成数、报名数应该每个都是一个 tbox 和一个 entity」。**这个设计不对，但他的直觉有一半是对的。**

**为什么不对**：**entity 的定义要求它能回答两个问题——一行代表什么，有哪些列。** 「小节完成数」两个都答不出来：它不是一批行，是对一批行做 `COUNT(DISTINCT student_id)` 得到的一个数。给它建 entity，`table:` 写什么表名？`fields:` 写什么列？加载期第一道校验就过不去（`semantic/mapping.py:108` 起）。

按 CLAUDE.md 那条判据的第二问——**同类需求再来一个，要不要再写一段？** 要。注册表现有 60 多条指标，每条至少一个分子、很多还有分母，**那是上百个绑不到任何物理表的 entity**。

**更硬的一条：这个仓库栽过一次，栽的就是「把一个数字登记成口径」。** `exam_attempt_buckets` 那条指标把「考了几次、过没过」这个切片登记成三档口径，标签写「重考后才通过」而算式是「提交次数>1 且最高分达标」，**17 实为 11+6，矛盾在注册表里活了十天没人发现**，2026-08-09 整条删掉。

**tbox 登记的是「世上存在的一类东西」——学员、课程、考试、一条完成度记录。数字不是东西，数字是对东西做统计的结果。**

**他直觉里对的那一半**：那三个数确实应该各自独立可用、可复用。而且查下来**其中两个本来就已经独立登记了——登记的层是指标，不是 entity**：`course_session_complete_user`（小节完成人数，课程 752468 的小节 7271640 实测 105）、`course_participate_user_by_completion`（课程 381287 实测 1273）。

**所以「小节完成率」的分子确实有两个正本**：一份在 `course_session_complete_user`，一份内联在 `session_complete_rate` 的 `compose.inputs.done` 里，**两者是同一个算式**（同一张表、同一个条件 `session_completed_only`、同一个 `count_distinct of: learner`）。哪天小节完成的判定口径改了，改一处漏一处不会报错。**这是一笔真实存在的账。**

### 「定位参数」是什么，以及值从哪来

**定位参数指的是：这条指标接受哪些参数来收窄范围**（例如「只算这门课的」「只算这场考试的」）。**这份清单进路由的提示词**，大模型照它判断某条指标能不能答当前这道题。

实测 `kp_correct_rate`（知识点正确率）的定位参数是 `['course_id', 'exam_id']`。`exam_id` 的推导链是：指标声明里有 `{ field: session, op: eq, param: exam_id }` → 这个参数绑在 `exam_answer` 的 `session` 字段上 → 查那个字段的 `concept` 得到 `Exam` → `Exam` 在 tbox 里声明了 `identified_by: exam_id` → 所以 `exam_id` 算一个定位参数。

**值的三条来源**：

| 来源 | 什么时候 | 真实例子 |
|---|---|---|
| 路由从问句里抽出来 | 选完指标那一步，和指标 ID 一起返回 | 问「552160 这门课的测评考得怎么样」，抽出 `course_id=552160` |
| 调用方直接传 | 进链路之前 | 页面已在某门课详情页，课程 ID 是页面上下文 |
| 由另一个 ID 换出来 | 参数解析那一步 | 只点名考试 `6589717`，经 `course_of_exam` 把所属课程补上 |

**抽出来的东西不是原样收下的**：`poc/chain.py:447` 的 `_extract_params` 有一道白名单，**白名单之外的键一律丢弃**——理由是模型可能编出参数名，让它们进到编译参数表，等于把 SQL 的一部分交给模型写。白名单本身也不是手写的，它来自 `nameable_params`（声明了 `identified_by` 且不是隔离轴的那批概念的标识参数名）。

### `course_id` 是槽位名，不是值——这一点我上一轮说含糊了

**声明里 `anchor.param: course_id` 的意思是「去本次查询的参数表里取键名为 `course_id` 的那一项」，值要到运行时才有。** 我上一轮说「出发点由 `course_id` 给」，听起来像里面已经装着某门课。

到了编译器手上它就是一次按名字取值（`semantic/compiler.py:835`）：

```python
frag = _cond_sql({"field": bind_to, "op": "eq", "param": pname}, ctx)
```

同一份声明喂不同的值，编出来的 SQL 只差那个数字（实测）：`course_id=552160` → `WHERE t0.course_id = 552160 AND (session_type = 10 AND is_deleted = 0) AND enterprise_id = 1791`；`course_id=724975` → 同形，数字换成 724975、企业换成 227。

**一个都没传会怎样，也实测了**：`CompileError: 条件 course eq 缺参数 course_id`——**报错，不是「那就列出全部课程的考试」。这条声明里没写 `optional: true`，所以缺参数直接拒绝编译，这就是「不静默降级」在这一层的落点。**

**凭什么这个名字代表「课程」**——不靠名字看起来像，两道校验把名字和概念钉死（`semantic/compiler.py:809-827`）：① `course_id` 必须是某个概念声明的对外标识（反查 tbox 的 `identified_by`，查到 `Course`）；② 绑定列的概念必须等于第一道查出来的那个概念（绑定列是 `steps[0].join.to`，即 `exam_session_dim` 的 `course` 字段，`concept` 是 `Course`）。任一条不成立就拒绝编译。

### 关系有三种用法，`entry_relation` 是第三种

编译器对关系有三条不同的代码路径：

| 用法 | 声明写法 | 干什么 | 真实例子 |
|---|---|---|---|
| join 进主查询取对面一列 | `attach: [{via: refersToSession, field: title}]` | 已有主查询，顺便把小节标题带出来 | 小节完成人数 |
| 条件里走过去过滤 | `{field: enterprise, op: eq, param: enterprise_id, via: examSessionOfCourse}` | 已有主查询，在对面实体上加条件 | `exam_catalog` |
| 关系本身当行来源 | `entry_relation: courseHasExamSession` | **没有主查询**，从一个字面值出发，把这条边编译成独立结果集 | `course_exam_session_list` |

**前两行都要求「已经有一个主查询」，第三行不是**——「给我这门课的考试清单」这件事没有主查询，它要的就是关系本身作为行的来源。

`semantic/compiler.py:754-757` 记着它为什么被加出来：前两种都要求已有主查询，而参数解析要的是「给定 `course_id` 把考试独立列出来」这种独立行集，**关系原先给不出，所以那件事被绕成了一条手写的指标查询**——那正是四份副本里的一份。

他的原话：

>

**查 git，他的判断是事实。** `kp_correct_rate` 那两条定位通路不是一起设计的：「按课程筛」（`scope: course_sessions`）在 2026-07 语义层首次提交里就有；**「按测评小节筛」那条是 2026-08-11 才加的**（提交 `20e2bbb`），而那次提交自己把理由写进了注释：

**所以第二条通路是一道题答错之后补的，不是从「这条指标该能按哪些对象筛」推出来的。这就是补丁的形状。**

### 「某个老师的课程里知识点正确率如何」今天答不了，有三道卡口——穷举只是第三道

**第一道：讲师压根不能被点名。** `tbox.yaml` 里 `Instructor` 的 `identified_by` 是**空的**。这一栏空着意味着用户在问句里点名讲师时，**系统没有参数名去装它**，路由那一步就抽不出来。跟 `Learner` 同样状况。**这一道不打通，后面两道全免谈。而它要填什么值（讲师用哪个号对外）是业务决定，不是代码能查出来的。**

**第二道：概念层的路是通的，物理层断在第一跳。** `rbox.yaml` 里这条链完整存在：答题记录 `answerInExam` 考试 `examSessionOfCourse` 课程 `courseTaughtBy` 讲师，**三条关系的基数全是 one**（走完不会把答题明细的行数撑大，这对建模消 join 有利）。但物理映射只有两条到位：

| 关系 | 有物理映射吗 |
|---|---|
| `answerInExam`（答题记录到考试） | **没有** |
| `examSessionOfCourse` | 有（join 到 `course_dim`） |
| `courseTaughtBy` | 有（join 到 `instructor_dim`） |

**四个节点三条边，缺一条就走不过去，而缺的那条恰好是第一跳。** 而且这不是个例：**53 条关系里只有 17 条有物理映射**——「登记了没接线」这个形状仓库已识别过一次（`examSessionOfCourse` 曾经是零消费者）。

**第三道才是穷举那一层，而它排在第三位——前两道不解决，写了也不生效。**

**崔扬提的方案（用关系描述过滤路径）编译器已经支持**，写法是条件上加 `via`（`exam_catalog` 就在用：按企业筛，但企业列不在考试表上，经 `examSessionOfCourse` 走到课程表上去比）。**所以他的方向和现有机制不冲突。**

### 一对近乎重复的声明，是已知事故的残留

崔扬问「`scope` 引用的范围和 `entry_relation` 的 `anchor.param` 解决的场景很像」。**内容上确实有一对近乎重复：**

| | `course_sessions`（scope） | `courseHasExamSession`（关系） |
|---|---|---|
| 从哪出发 | 课程 | 课程 |
| 到哪 | 小节维表 | 测评小节维表（**同一张物理表**） |
| 怎么接 | 课程列相等 | 课程列相等 |
| **额外条件** | **没有** | `type = 10` 且未删除 |

**差别只有一个条件。** 这正是 CLAUDE.md 记着的那次事故：「课程有哪些考试」被写进四个地方（关系、指标 `course_exam_session_list`、范围 `course_sessions`、目录检索 `exam_catalog`），**而 `course_sessions` 少了 `type=10`，于是它其实是「全部小节」而不是「测评小节」**。

裁定是两份都保留（说的不是同一件事：一份「全部小节」、一份「测评小节」），但 `course_sessions` 上现在挂着警告注释。

**但机制上两者不同**：`entry_relation` 是整条查询，有三个输出列和排序，**用户会看到它的结果**（反问时列出 31 个考试让人选）；而 **scope 的结果用户永远看不到**。

### csrs：实证了一个隐性 bug——CE 的建表 DDL 从来没执行过

给 MR !162 做讲解页时核出来的：**master 上 `@app.on_event("startup")` 注册在 494 行，而 601 行把 `lifespan_context` 整个替换掉了**（cognee 的自定义 lifespan），所以那个 `on_event` 从不执行——**CE 的建表 DDL 压根没跑过**。

**这条的意义**：本 MR 把它从 `on_event` 挪到 `lifespan`，修好之后**这批 DDL 会第一次真正跑，而且跑在存量表上**，单事务、失败则服务起不来。作者已加守卫并附了只读预检 SQL。

**通用形式：一个注册点被上层整体替换掉时，注册在它上面的东西会静默失效——不报错、不告警，只是永远不执行。**

### umu/prove：一整天的追问，没有代码改动，产出是三笔账和一条取向

## 4. 经验与教训

### 盘中重建 cron 有实际代价：会立刻放出一轮全量触发

上午 11:00 BJT 全量重建 9 条之后，**紧接着 7 条集中触发了**——sync、daily-memory、三档板块播报、日内流水线、自愈检查，**全都不在自己的排期点上**（它们的排期分散在 9:15、10:00、10:15、10:30、16:00、21:00、23:00，没有任何一个该在 11:05 触发）。

**这不是「排期到点」，是重建这个动作本身让它们全部入队了一次。**

如果没拦下来，后果会是：**一份半天的 memory 覆盖掉完整版、三条重复的 Slack 播报、一次会被守卫挡住的日内采集。**

**判据：要重建 cron，放在收盘后或开盘前，避开有实际产出的时段。**

**另外今早那两条（早盘 10:56、尾盘 10:57）错时发生在重建之前**，那是队列积压（cron 只在 REPL 空闲时触发）——**两个原因叠在同一天，重建治不了积压。**

### 「用户重复同一个请求」的第一反应应该是「他看到的东西没变」

崔扬一小时内两次发同样的两条要求（重建 loop + 改股票程序）。**我第一次做完了代码改动并汇报了，但他看到的悬浮窗还是老样子**——因为进程是 8 月 11 日启动的，跑着旧代码。

**判据：交付物不是「代码改了」，是「用户能看到那个变化」。** 涉及常驻进程的改动，重启（或明确告知需要重启并问要不要现在做）是交付的一部分。

**推论**：第二次我没有再重建 cron（那是重复且有代价的），而是去做了真正没交付的那一步。**重复的请求里，要分辨哪一部分是真的没做到。**

### 直接改配置文件不够——运行中的进程会把它写回来

移除做 T 时，**直接编辑 `~/.stock_watch_trade.json` 不够**：运行中的进程内存里持有 `self.books`，下一次 `save_books()` 会把它写回文件、把删除覆盖掉。**所以必须改文件 + 重启，而且重启后要回读一次文件确认。**

### 被问「在 X 过程中起什么作用」而答案是「不起作用」时，要先说这句

崔扬三次追问 `concept: Exam` 在**数据查询过程**中起什么作用，我三次都在讲加载期的事。**正确答案是「它在生成 SQL 的过程中不起作用」**——先把这句说出来，再讲它在别处（加载期、对账期、编译期的别的用法）起什么作用。

**这是「答非所问」的一个具体形状：问的是 A 过程，答的是 B 过程，而且没说 A 过程里其实没有它。**

### 生成产物之后要校验产物本身的规模

`content.json` 里的 SVG 因为 Python 条件表达式作用域写错（`if False else ""` 吃掉整个拼接串）**被压成 356 字符，相当于一张空图**，而生成脚本**没有报错**。是后来做几何校验时才发现的。

**判据：生成脚本没报错 ≠ 产物是对的。要校验产物的规模（字符数、节点数、条目数）。**
