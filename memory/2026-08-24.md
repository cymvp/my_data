### 「单独拿出来还能不能成一句话」——今天最重要的一条判据

这是 cuiyang 逼出来的，用来判断**两个东西该拆成两条记录、还是拼进一格**。

学员画像设计里原先有个写法：用竖线把两段拼进一格，比如 `复述|迁移`，表示「能复述但迁移不了、卡在衔接上」。cuiyang 直接反驳：**复述和迁移是两个不同的谓词，如果复述好、迁移不好，那就应该记两条，而不是因为一个中间状态就混在一起。**

**他是对的，而我错的原因值得记**：我当时列了三个选项（每种衔接都进词表 / 只记落点 / 竖线拼一格），**「两条记录」这个正确选项根本没上表**。漏掉它是因为 PM 的提示词把这件事表述成一次过渡（「从识别一个概念过渡到自己复述，容易卡住」），**我把业务的表述当成了存储单位——表述是一句话，事实是两个。**

**拼一格的四条实害**（拆开之后全部消失）：

| 问题 | 具体后果 |
|---|---|
| 次数只有一个 | 「识别顺畅」可能观察到 5 次、「复述易卡」只 1 次，两个截然不同的证据强度被压成同一个数 |
| 确认与反驳没法分开落 | 他复述通了要反驳哪一半？整条反驳的话，识别那一半从来没错过 |
| 读取要靠模糊匹配 | 问「他在复述上卡不卡」，两条记录是一次等值查询，拼一格得匹配第二段字符 |
| **次数会碎在组合上** | 10 个认知动作有 90 种有序组合，`举例\|复述` 是一条全新记录、次数从 1 开始，而「复述易卡」其实已经是第二次观察了 |

**最后一条是致命的，而且它的失效形态要记住：不报错、字段看着在工作、读出来一直是空的。**

**但同一条判据的另一边是「该拼」**：`概念类|先给具象引入` 保留。判据一句话——**两段各自能独立成立的，拆；一段是另一段的限定条件、拆开会丢掉合取关系的，拼。** 「他识别得了」自己成立，所以拆；「内容是概念类」不是关于这个学员的事实、而且「先给具象引入」在概念类内容上有效、在程序性内容上可能无效，拆开就分不出来，所以拼。

**一个好用的类比（cuiyang 认可的那个）**：你点一份「加辣的牛肉面」。牛肉面能单独下单，它自己就是一道菜；**加辣不能单独下单，光说「加辣」店员不知道你要什么。** `hasInterest` 是牛肉面，`playing` 是加辣；而 `复述` 和 `迁移` 两个都是牛肉面。

### GUMO 的原文我读反了三处，三条全部撤回

**GUMO** 是一套用户建模本体（General User Model Ontology），出自一本讲用户建模的书。今天核了原文（书里 §8.1.4 第 159 页、§4.5.4 第 80 页），我先前的三个说法全错：

| 我先前说的 | 原文实际是 |
|---|---|
| GUMO 用竖线是因为拆开会丢东西 | 理由是**词表会爆**——原话是可以把「看球」「踢球」作为「足球」的子类加进本体，但对所有运动都这么做，本体会长得非常快 |
| GUMO 那个例子把两个事实拼成一条 | **原文记的本来就是两条语句**，踢球那条取值「否」、看球那条取值「是」，各有自己的取值 |
| 竖线是辅助词位置专用的写法 | §4.5.4 定义的 UbisList 是**通用值语法**，任何属性的值都能是竖线分隔的一串；原文里辅助词和谓词位置都用了 |

**还有一层**：这种写法相对 RDF 的好处是**把带多个子节点的空白节点缩写掉**——**它是语法糖，不是一种新语义**。

**而 GUMO 为什么不把限定放进别的属性？** 因为它那 25 个属性里**没有能装「适用条件」的格子**。五个分组逐个看：主体（主语/辅助词/谓词/取值范围/取值）五格已满；情境只有时间和空间（它为普适计算而做，「情形」就是何时何地）；解释讲这条记录怎么来的；隐私和管理无关。**所以拼合是它在受约束下的做法，不是更好的做法——而我们和它的差别是我们可以自己加列，它不能**（它是给多方共用的公开本体，加属性要所有人接受）。

### 一列该不该进判重键：判据 + 一个必须不进的例外

**判据：这一列的值变了，说的是不是另一件事。**

| 列 | 值变了意味着 | 进判重键吗 |
|---|---|---|
| 学员标识 | 另一个人 | 进 |
| 字段 | 另一类事 | 进 |
| 谓词 | 另一个方面 | 进 |
| 刻度 | 另一件事（课题来源 vs 课题权重） | 进 |
| **适用条件** | **另一条规律** | **进** |
| **取值** | **同一件事的新取值** | **不进** |
| 叙述、次数、状态 | 同一件事的附加信息 | 不进 |

**取值那一行是关键：它必须不进。判方向就是拿新旧取值比大小——取值一进判重键，同一件事的每个新取值都会变成一条新记录，判方向这套机制整个不存在了。**

**而适用条件必须进**，是 cuiyang 追问出来的：假设「先给具象引入」在概念类内容上有效、在程序性内容上无效，两行的判重键就完全一样，**系统会把第二行当成对第一行的反驳，次数从 1 减到 0、状态转休眠——两条互不矛盾的规律被判成互相矛盾，然后一起消失。**

**他还指出了拼一格的一个安全性质是我原先没写的**：拼在谓词里的话，判重参与是自动的、忘不掉；独立成列就变成一个人可以做错的决定。**但两边失效性质不同——加一列的风险是一次性的（建表那一下）、可测的；拼一格的风险是长期的。** 所以仍取加列，但配一条测试用例焊死。

### roleplay 的多智能体设计与状态机

**5 个 agent**：Customer（扮演客户、生成回复）、StageEvaluator（判环节）、TrustEvaluator（判信任度）、ConcernObjectionEvaluator（判关注点与异议）、InfoExtraction（提取信息）。三个评估器是**三个 goroutine 并行 + `wg.Wait`**（`coordinator.go:398`）。

**四组状态**：环节（7 种，`opening` 到 `ending`）、信任度、关注点、异议状态。**含义全部写在 prompt 里，代码只存字符串。**

**InfoPool 的机制值得单独记，因为它的形状很聪明**：

- **不是每轮做一次摘要，而是每轮往一个池子里追加 0 到 2 条。** 提取的输入只是**上一轮的一问一答两句话**，不是整段历史。prompt 明确要求「宁少勿多，每轮最多 2 条，大多数轮次应该是 0~1 条，每条不超过 20 字，第一人称」。
- 条目带 `round_number` 追加，同分类内做 **Jaccard 相似度去重、阈值 0.7**。**池子只增不减、也不重写。**
- **两个消费者看到的范围不同**：InfoExtraction 自己看全部（用来判重）；Customer 只看 `round_number ≤ 当前轮 − 3` 的条目。**这条截止线是刻意的**——第 8、9、10 轮的原话还在对话窗口里，摘要只补窗口之外那一段，**原文和条目各管一段、不重叠，避免同一件事在 prompt 里出现两遍**。
- **它敢无上限累积的原因是提取端把量压住了**：30 轮的对话池子里大概十几条、每条 20 字以内，加分类头总共几百字。**池子本身没有任何淘汰机制。**

**关注点的正本链路是三段，中间有一次视角翻转**：作者在 ucs_v2 配「关键信息 + 语义点」（`key_messages_with_semantic_points`，字段在 `internal/infrastructure/api/chatbot.go:563`）→ 生成剧本时调 ullm 的 `generate_drama`，用 `roleplay_drama_prompt` **把关键信息翻成客户视角的关注点**，prompt 里的约束写得极死（「配置了 N 条关键信息就输出 N 条 concernPoint，一对一对应，不合并不删减不新增不补充」）→ 运行时的 concern 状态机。**而练习结束后评估时直接用原始配置，不经过 concernPoints。**

**「信息传递」这个词在三个层面指三样东西**，是这套系统最容易绕晕的地方：环节类型的标识是 `value_demonstration`（中文叫信息传递、英文标识叫价值展示）；环节内的模式叫「信息传递模式」；评估维度是 ullm 的三个端点。**ucs_v2 的枚举名 `SectionTypeInformationPass` 和 flag 值 `value_demonstration` 不一致，就是这个历史遗留的痕迹。**

**关于方法论的选型判断**（今天补进文档第五节开头，因为不写在那里下一个读文档的人会问同样的问题）：**如果只选一套本体工程方法论，推荐的不是 METHONTOLOGY 而是 SAMOD（2016 年，把敏捷开发原则搬进本体工程）**；METHONTOLOGY 的位置是补 SAMOD 缺的那一块——规格说明该写什么。METHONTOLOGY 能用的只有三分之一，四样该用的是：需求规格说明模板、「三个贯穿全程的活动」结构（尤其评估要在最早阶段做）、中间路线加术语表、骨架预先定细节演化迭代。不用的三样：形式化与实现两个阶段（绑在 1997 年的框架系统上）、它 1995 年的评估框架、它的文档化建议（原文自陈这个领域还没发表过任何工作）。

**`field` 与 GUMO 辅助词的关系今天更正了**：GUMO 的辅助词是**关系类型**（`hasProperty`/`hasInterest`/`hasKnowledge`/`hasPlan`/`hasRegularity`），回答「主语和谓词之间是哪一种关系」；**我们的 `field` 是记录分组键**，决定这条记录用哪张词表、哪套刻度、给不给学员看、随不随时间变、单值还是多值、默认怎么消解。**两件事有重叠但不是同一件事，而我先前说「就是关系类型」，这个错误正好盖住了两处真实的设计问题**：

- **岗位的 `predicate` 是一个常量**（永远填「岗位」），等于一列不带信息。这是为结构统一付的代价——接受它但要知道它在那里。
- **教学适配规则隐含两种关系，这是它该拆的结构性证据**：把两半分别读成句子，**主语都不一样**——正面是「某个手段对这个学员奏效」（主语是手段），反面是「学员在某类动作上卡住」（主语是学员）。**一个字段对应两种关系，说明它是个文件夹、不是一种关系。这条理由比刻度不同、类型异质都硬。**

**决定不加 `auxiliary` 列**，理由是它只解决一个问题（教学适配规则的两半），而另外四个字段的辅助词都是常量、加了也是一列不带信息；而那一个问题已有两条更直接的路。**但写进了重估条件**：如果将来同一字段内部在派生属性上出现分歧，那时就该重新考虑把关系类型独立成列。

## 4. 经验与教训

**「三选一」的表里如果有一个选项明显更好，先问那个正确选项是不是根本没上表。** 今天最大的一次纠正就是这个形状：我列了甲乙丙三个方案，丙看起来比甲乙都好——**因为真正对的那个（拆成两条记录）根本没进入选项集**。**判据：当某个方案在对比表里"完胜"时，那通常不是它好，是对手挑得不够。**

**不要把业务的表述当成存储单位。** PM 说「从识别过渡到复述，容易卡住」，那是一句话；而事实是两个。**拆成两条不是重新解释业务，是把一句话规范化。**

**「单独拿出来还能不能成一句话」是个能反复用的判据。** 能就拆，不能就别拆。牛肉面能单独下单，加辣不能。

**引用原文之前先去核，尤其是"我记得它是这么做的"。** 今天在 GUMO 上错了三处，全是凭记忆引用造成的，而且**其中一处正好被我用来支持一个错误结论**——cuiyang 追问「为什么 hasInterest 和 playing 不能拆成两个辅助词」逼我去核书，才发现原文记的本来就是两条。**判据：如果一个引用正在承担论证的重量，它必须被核过。**

**代词是禁止的，这条 cuiyang 已经说过多次而我今天又犯了。** 原话：「"会上天舒给的那个理由仍然成立" ==> 我已经说了很多次了，不要用这种代词，我完全对不上是哪个理由！」**每次提到一个理由、一条判断、一个结论，都要把内容重述出来，不许用「那个」「上面那条」「如前所述」指代。** 今天为此专门 grep 了全文的含糊指代并逐处修掉。

**给别人填的表，自己先填一版。** cuiyang：「你如果要 PM 来填表，那你首先要自己先给出一些例子，甚至给出你建议的填表，让 PM 参考并修改，否则 PM 如何知道怎么填？」**做法：每条加「依据」一列（标明是他的原话还是我们猜的，他据此判断留还是删）、每张清单后给「填好之后长什么样」的真实形态、开头改成「你在初稿上改就行，不用从空白开始」。**

**对抗式审查的价值在于砍掉措施，不在于凑出达标的数字。** 今天四个目标里两个明确不可达，我把它写出来而不是把数字凑到看起来达标。**而对抗真正的产出是两条重头措施被证伪，且都给出了具体失败场景**——「三个评估器合并」在延迟上是零或负贡献（并行取 max 不取 sum）且失败半径从 1/3 抬到 3/3；「摘要异步」会打掉一道明文写在 prompt 里的容错。

**裁决 agent 的输出不能直接转述，承重的新论断要自己核。** 今天挑了三条最关键的验证，**三条都成立，而且验第三条时发现一个 workflow 漏掉的缺陷**（Customer 的行为准则要求扫 5-8 轮，代码只给 3 轮）。

**「进程活着、日志无异常」推不出「程序正常」。** 浮窗程序今天不刷新，而进程活着、无 traceback、`_fetching` 没卡。**我推翻了自己两次**：先猜 `drain()` 里 `_update_labels()` 不在 try 里、抛异常会让重排链条永久断掉（**这个 bug 形状是真的，但今天不是它**——stderr 零 traceback）；再猜后台线程挂在 SSL 握手上（**也不是**——当时 3 次 lsof 采样全空，但那是采得太稀撞空了，连接存活不到 1 秒而我 4 秒采一次）。**改成 0.5 秒采一次之后，20 秒里 7 个采样点抓到连接、间隔稳定 3 秒。真正的结论是后端每一环都正常，冻的是显示层**（macOS 上 Tk 长时间运行后的重画冻结，已连续跑 2 天 22 小时）。**判据：这类故障不写日志、不抛异常、进程状态正常，唯一能区分的办法是去查数据链有没有在动，而不是看进程在不在。** 决定性证据是 `pulse_store.jsonl` 每 3 秒追加一行、最后一行与当前时刻同秒。
