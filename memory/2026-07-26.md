- **真因（是建模缺陷，不是路由算法问题）**：加考试域时复用了 `Exam` 概念，但本体里"测评小节"是 `Session`（`vote_session` 里 type=10 的行），而通过率指标挂在 `ExamSubmission` 上，**Session 与 Exam 之间没有任何关系边**，模型无法确认"测评小节 X"和"一场考试"是同一批数据，于是时选时不选（表现为失败题每次不同）。

## 4. 经验与教训

- **没验证过的归因不许当结论输出，更不许配着方案对比表建议动手**：今天连续两次给出未经验证的根因（候选集太大、问法贴合度），还配了 A/B/C 方案表建议改路由代码——都被受控实验推翻。真因是本体缺一条边，若按错误归因去改路由代码就是纯返工、断边还在。**用户一句"你验证过么"挡掉了返工。** 原则固化：归因先做受控实验（改一个变量、多跑几次看差异），拿到证据再下结论；说"我没验证过，这是假设"比给一个自信的错误归因诚实得多。
- **排查路由/召回问题，直接看模型给的理由最快**：绕了两圈错误假设，第三步"直接看模型为什么拒选"一下命中真因。模型的拒选理由（"本体里没有 X 到 Y 的路径"）是可信的诊断信号，因为它指的是治理资产的缺口。
- **质量退化未必是算法问题，可能是数据/本体建模缺陷**：加考试域引入的断边导致退化，"退化恰好在加考试域之后出现"是关键线索。排查时先看"这次退化和最近的哪个改动同步出现"。
- **本体系统的自我暴露能力是它相对"LLM 直接写 SQL"的核心优势**：缺陷以"模型拒答并说明缺什么关系"的形式暴露，而不是被一个看似合理的错误数字掩盖。
