## 1. 今天获得的知识与技能

- **数仓宽表化的两条硬原则（用户拍板，已在 prove 落地）**：① JSON/半结构化数据必须在 ETL 阶段展开成普通列，不许在列里留 JSON;② 尽量用宽表(事实表把常用维度属性冗余进来)，减少查询期 join。prove 据此重做数仓:题目分值从 `setup` 的 JSON 键变成 `dim_question.score`，出题规则 JSON 展开成 radio_num/radio_score 等列，提交明细自带考试标题/课程标题/学员姓名/满分。实测收益:4 个用 attach 取维度的指标,在分散原表侧各走 1 次 join,在数仓侧全是 0 次。
- **宽表冗余列的"静默取错列"陷阱**（今天新踩的坑,又一个静默错误案例,见 [[2026-07-24]] 的 course_id 静默降级）:宽表短路优化一开始按字段名匹配——attach 输出叫 `title`、主表也有字段叫 `title` 就直接替换。但参与明细表同时有 `course_title` 和 `session_title`,撞错一个,行数/类型/非空全部正常,只有数字悄悄取自另一个维度,对账都未必看得出。解法:冗余列必须在映射里声明它替代哪条关系的哪个字段(`denorm_of: { via: refersToSession, field: title }`),对得上才短路。加这约束当场抓到两个写错的关系名 + 一个没人用的冗余列。
- **完成度指标的口径可以大幅简化（和课程组确认后）**:prove 的"课程完成人数"原本有两张表——`data_course_completion`(课程×学员,负责"圈人":取参与学员名单)和 `data_session_course_completion`(课程×小节×学员,负责"判完成":每人每小节的完成态)。页面 PHP 算法是 5 步(圈人→取小节清单→读小节完成态→逐人累加 complete≥2 的小节→判定并计数)。但登记的指标其实只读课程级表预算好的汇总列一条 SQL 出数(`all_user_cnt=all_session_cnt`),结果与逐小节手算一致(课程 381287 都是 71 人)。课程组确认历史 bug 已修后,**离线指标可以直接用 `data_course_completion.complete` 字段判断完成**,不必走小节级重算——屏蔽底层细节、保证取数口径一致。据此引入"离线指标 vs 实时指标"的区分:总览页用实时(每次重算)、趋势页用离线(complete 快照,更新不频繁),让 LLM 知道该用哪个。
- **知识库"自我投喂"污染召回的风险与规避（csrs Slack 摘要功能的核心洞察）**:如果把 Slack 频道里 @bot 的提问也沉淀进知识库,会出现"有人问过 X,结论:无"这种只有问题没答案的空记录;而这个库正是 bot 回答时检索的同一个库,下次别人问 X 就可能命中这条空记录——不是不生效,是**主动污染召回**。更严重的是方案 B(把 bot 的回答也沉淀)会让 bot 自己生成的答案喂回自己的库,答错一次就被固化成"事实"、反复自我强化,且从结果看不出来源是自己。规避手段:摘要消息正文打固定前缀 `[CSRS摘要]` 让过滤器排除自己(不能用 bot_id,因为问答 bot 和发摘要是同一个 App、分不开)、prompt 规定"没得到答复的问题整段丢掉不许写结论:无"、transcript 里给 bot 消息标"知识库助手"避免 LLM 把答案当问题。
- **同一 App token 开第二个 Socket Mode 连接会分流事件**（csrs 排障发现）:Slack 在多个 Socket Mode 连接间分发事件(不是广播),所以本机起一个 bot 调试,会把生产频道的一部分真实请求分流到本机处理,进程一停正在处理的请求就丢。调试生产 bot 要注意这个。
- **CSRS 检索与答案生成是分离的**（dev 排障学到）:`/gateway/search/retrieve` 默认 `with_answer=False`,这个模式下 CSRS 只返回 chunks、不生成答案,最终答案是调用方(uask 侧)自己用 chunks 生成的。所以"答非所问"要先分清是 CSRS 检索侧没召回对,还是 uask 生成侧的问题——今天那个日文提问,CSRS 召回的 chunk 里就有逐字答案(rerank 0.95),问题在 uask 生成侧。

## 4. 经验与教训

- **静默取错值是反复出现的最危险 bug 类型,凡"找不到就兜底"都要查"对不上时会不会假装成功"**:今天宽表冗余列按名字撞错列(prove),延续 [[2026-07-27]] 的 cognee 静默建库、[[2026-07-24]] 的 course_id 静默降级。通用判断已成型:任何"按名字匹配替代""找不到就新建/用默认"的逻辑,都要加显式声明+校验,让撞错/找不到时报错而不是悄悄给错值。
- **指标口径变动必须打 apolo 真数据验证,不能只信本地少量镜像**(用户明确要求,延续 [[2026-07-24]] 的超集环境验证教训)。本地镜像数据少、容易"看起来对"。
- **知识库要防自我投喂**:bot 生成的答案沉淀回自己检索的库,会把错误固化且反复自我强化、看不出来源。用标记排除自己 + prompt 规则(无答复的问题不写"结论:无")规避。设计任何"AI 产出再进 AI 输入"的闭环都要先想污染路径。
- **测试桩会掩盖真实缺陷**:MR!134 的 resolve_agent_by_id 未定义导致 13 个测试失败,但 e2e 用计数桩替换了真实调用、绕过了它,最后一个提交还把这批失败当既有基线接受。review 别只看"pass/fail 数一致",要看桩有没有把真实缺陷挡在外面。
- **交易系统的观测工具本身会失灵,且改观测可主动、改交易参数需确认**:做 T 自检连续两天漏报(信号阻塞当正常弹窗、程序崩溃没抓到),说明自我观测工具也是代码、也有盲区。边界:检测/报告/看门狗这类观测运维改动可主动提,动实盘参数(档距/阈值/触发)必须人确认(延续 [[2026-07-24]])。
- **给套牢的用户做投资建议要敢 push back,不顺从**:用户连续问"红利一周 5%""抄底博反弹""3800 支撑",这些是回本焦虑驱动的不切实际预期。对用户资金负责的做法是用数据讲清"防御品种给不了短期高收益""支撑位不可靠""追高与抄底逻辑冲突",而不是顺着找标的。同时守住边界:不做方向预测、不给具体买卖指令(不是投顾)、给决策框架和风险。
- **远程机器地址必须用户当次明确给出,不能拿仓库注释/memory/历史笔记当依据**(csrs dev 排障 skill 明确写死这条纪律,延续 [[2026-07-27]])。"基于证据默认 X 台、你不回复就执行"也不行。
