## 1. 今天获得的知识与技能

- **本体的两平面分离设计（治理平面 vs 产品运行时平面）**：这是 cuiyang 让我读的一份设计文档（`umu/ontology_governance/docs/superpowers/specs/2026-07-22-post-extraction-ontology-reasoning-engine-design.md`）的核心。治理平面负责推理规则的编写、编译、发布，规则是受治理的资产（声明式 DSL，引用 TBox/RBox，限三跳、禁递归，编译成确定性中间表示 IR）；产品运行时平面在自己的事实库（ABox）上执行规则，产出可解释、可撤回、绑定版本的派生事实。几条关键铁律：LLM 只能产生假设（hypothesis），权威派生事实只能来自确定性规则（文档里编号 G-07）；查询（Query）只读事实不创造事实，规则（Rule）才创造事实；事实必须分级（reference 参考事实 / asserted 断言事实 / derived 派生事实 / llm_hypothesis 大模型假设）。
- **"取数题"与"判断题"的分野**：这是理解 Prove 下一步该往哪走的关键。目前 Prove 的问答全是取数题（多少人参与、完成率多少），查询层就够。一旦进入判断题（这门课健康吗、为什么完成率低、哪些学员有流失风险），结论不应让 LLM 临时发挥，而应由受治理的确定性规则派生（例如"完成率<0.1 且参与>100 就判定为 CourseRisk 课程风险"），LLM 只负责解释规则结论。这正是 Prove"验证二（归因）"要面对的问题。
- **本体感知路由（用本体图结构做意图识别）**：把课程问答的目录驱动路由从"纯词表匹配"升级为"先在本体上做概念定位、再选指标"。给大模型的路由提示词里同时放三样东西——TBox 概念清单（id + 描述）、RBox 关系清单（id + 定义域 domain + 值域 range）、指标目录（每个指标一句短的路由区分句 hint）。大模型先推理"问题涉及哪些概念、经什么关系"（概念定位），再从挂载在这些概念上的指标里选。这是第一次真正用到本体的图结构而不只是词表。
- **确定性取数 + 充分性探针**：确定性取数指大模型选中指标后，取数不经过大模型，直接执行指标注册表里登记好的 SQL 模板（填入校验过的参数），大模型改不了一个字。充分性探针解决"0 的歧义"——某课程"必修完成人数=0"有两种含义：真没人完成，或这门课根本没设必修小节。探针是为该指标声明的第二条小 SQL（查"这门课有没有必修小节"这个完备性事实），返回 0 时链路产出机器可读声明，强制大模型在回答里如实说明，而不是把 0 当成"没人完成"。
- **类与实例的边界在本体里怎么摆**：TBox 里只有一个概念 `MetricDefinition`（指标定义这个"类"）；16 个课程指标是这个类的实例，登记在指标注册表（属于 ABox/实例层）。"指标是本体一等公民"指的是指标作为实例有自己的关系（`attachedTo` 挂概念、`answersCQ` 挂业务问题），不是每个指标升格成一个概念——否则概念层会被几百个指标淹没。
- **口径选择半确定化**：与其靠自然语言 caveats 让大模型"悟"出默认口径，不如加结构化字段：`caliber_group`（哪些指标是同名多口径兄弟）、`default_for_qa`（问答默认选谁）、`select_when`（什么触发词才切非默认口径）。触发词匹配可以完全代码化（问题含"总体概览"就确定性切 by_completion），把口径这一步从自由裁量降成受约束选择。

## 4. 经验与教训

- **daily-memory 被打断就会漏跑，且不会自动补**：7/21 和 7/22 两晚都是——loop 到点触发、抽完 digest、读完内容，但在写文件之前 cuiyang 发了新消息打断，文件没落盘。教训是 skill 执行到"读完 digest"这步还没产出任何持久结果，一旦中断就等于没跑。改进方向：抽完 digest 后尽快先写文件再做别的，或把"是否已写当天文件"作为 loop 每次唤醒时的检查项。补跑很简单：`/ycui-daily-memory 2026-07-22` 带日期参数即可。
- **优化前先建可度量基线**：面对"提升路由准确率"这种请求，cuiyang 认可的做法是先写稳定性测量脚本拿基线，再改，再用同一套测量证明改善了多少。没有基线的优化（如两段式路由）即使做了也无法证明价值，应缓做。这符合 Prove 的评测三条线纪律。
- **把易错的自由裁量降级成受约束选择**：路由里最容易错的是"选哪个口径"。与其让大模型从一堆治理引用噪声里"悟"，不如用代码做确定性兜底（触发词命中就强制、没命中就回落默认），大模型只在触发词没覆盖的模糊问法上判断。这是"计算类代码不静默降级、该确定的就确定下来"原则在 LLM 系统里的应用。
- **如实说明能力边界，不夸大"推理"**：今天多次主动向 cuiyang 说清"哪些是真推理、哪些还不是"——当前本体在路由中的作用是概念定位 + 挂载约束 + 域一致性校验三层，更深的多跳图遍历还没有用武之地（只有一门课程域评测集）；跨域推理当前止于路由层，数据层的课程级知识点过滤因绑定表为空还做不了。这种边界声明是 cuiyang 看重的。
- **读长设计文档后要给出"采纳/不采纳/为什么"的判断，而不是全盘照搬**：对那份 1694 行推理引擎设计，正确做法是逐项对照现状，明确哪些已天然对齐、哪些低成本采纳、哪些是现阶段的过度设计（整套 Rule DSL/IR/Kernel），并说清何时再接。
