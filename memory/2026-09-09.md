### 医药销售的知识/技能分类：业内没有现成答案，只能拼

这是今天最有智力含量的一段调研（用了 Sciverse 学术检索 + 公开资料）。**结论：业内没有一套现成的「医药销售知识点/SKILL」分类**，能找到的分五类、各答一个问题：

| 来源类型 | 代表 | 回答什么 |
|---|---|---|
| 职业分类体系 | O*NET 41-4011、ESCO「medical sales representative」、日本职业分类大典 2-06-07-07 | 岗位要哪些知识/技能/任务 |
| 行业考试与培养规范 | ABPI 考试、RDPAC MRC 五篇、团体标准 T/YYHG 0001—2019 | 推广人员必须掌握的知识边界 |
| 胜任力模型 | 冰山模型下的 KSA、中国医药代表胜任力论文、Medical Affairs 的 MAPS/MAPA | 企业内怎么给人分域分级 |
| 销售学术研究 | Rentz 2002 三维技能量表、Weitz 与 Sujan 的销售知识结构、adaptive selling、B2B 六维 | 哪些技能真和绩效相关 |
| 学习科学的知识类型学 | 布鲁姆修订版、陈述/程序/条件三分、de Jong 四类、Koedinger **KLI**、**Merrill CDT** | 一个知识点是哪种类型 |

**四个直接可用的发现**：

1. **知识与技能怎么分，ESCO 的操作定义最清楚**：知识条目是**学科名**（药理、药物警戒法规），技能条目是**「动词 + 对象」**（advise on、negotiate）。销售量表里叫 technical skill 的「产品知识」，按这个口径**实际是知识**，要归知识侧。
2. **行业标准只覆盖学科级知识**——RDPAC MRC 五篇是医学基础、药学基础、药事管理、市场概况、行为准则；ABPI 考人体系统、疾病治疗、医疗体系、行业守则。**没有一个考具体产品的数据。** 所以 K2 产品、K3 证据、K4 竞品必然是**企业私有层**，K1 疾病、K5 医疗体系、K7 法规可以**跨企业共享**。这条和 Roleplay 关键信息几乎全落在产品与证据上的观察互相印证。
3. **「域」和「知识/技能」是正交的**。MAPS 与 MAPA 都把「科学知识」和「客户沟通」并列为域，不先分知识技能再分域。
4. **知识点类型有严格判据**：**KLI 框架**用「应用条件恒定还是可变、响应恒定还是可变、能否言语化」区分 fact / concept / rule / principle / skill；**Merrill CDT** 的四类内容 fact / concept / procedure / principle **正好对上 AGL 落库的四值**（information / concept / procedure / decision），可以直接承接 spec 里的 `knowledge_kind`，不另造词表。

**最终确定的分类是三条正交轴**：轴 A 内容域（K1–K8 知识域 + S1–S10 技能域）、轴 B 节点性质（知识 vs 技能，按 ESCO 口径）、轴 C 知识点类型（Merrill 四类，KLI 作判据）。**态度和特质不进分类——它们不可由对练 trace 观测。**

### 三条轴怎么用：拿百特「爱透佳」的真实数据走一遍

cuiyang 说「你上面说的太抽象了，具体给我解释」，于是用 CN 企业 203（百特，腹膜透析液爱透佳）一个真实场景逐条演示。这段值得完整记下来，因为它是整套分类法的操作范例：

**原材料**（作者在场景里配的三种东西）：
- **一条关键信息**：「代谢获益数据：每日 1 袋爱透佳可减少糖吸收 42g。回顾性研究显示其可使新发糖尿病风险降低 34%，并显著改善总胆固醇与甘油三酯水平。」带 3 个语义点。
- **一条异议**：客户说「新患者没什么容量问题，也没什么血糖问题，直接用艾考，有这个必要吗？」作者写了建议回应，拆成 3 个语义点。
- **几条评分要点**：「能够传达所有关键信息的语义点」「主动询问确认对方是否理解」「介绍病例前先征得同意」。

**轴 B 先分知识还是技能**：
- 「每日 1 袋减少糖吸收 42g」是名词性内容、脱离对练也能背出来 → **知识**
- 「主动询问确认对方是否理解」是一个动作、只有在对话里才看得到 → **技能**
- 「能够传达所有关键信息的语义点」**两边都不是**——它是**评分规则**，说的是「拿知识去做什么算过关」，**不进节点库**
- 异议那句「有这个必要吗？」**也不是节点**——它是客户的话、是**考题**；要学的东西在**回应**里

**轴 A 定内容域**：爱透佳那 3 个语义点都是 K3 临床证据；异议回应里「葡萄糖吸收导致糖负荷增加、引发肥胖和血脂异常」是 K1 疾病机制。技能侧「主动确认理解」是 S4 探索倾听，「介绍病例前征得同意」是 S6 疑问处理。**Roleplay 一次对练只覆盖 S4、S5、S6 三个技能域**——区域规划、CRM 记录这些域，Roleplay 数据里根本没有。

**轴 C 判知识类型**：只对知识节点用，按 KLI 的「条件固定不固定、答案固定不固定」判。

**`d_capability.capability_name` 医药版三站全空、通用版全有。** 原因已定位：PHP 页面显示的名字**不从库里取**——`ChatbotInfo::getManasimCapabilities` 读的是 `capability_key`，再用 PHP 自己的 `\i18n\Translate::_($key)` 翻成中文（`ChatbotInfo.php:103`）。所以名字有两份正本（Go 的 `i18n.yaml` 和 PHP 的 i18n 表），**库里那一列没有读者**。

### chatbot_reporting：Roleplay/ManaSim 的 Flink 实时数仓

`MySQL Binlog → Flink CDC → Paimon ODS → dwd-job → Paimon DWD → dim-job / dws-job → StarRocks`。CO 站同步 16 张 ucs 表。

关键在 `dwd-job` 的 **Path 4**：一个 UDTF `AbilityScoreExplodeFn` 把 `evaluation_result` JSON 拆开——`scores{}` 每个子能力一行、`stage_scores{}` 每个阶段一行——再 lookup `setting_capabilities` 拿 id，写进 `dwd_practice_record_detail.section_details` 数组，最后 UNNEST 成 `dws_practice_section_score`：

| 行 | `section_id` | `section_type` |
|---|---|---|
| 子能力分 | 子能力 id | 父能力 id（>0） |
| 阶段分 | 父能力 id | 0 |
| Roleplay 环节分 | 环节 id | 1-4 |

**能力分和 Roleplay 的环节分共用一张表一组列**，靠 `section_type` 取值区分层、`section_id` 在不同 `chatbot_type` 下指向不同实体。统一模型接进来时**要先按 `chatbot_type` 分流**。

### Roleplay 的实体层级（今天问清的）

```
chatbot（一个训练项目，level 1）
 └─ 大关卡（level 2，目录节点）
     └─ 小关卡（level 3，目录节点）
         └─ theme（挂在小关卡下的 directory_resource，才是有内容的场景）
             ├─ 客户角色 robot_id、难度 0教学/1简单/2中等/3困难、语言、对话前提示
             ├─ 剧本 scenario_id
             ├─ 环节 × N → 评分要点、关键信息、异议
             └─ 练习次数限制
```

- **theme 不是一次练习，是一个可反复练习的场景**，相当于「一道题」。一次练习是 `dialogue_chat_room`（数仓叫 `practice_id`），外键指向 `theme_id`。JP 站 Roleplay 965 个场景对应 42.7 万次练习、1.7 万名学员，**平均一个场景被练 442 次**。
- **一次练习只练一个 theme。** 两个 theme 是两个独立场景，互不共享状态，「衔接」只有顺序和解锁（chatbot 上的 `unlock_rule`：2 = 不限制、1 = 按顺序闯关）。「第二个场景的客户记得第一个场景说过什么」这种机制**不存在**。
- 大小关卡只是分组和解锁顺序的壳，JP 1229 个场景里 1201 个有大关卡、1180 个有小关卡，但很多客户不真正用（ルンドベック 每个 chatbot 只 1 个 theme，关卡全是默认名）。JP 平均一个 chatbot 两个 theme。

### 评分要点与关键信息：两个维度，做笛卡尔积不是配对

这条 cuiyang 追问了两轮才讲清（第一次我答偏了，他说「不对啊，我说的是 evaluation_standard 和关键信息的对应关系！」）。

`evaluation_standard` 挂在**环节**上、是这个环节的评分维度列表；关键信息是这个环节的**内容**列表。两个列表**相互独立**。评估请求里是两个并列字段 `eval_standards` 和 `key_messages_with_semantic_points`，**没有任何字段说「这条信息对应哪个要点」**。

| 模式 | 返回结构 | 10 条信息 × 3 个要点得到 |
|---|---|---|
| **整体评估** `evaluate_type=1`（JP 99%、CN 91% 的信息传递环节） | `point_scores[]`，每要点一分 | **3 个分**。覆盖类要点的分 = 讲到的语义点数 ÷ 总语义点数 × 100（prompt 里写死了这个公式）；动作类要点看学员有没有做，与信息条数无关 |
| **逐条评估** `evaluate_type=2` | `evaluations[]`，每条信息一项、项内再有 `point_scores[]` | **30 个分**，行权重 = 信息的 Weight、列权重 = 要点的 weight，两层加权 |

**要点怎么写由作者自己定，系统不校验要点和信息之间的关系。** 语义点判定是**独立跑的一次调用**，逐条输出 `is_mentioned` 和原话证据，只产生打勾**不产生分数**。

### 测评的模型与规模（JP 站）

方案 → 维度（名字、区间、权重、阈值、推荐课程）→ 题目 → 选项加分规则。答一遍题，选项加分按维度累加成维度分，截到区间，再算总分和加权均分；低于阈值推学习任务。

⚠**cuiyang 给的 Go 仓库 `umu-supporting-task` 不是测评本体**——它是通用任务分配引擎，只管「谁测谁、几轮、定时、部门负责人规则」，同时服务测评和带教，里面**没有任何维度和分数**，只在分配记录里存一个 PHP 记录 id。测评本体全在 PHP 主仓库 `backend/service/assessment/`，库是 `umu_assessment_jp`。

规模：方案/企业 4,532 / 180（2021-04 起活跃）；维度定义行 50,825 / 去重名字 6,801；已提交记录 236,099（导入 31,134、自评占 72%）；维度分行 178 万 / 被测者 11.9 万；合并方案 121 / 维度映射 2,124 条；能力卡 998。

### 统一模型 spec 已写定的设计判断（v0.6）

- `owner` 字段：平台内置 / 企业自定义 / AI 生成。**没有它，29 项平台能力和某企业 1,217 项自定义能力会混成一类。**
- `knowledge_kind`：Merrill 四类，**唯一 100% 覆盖、由设计者判定、直接驱动教法的类型来源**（来自 AGL）。`unit_type` 由它折叠，但**折叠不可逆**，所以原值单独保留。
- `kp_nature`（结构性/装饰性）放在「课程 × 知识单元」**关系表**上，不放实体上——同一个案例换一门课角色会变。
- **掌握度按测量事件存**：同一学员同一能力每练一次一行，「当前水平」是聚合口径算出来的、聚合口径单独配置。**这条反过来修正了前三个产品的建模**——学习平台的正确率其实也是每天一次测量。
- **掌握度不做跨量表换算**，`learner_unit_state` 带 `scale_id`。已有量表：`manasim_med_5level_pct`（五级锚、百分制存）、`assessment_dimension_range`（逐维度连续区间）。**通用版的量表要能挂到单个 `unit_id` 上**（21 个子能力各有自己的五级描述）。
- `course_knowledge_unit.weight`：ManaSim 的场景 × 子能力有权重，LL 没有。
- 事实表需要 `rater_id / rater_role`（测评的自评 vs 上级评是两条事实）。
- 新关系 `remediated_by`（维度低于阈值 → 推荐课程），方向与 `course_knowledge_unit` 相反。
- **`same_as` 有了第一个现成来源**：测评的合并方案映射表是人工建立的跨方案维度映射、自带刻度换算。此前所有产品都没有。
- 需要一个「**被引用次数**」字段——通用版有两个子能力（「用词准确、表达简洁」「小结已讨论的要点」）在 30 个场景里**一次都没绑**，字典里有、事实里没有。

### 几个数值口径（容易搞错的）

- **ManaSim 学员看板**：场景内多次练习取**最高** → 跨场景取**平均** → 父能力取子能力**平均（不加权）**。**练习内加权、跨练习不加权，两处不对称。**
- **每个场景恰好 5 个子能力、权重和恰好 100**（通用版）。JP 280 / CN 1,031 个场景无一例外，医药版 42 个也是。**我之前在 spec 里写「不要求和为 100」是错的，已改。**
- **总分公式**：`round(Σ 分 × weight ÷ Σ weight)`，但代码里 **score == 0 的子能力跳过分子、weight 仍在分母**（`overall_analysis_service.go:1284-1290`）。效果等于「这项拿 0 分」，**不是**「这项不计」。
- **同一个子能力在 CN 和 JP 的 key 不一样**（通用版）：6 个词干不同（CN `listening_accurate_paraphrase` = JP `listening_paraphrasing_co`），其余 15 个只差 `_co` 后缀。两站 `capability_id` 相同只是 `clean_data` 按字母序分配的**巧合，不能当跨站主键**。医药版没这个问题（29 个 key 两站全同）。
- **知识点 `exam_detail`（JP StarRocks）**：559 万行，近三天每分区约 186 万行、16 家企业。跑批直写的只有企业 5（239,165 行/日，id 全部哈希），DataX 搬运的其余 15 家（企业 2614 一家 145 万，id 全部自增）。**两种 id 没在同一分区撞过。** DataX 每天搬的 162 万行，读侧对这 15 家走 MySQL、**StarRocks 里没人读**，还要被两个物化视图各刷一遍。物化视图 06:00/07:00 JST 刷新，集群时区 `Asia/Tokyo` 和 PHP 一致，**JP 没有 COM 那个时区错配**。

第一次：我看到 COM 站 `dws_practice_summary` 里 `chatbot_type=6` 只有 42 条、明细几乎为空，就下结论「数仓里没有医药版的能力分」，写进了报告第 6 条和第 7 条（还当成两个不同的问题）。cuiyang 追问「这个和 #6 是同一个问题么」，我去读 `chatbot_reporting` 的 `dwd-job`，发现**数仓设计上早就覆盖了**——那 42 条是测试数据。**两条一起撤回。** 后来查 JP 拿到正面证据：166 次练习有明细、1,176 条子能力行 + 664 条阶段行。
