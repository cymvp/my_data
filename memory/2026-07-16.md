## 1. 今天获得的知识与技能

- **本体驱动问答的两种范式，cuiyang 亲自澄清了区别**。所谓"本体"（ontology），是把业务概念、概念之间的关系、每个概念挂哪些指标和维度、指标背后是哪条 SQL，全部预先定义成一张"业务地图"。基于这张地图做问答有两条路线：一条叫"问题驱动"，指为某一类问题预先画好完整解题路径（这个问题关联哪些概念、概念挂哪些指标维度、指标对应哪条 SQL 全部提前定死），用户提问时系统沿图取数、把地图和数据一起交给大模型作答；另一条叫"目录驱动"，指不预先画路径，而是把整张地图（有哪些度量、维度、约束）直接给大模型，让它当场找相关部分、组合出取数计划，再由编译器校验生成 SQL。这个区分对 cuiyang 重要，因为他在做的正是这套语义层系统（在 umu/prove 项目里），需要对内对外讲清楚方案。

- **语义层的核心价值是"统一指标口径"，而口径漂移是真实存在的产品事故而非理论风险**。所谓"口径"指一个指标到底怎么算（分子分母是什么、用哪张表、实时算还是读预聚合）。今天溯源 UMU 课程数据页面时坐实了一个关键事实：同一个页面里，"参与人数""必修完成人数"这类同名指标存在多套并存的算法。这就是为什么要建统一指标层——把每个指标的口径登记进注册中心，同名不同义的必须"异名登记"（起不同的名字分开管理，不能混为一谈）。

- **UMU 课程数据的实时链路与离线链路是两套体系**。"总体概览"标签读的是实时业务库（MySQL 的 `umu`/`task`/`data` 库），算的是当前快照；"进展趋势"标签读的是预聚合的 Doris BI 库（`doris_course_bi`）和 Doris 学习时长库，算的是历史趋势。Doris 是一种列式分析型数据库，这里的 BI 表不是实时业务表，而是由定时任务/worker（`ImportCourseData`）离线聚合写入的。这个"一个即时算、一个吃离线聚合"的区别决定了两个标签的实时性和口径都不同。

- **UAPI 路由规则**：UMU backend 的 UAPI 接口，URL 里的 kebab-case（短横线命名，如 `learning-data-overview`）直接映射到 `PascalCase + Controller.php` 的文件（如 `LearningDataOverviewController.php`），Controller 都在 `uapi/v1/course/` 目录下。这是快速从接口名定位代码的规律。

- **rsync 与 macOS 的两个隐蔽坑**（来自备份脚本排障）：其一，unix socket 文件（`.sock`）会让 rsync 报 `mkstempsock: Invalid argument` 直接中断，尤其当目标路径长度撞上 macOS 104 字符的 socket 路径上限时；其二，GitHub 单文件硬限制是 100MB，超过就拒收 push。解决办法是备份时 `--exclude='*.sock'` 和排除运行时目录，大文件用 `reset --soft` 重做提交剔除后再推。
