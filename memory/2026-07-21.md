## 1. 今天获得的知识与技能

- **凯利公式在仓位判断上的应用**：一只标的即使基本面很强、赔率很好，只要"胜率还没被验证 + 波动极高"，任何仓位管理框架给出的结论都是小仓位——赔率好不改变这一点。这条今天用在中际旭创（300308，光模块龙头）该不该重仓的判断上：它一个月最大回撤 33%、单日能 ±12%，重仓意味着组合单日可亏 6–8%。
- **A 股情绪底的三个确认信号**：真正的情绪冰点反转通常同时出现"跌停潮衰竭 + 市场宽度修复（涨多跌少）+ 两融余额止跌"。7/20 这三个都没满足（跌停仍超 200 只、涨跌 1740:3710、融资余额仍在流出约 1400 亿），所以判断当天不是确认底。这套信号框架可复用于后续择时。
- **本体（ontology）与"本体治理"是两件事**：本体本身就是那几个 YAML 文件（tbox/rbox/metric-registry，声明式、不到一千行）；而 umu/prove 里 `ontology_governance` 那一万两千行代码管的是本体的"变更过程"，不是"实现本体"。类比：YAML 是源代码，治理平台是它的 git + PR 评审 + CI + 发布仓库。本体历史上落不了地，不是建不出来，而是维护不起、很快和业务对不上；治理平台的全部理由就是把本体从"一次性文档"变成"能持续和现实同步的活资产"。
- **Docker 端口映射概念澄清**：`-p 3307:3306` 是"宿主机 3307 转发到容器内 3306"，容器内 MySQL 始终是标准 3306。选非标端口是为避让宿主机可能已占用的 3306。
- **apolo 查询工具的一个硬限制**：服务端对返回行数封顶 5000 行，且会自己追加 `LIMIT`，与手写的 `LIMIT/OFFSET` 分页冲突。绕过办法是按业务主键（如 student_id）分批拉（每批控制在 5000 行内），确定性且不丢行。（apolo 是公司内部的 Web SQL 查数工具，通过 `~/.claude/skills/ycui-apolo-query/apolo_query.py` 调用。）
- **daily-memory / loop 机制**：`/ycui-daily-memory` 必须本地跑（要读本机 `~/.claude/projects` 的会话记录，云端读不到）；`/loop` 是本会话内的动态自调度，靠 ScheduleWakeup 逐次逼近目标时刻，单次 wakeup 上限 3600 秒。
