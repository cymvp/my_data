### Claude Code 的 output style（原稿）

它是一个 markdown 文件，放在 `~/.claude/output-styles/` 下，内容会被塞进系统提示，决定 Claude **怎么说**——语气、结构、详略。它不改变 Claude 知道什么。用 `/config` 里的「output style」项切换。内置三档：Default（简洁工程输出）、Explanatory（额外加解释）、Learning（边做边学、留 `TODO(human)` 让人填）。

**一个会静默出事的坑，今天恰好避开了。** 自定义 output style 默认**替换**掉 Claude Code 内置的软件工程指令（怎么划定改动范围、怎么写注释、怎么验证工作），不是叠加。要在 frontmatter 写 `keep-coding-instructions: true` 才是叠加。cuiyang 的 `jiang-ming-bai.md` 已经带了这一行。**没带的人会发现 Claude 的工程纪律莫名变差，而且不会有任何报错。**

**ASD-STE100 是什么。** 航空维修手册用的受控语言标准，把「说清楚」拆成可逐条检查的条款。今天被搬成中文版六条：一句话只讲一件事；步骤句不超 40 字、背景句不超 50 字；同一个东西全篇只用一个名字；主动语态不省主语；不要长定语套长定语；段落不超 6 句。

**「降智」这个说法的根因和大家想的不一样。** 网上普遍归因于模型能力下降，而查下来至少有很大一部分是输出格式没配——同一个模型换个 output style，可读性差别很大。

### Slack 的翻译 App 为什么翻译不了 bot 的消息（今天最干净的一次根因定位）

现象：`C0BMY7FAULX` 频道装了自动翻译，真人的话能被翻成日文英文，**bot 的回复不能**。

把被翻译过的消息扒出来看结构，答案就清楚了：

```
ts=1786972674  发送者=U08T1SQ24Q5(真人)  edited=True  attachments=2
  正文  : <@bot> カテゴリー作成数のシステム上限について？
  附件 1: *English:* What is the system limit for the number of category creations?
  附件 2: *中文:*   类别制作数量的系统上限是多少？
  edited_by: U08T1SQ24Q5          ← 关键
```

**翻译不是单独发一条消息，而是把译文作为附件追加到原消息上、通过「编辑原消息」实现。** 而 `edited_by` 是**发消息的那个人自己**——说明这个翻译 App 拿的是**用户令牌**，以「这个人自己」的身份去改他自己发的消息。

**Slack 的权限规则在这里卡死了：一条消息只能由它的作者本人编辑。** 翻译 App 借用的是真人的身份，所以能改真人的消息；bot 的消息作者是 bot，那个 App 拿不到 bot 的身份，**编辑不了，只能跳过**。

**举个例子**：公司规定文件只能本人签字修改。翻译助理拿到了每位同事的授权，可以替他们在自己的文件上补一栏译文；但知识库机器人出的文件不归任何同事所有，助理没有它的授权章，只能原样放着。

**顺带排除了一个看起来更可能的解释**：不是「格式不兼容」——我们的回答是纯文本放在 `text` 字段里（没塞进 blocks），内容对任何工具都可读。**问题只在改不了。**

### socket 模式下「确认」是在处理完之后才发的，所以慢就会被重投

加了多语翻译之后出现「同一个问题答两遍，而且第二遍答得更差」。

**根因**：socket 模式下，**Slack 的确认（ack）是在我们的处理函数返回之后才发的**（库代码 `slack_bolt/adapter/socket_mode/async_internals.py`：先 `await app.async_dispatch(req)`，再 `send_async_response`）。**Slack 等这个确认只等 3 秒**，收不到就认定我们没收到，把同一条消息**重投一次**。

加多语之前一次问答几秒、勉强踩线；加了之后要十几秒，于是每次都超时、每次都重投。

**两遍执行各自做了一次检索、各自调了一次生成**，所以两份答案措辞不同——**「第二份更差」正是这个原因：它们是两次独立的抽签，不是同一份内容的两种排版。**

**举个例子**：你给同事发消息问事，他手头活儿多，十几秒没回「收到」。系统以为消息丢了，替你重发一遍，同事就当成两件事各办了一次，给了你两个不完全一样的答复。

### 「重投会带同一个 event_id」这个假定不成立

第一版修法用 `event_id` 去重，实测**没挡住**：日志里两条 `mention:` 相差 4.7 秒，**但没有打出「重复投递」那行**——说明两次投递的 `event_id` **不一样**。

**上一版的判断只对了一半**：确认超时这件事是真的（所以才有 4.7 秒后的第二次），但「重投会带同一个编号」这个假定不成立。

**修法改成把去重键换成消息本身的身份**（频道 + 消息时间戳），并把诊断信息打进日志——否则下次还是分不清「去重没触发」和「压根没重投」。

**这条的通用形式**：**去重键要认「这件事本身」，不要认「传递这件事的那次投递」。** 投递可以被重试、被换编号、被走另一条通道，而事情还是同一件。

### 两个必须成对处理的后台任务坑

把活儿丢后台之后有两件事不做就会静默出问题：

- **后台任务必须强引用住**，否则可能被垃圾回收掉，表现就是「@了 bot 没反应」
- **后台任务的异常必须在回调里记成 ERROR**，不然失败是完全静默的，最难查

### 判语言用字符类，不额外调 LLM——但要先剥掉 @提及

有假名就是日文，只有汉字是中文，都没有算英文。

**判定前先剥掉 `<@U0B9MGSJHFT>` 这类标记**——每条提问都带 @bot 前缀，**不剥的话那串字母会把日文问题带偏成英文**。

## 4. 经验与教训

### 原稿的五条

- **「用户说看不懂」是补救的唯一机会，做错这一轮就白费。** 今天一轮里 cuiyang 说了四次看不懂，前三次我的做法是重复原来的措辞再解释一遍，都失败；换一套词从头讲才通。规则第六节因此写死：**原来那套词已经证明不通，不许再用。**
- **「不在关键路径上」「省事」「现成」都不是选择理由，只能作为代价说明。** 今天我用「它的失败方向是安全的」为一处词表判据辩护了三轮，是错的——那句话本身没错，但它推不出「所以该留」。
- **「它在别的条件下会绿」推不出「它红是环境问题」。** 今天把一条测试的红判成服务抖动，而它其实是我引入的回归；判错的原因是没读测试就归因。
- **靠人记得的纪律一定会忘，而且忘掉时不报错。** 今天修了三处这个形状：重录脚本要求「重录后手工把某个例子加回去」、`force_metric_ids` 少清一个条件、录制脚本取了一个已经删掉的字段名。
- **配置类改动要先查「这个开关的默认值是什么」。** `keep-coding-instructions` 默认 false 会静默削弱工程能力，这种坑不看文档发现不了。

### 补充：去重键要认「事情本身」，不要认「投递」

用 `event_id` 去重没挡住重复，因为**两次投递的 event_id 不同**。改成「频道 + 消息时间戳」——那是消息本身的身份。

**通用形式：投递可以被重试、被换编号、被走另一条通道，而事情还是同一件。去重键要落在后者上。**

**而且第一版的失败本来是可见的**——日志里没有「重复投递」那行就说明去重没触发，只是当时没把这个缺失当信号读。**「该打的日志没打出来」本身就是一条信息。**

### 补充：「数据没更新」有两种原因，处理方式相反

8/17 那天新浪 `znb_KOSPI` 的时间戳停在 8/14，第一反应是「数据源坏了」。实际是**韩国那天休市**（光复节补休）。

**判据：先确认那个市场当天是否开市，再判断数据源。** 两者的处理完全相反——源坏了要换源或告警，市场没开则当前没有可用信号、该说「这一路今天不可用」。

### 补充：脚本的单一口径会看不见板块内部的分化

今天早盘脚本按纳指100（−0.17%）判「低开」并打出「KOSPI 与美股方向相反」的告警，**而费半 +1.64%、存储硬件供应链 +4.77%、光通信 +3~8% 全是大涨，KOSPI +3.12% 与费半是同向的**。
