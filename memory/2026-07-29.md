## 1. 今天获得的知识与技能

- **「改本体不改代码」这条原则的真正判据（被用户追问后澄清，我先前误读过）**：prove 的 CLAUDE.md 原文是"加指标、加 CQ、加 join 路径都在 `ontology/` 里登记完成；**发现必须改代码才能加指标时，先说明为什么**"——它要求的是先摆理由讨论，不是绝对禁止。三层理由：① 交付速度（登记一条 YAML 就能上线，vs 改代码要发版，对业务方是两种产品形态）；② **口径可审计性（最要命）**——编译器里的特例是注册表看不见的，一旦口径一半在 YAML、一半藏在 `if metric_id == 'xxx'` 里，注册表就不再是唯一正本；③ 这个仓库付过一次代价（任务列表里就有"24 指标全量迁 DSL、删除 chain.py 六个特例机制"）。**真正的判据是：这个特判是某个指标独有的，还是一类指标共同的能力缺口？独有的先别登记；共有的应扩展 DSL 让所有指标受益——那不叫加特例，叫补能力。**
- **同名指标可能是两条完全不同的链路（"整体完成人数"的实证）**：`course_complete_user_total`（代码字段 `total_complete_user_num`，页面"学习数据总览·总体概览"，读存量表 `data_course_completion`，Merak 近实时、无时间窗）与未登记的"BI 整体完成人数"（代码字段 `complete_course_total_user_num`，页面"进展趋势曲线"，读 Doris 表 `complete_course_total_detail_bi`，配额触发 T+1、按完成时间落日期的区间口径）。用后端代码链路逐层追到 file:line 确认（`DataProgressTrendController.php:56` → `ConstSet.php:33` → `CourseDataProgressTrend.php:204` → `QueryCourseDetailBi.php:71-72` → `CompleteCourseTotalDetailBiDao.php:10-11`）。**由此暴露一个真实缺口：业务问"上周有多少人完成了这门课"，本仓答不了**——存量口径没时间窗，能答的那个没登记；而它不是粒度问题也不是代码特判问题（一张 Doris 表加窗口函数），属于"能登记但还没登记"。
- **"小节完成率"的分子分母粒度不一致（页面口径坑）**：页面算的是 `min(round(小节完成人数 total_finish ÷ **课程总参与人数 total_student** × 100), 100)`——分子小节级、分母**课程级**。小节参与人数确实存在（同一条 SQL 里 `COUNT(*)`、条件 `complete IN (2,1)`），但**没被用作分母**。"小节完成人数 ÷ 小节参与人数"这个看起来天经地义的算式，页面上不存在。
- **A 股 T+1 让换手率成为"干净"的派发指标，美股 T+0 不行（用户指出，纠正了我的对比方法）**：A 股今天买的股票今天不能卖，所以某日成交量必然全部来自开盘前已可卖的存量，**换手率是真实的单向派发比例**。美股 T+0 下同一批筹码可日内反复倒手，成交量被日内交易注水，**换手率高估实际派发比例**。所以拿 SpaceX 首日 78% 换手（5 亿股 / 6.37 亿股发行）去对比长鑫首日 66.4%（29.9 亿股 / 45.03 亿流通），**不是同一口径，结论不成立**。附带一条：**T+1 机械性压制崩盘速度**（今天买的人今天不能恐慌卖），每天卖压上限被"昨日及以前持有量"锁死，这是 A 股相对美股的结构差异。

## 4. 经验与教训

- **不要替用户把结论下了——引用他自己定的规则时更要读准原文**：我说"硬登记 `total_finish` 就违反『改本体不改代码』"，但原文留了口子（"必须改代码时，先说明为什么"）。规则要求摆理由讨论，我却当禁令否决了一个选项。**引用用户的规则/文档作为论据前先读准原文，不要凭印象加强它的约束力。**
- **同一个坑第三次出现就该改机制，不是再修一次**：满分写默认值 100 的坑今天在 demo 层是本会话第三次遇到。这类"允许写默认值的关键参数"迟早被写错，而且**每个数字看着都真、对账查不出来**。判据：同类错误出现第三次，说明是机制允许它发生，该去掉那个允许（强制从 `exam_full_mark` 查、不给默认值）。
- **归因必须验证到代码，我今天犯了三天的错**：我连续三天把做 T 日志里那段 300 秒空白报成"出信号阻塞主循环、osascript 卡死 runloop"的 P0 bug。**读代码后真相是 `_trade_status` 第一行 `if code in self.t_sig: return` 顺带跳过了日志——引擎一直在正常跑，那是日志空白不是引擎卡死。** 而自检脚本连续三天误报，根源就是它把日志空白当卡死。**教训同 prove 那次"你验证过么"：没读到代码/没做受控实验，就不该把归因当结论输出，更不该连续三天基于它报警。**
- **对比两个市场的指标前，先确认它们测的是同一个东西（用户指出）**：我拿 SpaceX 首日 78% 换手对比长鑫 66.4%，得出"SpaceX 也已出清获利盘却仍跌 50%，所以出清不是保护"。**但美股 T+0 允许日内反复倒手，换手率被注水；A 股 T+1 下换手率才是干净的单向派发量。两个数不可比，结论不成立。** 更一般的原则：跨市场/跨制度对比数据前，先问"这个指标在两边的口径一样吗"。
- **不要从几个例子推广出"普遍"（今天犯了两次）**：① 我说"硬科技 A+H 普遍倒挂"，实际 24 家里只有 2 家溢价（8%）；② 我说"小流通盘砸不动"是保护，但 SpaceX 自由流通仅约 4.9%（比长鑫 6.73% 更小）却跌 50%——**小流通盘是双向波动放大器，不是单向保护**。**举几个例子能证明"存在"，不能证明"普遍"；说"普遍"要有基础概率（分母）。**
- **抗跌/逆势上涨不是安全的证据**：长鑫在全球存储崩盘中逆势涨，是流通盘 6.73%、新股情绪、国产叙事 + **长鑫上市本身就是美股存储股跌入熊市的导火索**（市场把"中国存储竞争到来"同时定价到两边）四个机制共同作用，不是基本面更好——它 PB 约 31 倍是三星近 10 倍。**在下跌市里"能不能跌"是按流动性和定价体系分的，不是按质量分的。**
- **给有回本焦虑的用户做投资分析要敢反复 push back 且守住边界**：用户连续问"红利 ETF 一周能不能赚 5%""3800 有支撑是不是不会跌""长鑫抗跌是不是更好""长鑫会不会像 SpaceX 一样跌"。有效做法是用数据讲清矛盾（防御品种的低波动是双向的、给不了 5% 上行；支撑位是护盘护出来的、事件面前会破；抗跌是结构性的），而不是顺着找标的。同时守住：不做方向预测、不给买卖指令（不是投顾）、只给决策框架和风险量化。**并把这条边界写进了 skill（"不出可以买入的清单"）。**
- **时段与模式不匹配时要明说、不机械执行**：cron 触发的"早盘模式"在 11:32 才跑，此刻开盘方向预测已无意义、重复发 Slack 是过时内容——正确做法是说明情况、改按盘中模式给有用分析。尾盘建议在 11:33 给要标注"数据是上午收盘、下午若剧变需复核"。**skill 的"以 prompt 为准"不等于无视现实时点。**
- **自己写进定时任务的提示词也可能过期，要敢于当场纠正**：18:42 那个暗盘检查的 prompt 是我下午写的，里面让我带上"硬科技 A+H 普遍倒挂"的背景——**而我在那之后已经查证推翻了它**。照自己的旧指令执行就会传播一个已知错误。**执行任何预设指令（包括自己写的）前，先检查它的前提是否仍然成立。**
- **写进 skill/脚本的命令必须先实测**：给 skill 加多日板块趋势能力时，先测了东方财富接口（不可达）、腾讯接口（可用）、18 个代表股代码（逐个验证有效），才写脚本。**没验证过的接口和代码不写进 skill**——错代码会静默返回空，比报错更难查。
- **搜不到就说搜不到，不用不可信的数字**：查暗盘价格时搜到一个"暗盘反弹 13.2%、折价 77%"的结果，但该来源把发行价写成 1010（实际 980）、且两个数字自相矛盾，**明确拒绝采用并向用户说明为什么不采用**。
- **给 sync 类脚本加超时保护**：my_data 的 `git pull` 曾报 "correct access rights"（听起来像权限问题）并挂到 2 分钟超时，实际是瞬时网络卡顿（判据：同 key 同账号的另一个仓刚 push 成功）。加 `GIT_SSH_COMMAND="ssh -o BatchMode=yes -o ConnectTimeout=15"` 和 `GIT_TERMINAL_PROMPT=0` 后执行干净——**让网络不通快速失败而不是静默挂住**。
- **后台 agent 会空转反复唤醒，要主动终止**：ai-berkshire 那个长鑫业务 agent 成果早已并入报告，却反复发空完成通知等待子任务。**确认成果已交付后直接 TaskStop，不损失内容**。
