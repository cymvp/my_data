## 1. 今天获得的知识与技能

### 一个新的缺陷类型：系统能力齐全，但模型不敢用

**场景**：用户问「**测评小节 6589717 的课程完成率是多少？**」——他给的是一个测评小节的 ID，问的却是**整门课**的完成率。这两件事不是一回事：测评小节 6589717 属于课程 552160，他要的是课程 552160 的完成率。

**跑三轮，三轮都拒答。** 而模型的推理链条其实**完全正确**：

> 问题点名「测评小节 6589717」，在本体中对应 Exam，经 `examHostedBySession` 关联 Session、再经 `examSessionOfCourse` 关联 Course；但问的是「课程完成率」，目录中对应指标 `course_complete_rate_total` 只能用 `course_id` 过滤，**当前给定的是 exam_id**，且「缺参数时可由什么补上」里注明 **`course_id` 仅能由 `exam_id` 补上（不包含由题干给的测评小节 ID / ExamSession 概念补课）**，因此无法结构化定位到具体 `course_id`

**读这段话要注意它前后两句自相矛盾**：前一句说「当前给定的是 exam_id」，后一句说「题干给的那个测评小节 ID 不算 exam_id」。**同一段话里，同一个数字，一会儿是一会儿不是。**

而系统递给它的载荷里，这两件事都写得明明白白：

```
问句点名的对象:      {"exam_id": 6589717}
缺参数时可由什么补上: {"可用": {"course_id": "已可由 exam_id 经检索 course_of_exam 补上"}}
```

**两段它都读到了（它在理由里逐段引用了），还是拒答。**

### 为什么原来排好的修法对不上这个病

之前计划「给目录路由接一道可达性守卫」。那道守卫管的是**「选中的指标够不够得着问句点名的那个对象」**——比如问某个小节的情况却选了一条只收课程 ID 的指标，那就是够不着，该拦。

**但现在这个病不是够不着：指标够得着，参数也补得出，系统能力齐全，是模型不敢用。守卫接上去也永远不会红。**

试过一次修法：原来载荷给的是两段独立的东西——一段说「你手上有 exam_id」，另一段是整份注册表推出来的通用表说「course_id 可由 exam_id 解析」，**要用上它模型得自己把两段拼起来**。把这一步拼接搬进代码，直接给它算好的结果。

**没有改善**，c47 从 1/3 变 0/3（n=3，不当结论）。**改动保留了**（载荷更干净、少一步推理、删掉一份被取代的旧函数，**780 单测全绿**），**但在提交信息和 KI-14 里都写明它不是这条缺陷的修法**——这一点很重要，否则下一个人会以为这条缺陷已经修过了。

**举个例子**：给人两张纸条，一张写「你手上的是 A 号钥匙」，一张写「A 号钥匙开 3 号门」。他念完两张，说「可是我不确定我手上这把是不是 A 号」。我做的事是把两张并成一张写「你手上这把能开 3 号门」——**他还是那句话。**

**候选：在路由之前就把能补的 ID 真的查出来**，让模型看到 `{exam_id: 6589717, course_id: 552160}`——**一个具体的课程号摆在那里，没有任何要推的东西。**

### 「上下文撑爆」这个说法要纠正：撑爆的是输出，不是输入

崔扬要求查十问第 8 句失败（`LLMError`）的原因，用词是「上下文撑爆」。

**报错说的其实是输出被截断，不是输入超长**，判据是 `finish_reason == "length"`。这两件事的修法完全不同——输入超长要裁剪上下文，输出被截断要提高上限或让回答更短。

**而实测更意外：正常跑这一句只用 321 个输出 token，上限是 16384——差 50 倍。**

**所以那次失败不是「要列的对象太多写不完」**（这是现有的解释）。真实原因还没定位，但至少可以排除掉那个解释。

### 语义层框架调研：一个「直接用」都没有

用 workflow 跑了 11 个 agent、约 50 万 token、10 分半，报告落在 `docs/02-ontology/research/2026-08-14-semantic-layer-frameworks-scan.md`，已推送。

**这轮调研最值得说的结构性结论：凡是够得上「直接用」的，都因为某个前提不满足被降成了「有条件借鉴」。**

最典型的是 **Instructor**（用 Pydantic 给 LLM 输出定 schema，非法就报错）。它形态上很契合我们的 fail-fast，**但它自己带的两个前提不满足就会反噬我们的纪律**：

1. **校验用的枚举值必须在运行期从指标注册表这唯一正本动态生成**——手抄一份指标清单进 Pydantic 模型，就是制造「一份知识两个正本」，注册表加了指标那边会漂移
2. **必须显式配成「重试用尽即抛异常」**，禁止它退化成返回「最像的那一个」——那就是静默降级

### Semantica 不是同类东西

它是一个 **graph-native 的知识图谱平台**——RDF 三元组库加标签属性图，自带 Datalog / SPARQL / Rete 推理引擎，做的事是「从多源数据构建知识图谱 + 事实溯源」。

**它跟我们唯一的字面重合是都提「provenance（来源可追溯）」，但那是两种不同的溯源**：

| | 追什么 | 属于哪一环 |
|---|---|---|
| **Semantica** | 这条三元组事实是从哪个数据源抽出来的 | 数据**入库时**的血缘登记 |
| **我们的 gates** | 这段自然语言回答里的这个数字，能不能重放核对回证据表的某一行 | 回答**生成之后**的出口对账 |

**前者管数据怎么进来，后者管话怎么出去，不是同一个问题。**

**仓库信息是自己拉 GitHub API 核实的，没有转述 agent 的话**：`semantica-agi/semantica`，7957 star、815 fork、47 watcher、76 个 open issue，创建于 2025-06-25，最近提交 2026-08-15，Python，MIT。**项目真实且在活跃开发。**

**但有两个数反常，如实记下**：watcher 只占 star 的 **0.6%**（正常项目大致 2%–5%），fork 占 star 的 10% 也偏高；周边还挂着几个 0–1 star、名字像一次性小号的 mirror 仓库。**这不构成造假的证据，只是两个反常的数——判断留给崔扬。**

### 三点值得借鉴的设计

| 设计 | 它怎么做 | 我们现在怎么做 | 换过去得到什么 |
|---|---|---|---|
| **Cube 的 join 解析** | 关系带方向；每表标 `primary_key` 用来判断有没有把行数翻倍；两个概念之间有多条路径时显式指定走哪条 | 关系有 domain/range，但防「行数翻倍」和多路径消歧**隐含在编译器实现里** | 这两件事从代码里的隐式行为变成**关系声明上的显式字段**，登记期就能看出问题 |
| **MetricFlow 的实体类型学** | 实体分四类（主键/唯一键/外键/自然键）+ 列名映射；join 靠**类型化的实体名**驱动 | 概念用 `identified_by` 声明对外标识，但**标识没有分级** | **直接对上那条教训**——概念绑定不许靠字段名命名约定、拼错会静默失效；类型化让拼错在登记期暴露 |
| **Instructor 的结构化输出** | 路由结果与派生声明建成受校验的对象，指标 id 定成枚举 | Python + YAML 手写校验 | 「非法就报错而不是被悄悄接受」从手写逻辑变成 **schema 内建行为** |

**这张表怎么读**：拿第二行说——**MetricFlow 让两张表能 join，是因为两边挂的是同一个类型化的实体名，而不是因为两边的列名恰好都叫 `student_id`。** 我们现在靠概念绑定做同一件事，但没有区分「这一列是这个概念的主键」还是「这一列指向另一个概念」。借这个分类法，编译器判定主键就从约定变成读声明。

**「行数翻倍」（业界叫 fanout）解释一下**：一对多的 join 会把左表的一行复制成多行，这时再做 sum，数字会被冲大——**这是维度建模里最常见的一类静默错误**。

### 「我不知道你说的是哪个问题」这个反馈的处理方式

崔扬今天对两件事都说了「提供这个问题的上下文，我不知道你说的是哪个问题」。

**有效的解法是从问题本身讲起，而不是从上一轮的结论接着讲**：先给具体的用户问句（「测评小节 6589717 的课程完成率是多少」）、这个问句为什么难（给的是小节 ID、要的是课程数）、系统实际输出了什么（三轮拒答的完整理由原文）、这段理由哪里自相矛盾，最后才是要他拍什么。

**这条和 CLAUDE.md 里「自包含解释」那条规则是同一件事**——「阐述问题的分析结果」是明确的触发条件。

### 一个改动没修好问题时，要在代码和文档里都写明它不是修法

试的那个修法没有改善，但改动本身有价值（载荷更干净、少一步推理、删掉一份被取代的旧函数），所以保留了。**关键是在提交信息和 KI-14 里都写明「它不是这条缺陷的修法」**——否则下一个人看到「这条缺陷下面有个提交」，会以为已经修过。

**这和之前那条「一道会误报的 gate 比没有更坏」是同一类判断：不要让一个动作看起来解决了它没解决的问题。**
