## 4. 经验与教训

- **诚实拒绝比伪造交付更重要**：面对 goal hook 反复施压"目标未满足"，正确做法是给出终局性证据（117 天回测三重验证）+ 明确说"不会用包装过的噪音模型宣称突破"，然后停下等用户指令。用户最终接受了证伪结论并转向可行的替代方案——他要的是真相不是安慰。
- **用户的反馈往往指向覆盖缺口而非系统缺陷**：demo 现场两个"拒答"投诉，根因都是指标登记不全而不是路由错误——"行为正确但登记缺失"要当场闭环（登记→评测→accepted），这本身成了可扩展性的最佳演示素材。
- **公开仓库的密钥红线**：把 webhook 写进配置文件前先查仓库可见性（curl api.github.com/repos/... 看 200/404）。这次在 push 前拦住了，流程应固化为习惯。
- **git add -A 在含垃圾文件的仓库里是冲突制造机**：与另一台机器的 .gitignore 清理撞车。个人仓库要先有 .gitignore 再自动化 add -A。
- **presentation 的"没生效"先查缓存**：demo 页面改动用户看不到，根因是服务端没发 Cache-Control: no-store，浏览器渲染旧页面。给自建 HTTP server 加禁缓存头应成默认。
- **daily-memory skill 的固有弱点**：执行到"读完 digest"仍无持久产出，被打断即全丢（7/21、7/22 连续两晚）。改进方向：抽完 digest 先落盘骨架，或唤醒时先查当天文件是否存在。
- **量价分析要位置优先**：同样的放量下跌，高位=出货风险最高、低位=恐慌衰竭，判断前先问"他们赚了多少"；单日信号不作数，预设止损优于盘中解读。
- **cron 表达式在 zsh 里排查问题时，`for path in ...` 会覆盖 $PATH**（zsh 里 path 数组与 PATH 绑定），循环变量不要叫 path。
