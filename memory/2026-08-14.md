## 1. 今天获得的知识与技能

### csrs 里「图检索一直没结果」的根因：查不到 ≠ 不属于这个 dataset

**csrs 是企业检索问答系统**，检索是四路融合：ES 全文、Milvus 向量（chunks）、table、graph（Neo4j 三元组），另有一路 images（该部署 `fusion_weight_images=0`，所以压根没构造，`path_counts` 里连这个 key 都没有）。

**现象**：召回内容里从来没有 Neo4j 那一路，`path_counts` 里 `graph` 一直是 0 或极小。

**根因在 `csrs/retrievers/fusion_retriever.py:350` 的 `_filter_triplet_edges_by_datasets`**：它是三元组检索之后的一道兜底裁剪，做法是**把边的两个端点 id 一起丢给 Milvus 的 `Entity_name` 集合去查，查得到且 payload 的 `dataset_ids` 命中当前 dataset 才算有效**，两端都有效才保留这条边。

```python
records = vector_engine.client.get(
    collection_name="Entity_name",     # ← 只查这一个集合
    ids=all_ids, output_fields=["payload"])
for record in records:                 # 没返回的 id 根本不进这个循环
    ...
    valid_ids.add(str(record["id"]))
filtered = [e for e in edges
            if str(e.node1.id) in valid_ids and str(e.node2.id) in valid_ids]
```

**问题在于「Milvus 没返回」被等同于「不属于这个 dataset」。** 而三元组里大部分是 `DocumentChunk -contains-> Entity` 这种结构边，**DocumentChunk 的向量存在 `DocumentChunk_text` 集合里，在 `Entity_name` 里天然查不到**——于是这类边被无条件丢光。

**证据链（全部线上实测）**：

| 检查 | 结果 | 说明 |
|---|---|---|
| Neo4j 该 dataset 的节点 | 1986 个 DocumentChunk | 数据没问题 |
| 到 Entity 的 `contains` 边 | 10113 条 | 数据没问题 |
| Milvus `Entity_name` 该租户分区 | 30726 行 | 数据没问题 |
| 按线上同一条路真跑 | `graph_triplet_search edges=10` → `graph_search edges=1` | **10 条砍到 1 条** |
| 逐条拆 10 条边 | 13 个端点，`Entity_name` 只查到 5 个、**8 个查不到** | |
| 查到的那 5 个 | **全部属于本 dataset（5/5）** | **dataset 归属判断本身没错，错在「查不到」** |
| 那 8 个在哪 | `EntityType_name` 里 0 个、**`DocumentChunk_text` 里 8 个** | 全是 DocumentChunk |
| 10 条边的关系类型 | `{'contains': 8, '対象動物': 1, '試験薬': 1}` | **只有 2 条真正的 Entity↔Entity 语义边活下来** |

**为什么「只剩 1 条」就等于看不见**：线上权重是 ES=0.35 / TABLE=0.35 / CHUNKS=0.15 / GRAPH=0.15，RRF 常数 60。graph 唯一那条边排第 0 位，得分 `0.15/(60+0+1) ≈ 0.0025`；而候选池头部的 ES+chunks 双路命中项是 `0.0071`。它在 58 个候选里排中游，之后 LLM rerank 再筛到 8~10 条，基本留不下。

**等于说 graph 的有效 top_k 从 10 塌成了 1~2，剩下的还打不过其他三路。**

### 附带发现一：gateway 路径比 console 更惨，会到 0

同一个过滤里还有一行按 agent 卡：

```python
if agent_id and payload.get("agent_id") and payload["agent_id"] != agent_id:
    continue          # 端点被丢弃 → 整条边被丢弃
```

**Entity 是跨 agent 共享的，但 Milvus payload 上的 `agent_id` 是单值（谁最后写的算谁）。** 采样这个 dataset 的 800 个 Entity，**agent_id 散在 17 个 agent 上，占比最高的才 47.5%**。

**两个入口的差别决定了这一刀砍不砍得到**：

| 入口 | 端点 | agent_id 怎么传 |
|---|---|---|
| **console**（CSRS 管理后台页面提问） | `POST /console/api/datasets/query` | **`agent_id=None`**，注释理由是「dataset_id+tenant 已限定范围」 |
| **gateway**（业务方真实调用） | `POST /gateway/search/retrieve` | `agent_id=agent_id_uuid`，由 `_resolve_owner_dispatch` 从 `user_name`/`agent_name` 解析出真实 UUID |

**所以用 console 测出来的 `graph: 1` 已经是偏乐观的数字**——业务方走 gateway 会多挨一刀，更容易归零。这正好对上 co-prod 日志里 tenant 2713 的 `graph_search edges=0 entries=0`（那是 gateway 路径，`user_name=84`）。

**agent_id 过滤的引入时间**：`P1-10` 是 **2026-05-16 的 commit `cc04ae792`**（master review 的隔离加固）。值得注意的是**同一个 commit 里 `enrich_entity_context` 特意做了老数据兼容**（`c.agent_id = $agent_id OR c.agent_id IS NULL`）——**说明当时已经意识到 agent_id 可能缺失，但只在一处做了兼容。**

### 附带发现二：报错和「没结果」在可观测性上长得一模一样

`_fetch_graph_entries` 的 except 分支是 **`return []`**。所以**graph 内部报错或超时，和「跑通了但没结果」，在 `path_counts` 里都显示为 0**，靠这个指标分不出来。

（这次排查确认不是超时——`asyncio.gather` 没有超时包装；而且这个 dataset 的 ID-filtered 检索要 1.08~1.39s、4200~4500 节点，agl-demo 只有 578 节点、0.10s，量级差别很大但都没触发任何超时。）

### 排查方法上今天学到的四条

**一、「同一个 pod、同一版本，另一个 tenant 正常」是排除代码/部署问题的关键对照。** `tenant_id=agl-demo` 的 graph 是正常的（578 nodes / 782 edges，edges=1~3 有结果），所以问题不在代码也不在部署，是 tenant/dataset 特定的。

**二、`get(ids=...)` 能查到，不代表 `search` 能查到。** Milvus 搜索是**按租户 partition 隔离**的（`Entity_name` 是全局集合，检索只在该租户的 partition 里做），而 `get(ids=...)` 是**跨 partition 按主键取**的。这个差别一度把排查带偏——「我用 get 查到了 30/30 都带目标 dataset_id」这个结论并不能推出「search 也能查到」。

**三、环境变量拿不到不代表没配。** 环境变量由 entrypoint 从 env 文件 source 进 gunicorn 进程，**exec 新起的 shell 拿不到**。要用 CSRS 自己的配置加载来查，实测 `CSRS_FUSION_WEIGHT_GRAPH=0.15`，graph 路是开的。

**四、复现要按 service 的构造方式完整走一遍，不能只调中间函数。** 直接调用 `graph_search` 时是正常的（种子 10 条 → dataset 过滤后剩 2~4 条），和线上的 1 条不一致；最后是在 pod 里用**同一个 owner user + 同一个 dataset** 真跑一次 `cognee_search`（线上走的就是这条），才拿到决定性数据。中间的差异包括 tenant_id 传的是字符串 "2713" 还是 UUID。

### prove：CQ 注册表「留着但换角色」，不是留也不是删

崔扬问「注册表对目录驱动整套方案，还有意义么」。

**结论：作为路由输入它没有意义了，但它本来就不该是路由输入。** 「competency question」这个词的原意就是**用来检验本体够不够用的一组问题**，不是给模型挑的选项。去掉问题驱动之后它回到本义反而更正当。

**穷举消费者**（解析引用位置，不数词频）：

| 消费者 | 去掉问题驱动之后 | 影响答案吗 |
|---|---|---|
| `route_cq` / `classify_intent` | **消失**（就是要删的那条路径） | **是** |
| 本体全景页展示「这条指标回答哪个业务问题」 | 留着 | 不影响 |
| 页面上「34 条 CQ」这个计数 | 留着 | 不影响 |
| 加载期校验 CQ 的生命周期与引用完整性 | 留着 | 不影响 |
| `kp_weakness` 任务契约声明 `cqs: [KM2, KM3, REF1, REF2]` | 留着 | 不影响 |

**除了第一行，没有任何消费者影响答案。** 所以去掉问题驱动之后，这份注册表对系统行为的影响是零。

**三个方案，选了第三个**：

| 方案 | 做什么 | 代价 |
|---|---|---|
| 甲 删掉 | 注册表整个删，连带 34 条验收断言、生命周期记录、任务契约引用 | 「本体够不够用」失去量尺 |
| 乙 留着不动 | 只删路由那条路径 | **它成为零机制消费者的声明** |
| **丙 换角色** | 从「路由输入」改成「覆盖验收清单」：每条 accepted CQ 都要有评测题、且**目录驱动模式**能答对它（REF1/REF2 例外，它们要的就是拒答） | 要写一段评测汇总；34/34 已有题，是接线不是补数据 |

**推荐丙的理由是正确性而不是省事**：它让这份注册表**有一个会响的消费者**。**而乙的代价不是浪费，是它会变成下一个「看起来登记好了、其实没人兑现」的东西**——这个仓库今天修掉的四五个毛病全是这个形状。

**用四个场景讲清甲和丙的区别**（这个解释方法很有效，值得复用）：

- **有人把一条指标挡住了**（今天真发生了——带教触发完成率加了 `queryable: False`）。甲：什么都不会发生，那条业务问题从两条可查询指标降到一条，没有任何地方提到。丙：跑评测时打出「CM7 的可查询指标从 2 条降到 1 条」；降到 0 直接红。
- **同事看 demo 的本体全景页**。甲：每条指标只剩 ID 和技术提示，问「为什么要有这条指标」答不上来。丙：那一行写着「· 回答 CM1/CM6」，指标存在的**业务理由**看得见。
- **业务方提新需求「我想知道哪些学员长期不学」**。甲：这是一句口头需求、没有登记位，而项目硬纪律恰恰是「新增指标必须先说清它回答什么业务问题」——**那个「什么业务问题」以后没地方写**。丙：先登记成 draft CQ，评测立刻告诉你答不出，于是它变成有编号、有验收标准的待开发项。
- **给 Ethan 汇报「本体到底帮了多少」**。甲：只能报评测通过率「47 道题过了 41 道」，他问「业务上够用了吗」答不了。丙：可以报「34 条登记的业务问题里目录驱动能答 32 条，另 2 条是设计上要拒答的」——**这是可被机器核对的覆盖度声明**。

**实测数**：34 条 CQ 评测里全都点名过（34/34）；只有 2 条 CQ 挂的指标全不可查询（REF1/REF2，本来就是拒答类）；**34 条里 18 条已走完 draft 到 accepted 的治理流程，每条有 owner、来源、验收断言**——甲会把这 18 条治理记录一起删掉，而它们和路由是两件事。

### 拒答的正确性不该掩盖拒答的原因

**「拒答是对的」有两种，后果完全不同**：

| | 含义 | 该不该出现在缺口清单里 |
|---|---|---|
| **设计上拒答** | 这个问题本来就不该被回答（缺企业上下文、超范围） | 不该，它是健康行为 |
| **能力缺口** | 问题合理、业务需求成立，**只是我们还做不到** | **该，而且要一直显眼** |

KM4 那三道属于第二种（题保留是因为业务需求仍然成立），**可它们产出的信号和第一种一模一样**（`refused: true`、汇总里记「设计上拒答」），于是「有三道题我们答不了」这件事从此没人看得见。修法是让它们落在 `known_fail` 那一档，理由写「无指标可答、业务需求成立」。

**这是同一个形状第三次出现**：「空」把反问和放弃压成一档、`status: draft` 把三种原因压成一个值、现在是「拒答」把健康与缺口压成一档。**共同点都是：一个字段回答了两个问题，而只有其中一个需要人去做事。**

### 推导要有边界：只推该推的那一半

`poc/chain.py:244` 那张槽位表混着两类东西：

```
course_id / session_id / exam_id          ← 点名一个对象，可从 nameable_params 推
time_from / time_to                       ← 时间窗
kp_name_contains                          ← 模糊匹配
sort_dir / sort_by / top_n / group_by     ← 查询整形
```

**只有第一类是「哪些参数能点名对象」**，而那正是 `identified_by` 已经登记的事。后六个不指向任何概念、也没有 `identified_by`。

**所以边界是：ID 类槽位从声明推（`question_id` 自动进来），其余保持现状。** 别把整张表都改成推导——**那会逼你去给 `sort_dir` 发明一个概念声明，而那是为了让机制统一而发明知识，方向就反了。**

**一处细节**：那张表不只是名字清单，每个槽位带着值的形状（`"YYYY-MM-DD" 或 null`、`整数 或 null`）。**ID 类推导时要把「整数」这一层一起带上**——从声明推出名字、丢了类型，模型会不知道该填什么形态。

### 原始分散表本身分两类，做 CDC 时不该同等对待

这是数仓分层梳理里最关键的一条。读那份归档的溯源文档时发现：

> **总体概览**读的是**实时业务库**（MySQL 的 umu / task / data），每次请求现算；
> **进展趋势**读的是**预聚合的分析库**（Doris），由定时任务和 worker 按天/周/月预先写入，有延迟。

**所以「原始分散表」里有一类（`course_bi` 那几张、`learning_time_aggs_by_id`）本身就是一层加工产物、不是原始数据。** 做 binlog CDC 同步时这两类不该同等对待——把一张已经按天聚合过的 BI 表同步过来叫「原始表」，那一层就名不副实，**而且它的 binlog 反映的是 ETL 的写入而不是业务事件。**
