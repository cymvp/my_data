### 一处我必须更正的选型说法：JSON 和 RDF 不是平行的选项

我原话是「选 JSON 或 YAML，不选 RDF」。崔扬追问「为什么不选 RDF，RDF 的格式是什么样子」，查证之后要更正：

- **不成立**：把 JSON 和 RDF 当成两个平行的选项。**JSON-LD 既是 JSON 又是 RDF，这个对立不存在。**
- **仍然成立**：我们不该采用三元组这个数据模型。
- **准确的说法**：要拒的不是某种文件语法，是「**把一条陈述拆成一堆三元组**」这个数据模型。

**RDF 不是一种文件格式，是一个数据模型**：所有知识都必须表示成「主语、谓语、宾语」三个位置的三元组。它有四种常见的文件写法（N-Triples、Turtle、RDF/XML、JSON-LD），**其中 JSON-LD 就是 JSON**。

**真正的取舍在于：一条画像陈述要不要被拆成三元组。** 我们不拆——因为一条陈述带 25 个字段，在三元组模型里必须借「具体化」（reification）这个手法绕，**一条变成二十九条**，而我们的三个任务（塞进提示词、被服务代码读、被人审计）全都要求一条陈述是一个整体。

**这条的通用形式：选格式的判据是「要在它上面做什么任务」，不是「哪个表达力强」。** 但要注意我上一版把这条判据用错了——**判据本身对，我把「语法」和「数据模型」搞混了**。

### `predicate` 这个词：为什么中文是「谓词」不是「谓语」

崔扬问的，而这个词他正好在两个地方同时碰到——本仓库的 `tests/test_predicate_pushdown.py`，和 GUMO 论文的三段式。

**`predicate` 在计算机里指一个能判出真或假的判断。** 中文选「谓词」而不是「谓语」，因为这个词是从**数理逻辑**那一支借来的，不是从**语法**那一支借来的。

**三个落点，共同点都是真假，差别在于谁来判、什么时候判**：

| 落点 | 是什么 | 谁在什么时候读它 |
|---|---|---|
| 返回真假的函数 | `is_even(n)`、`has_passed(student)` | `filter`/`any`/`all` 这类高阶函数要求传进去的必须是谓词——`filter` 要决定每一项留不留，只有拿到真假才能决定 |
| 查询里的筛选条件 | SQL `WHERE` 后面每一个条件。**这个叫法写在 SQL 标准里，不是民间说法** | 数据库的查询优化器在生成执行计划时读它，决定把每个判断放在链路的哪一步 |
| RDF 三元组的中间那一项 | `(张三, 就职于, 优慕课)` 里的 `就职于` | 因为一条三元组在逻辑上等价于一个二元判断为真：`就职于(张三, 优慕课) = 真`。**名字来自逻辑，所以叫谓词** |

**谓词和谓语的区别，一句话**：**谓语把宾语包在里面，谓词把宾语吐出来当参数。**

| 对比项 | 谓语（语法学） | 谓词（逻辑学与计算机） |
|---|---|---|
| 「张三报销了 500 元」怎么切 | 主语「张三」，谓语「报销了 500 元」 | 谓词是「报销」，参数两个：张三、500 元 |
| 宾语算不算在里面 | **算**，宾语是谓语的一部分 | **不算**，宾语是谓词的参数 |
| 它关心什么 | 这个句子的成分完不完整 | 这个判断有几个参数，判出来是真还是假 |

**为什么这个区别有实际后果**：公司统计报销，如果每条记录只存一句话「张三报销了 500 元」，那想查「谁报销超过 500」就只能一条条读句子、一条条比数。**所以财务不存句子，要建表**——把动作单独拿出来当谓词，参数变成可筛选的列。

**顺带记一个本仓库的实测数字**（谓词下推那件事）：`docs/03-question-answering/spec/2026-08-09-predicate-pushdown-spec.md` 记了两条取数路径——一条把筛选条件写死在注册表声明里、编译成 SQL 在数据库端算（规模无上限但条件不能跟着问题变）；另一条在程序侧的派生计算里筛（条件能变，但只能在取回来的证据行上算）。**第二条路径遇到证据被截断时，数出来的是窗口内的数量，方向总是偏小——实测 88 人的数据里数出 33，真值是 36。**

**「谓词下推」的字面意思就是把这个判断往下推**，推到离数据更近的地方执行。**判断本身一个字没改，只是执行位置从程序侧挪到了数据库侧。**

### GUMO 的全称与配套三件套，以及一个要紧的事实

**GUMO = General User Model Ontology**，通用用户模型本体。三个词各有分工：**General** 指不绑定任何具体应用；**User Model** 指它描述的对象是「关于用户的模型」而不是用户本人的数据记录；**Ontology** 指它只登记概念与取值域、不存实例数据。

配套的两个名字一起记省事：**UserML** 是交换语言，负责怎么写；**UbisWorld** 是同一批人做的智能环境本体，负责 GUMO 之外的世界知识（房间、设备、位置、时间）。`u2m.org` 是那个用户模型服务的域名，`u2m` 是 ubiquitous user modeling 的缩写。

**一个刚查到的事实**：`gumo.org` 和 `ubisworld.org` 现在都返回 **500**，站点已经不在了；`u2m.org` 还能返回 200。**所以那套东西作为运行系统已经死了**——可以借它的设计，不能指望它的服务。

### UserML 不是一种独立格式，是写在 RDF 里的一套属性词表

书里第 73 页给的完整骨架：一条陈述就是一个 `rdf:Description`，底下挂 **25 个子元素**，分五组各五个：

| 组 | 五个字段 |
|---|---|
| **主体部分** | subject、auxiliary、predicate、range、object |
| **情境组** | start、end、durability、location、position |
| **解释组** | source、creator、method、evidence、confidence |
| **隐私组** | key、owner、access、purpose、retention |
| **管理组** | id、unique、replaces、group、notes |

（8 月 20 日我记的是「25 个属性分成四组」，**实际是五组**——主体部分那五个也算一组。这是当时读得不够细。）

### 那 25 个属性和「167 个基本维度、255 个兴趣类目」是什么关系

崔扬问的，而这个问题问到了一个容易搞混的地方：**25 个属性是一条陈述的「格子」，而 167 个维度和 255 个类目是往其中某个格子里填的「值」。**

具体说：167 个基本维度和 255 个兴趣类目**都属于 predicate 那一个位置的取值范围**。它们不是第 26、27 个属性，而是 `predicate` 这个格子能填什么的清单。

**这个区分的实际含义**：格子数是固定的 25 个，而清单可以增长——加一个新的用户维度不需要改结构，只需要往 predicate 的取值域里加一项。

### 悬浮窗拖动卡顿的根因：主线程被网络请求占住

崔扬报「股票程序在拖动的时候会 hang 住」。**实测数字**：

| 项 | 耗时 |
|---|---|
| 取数（A股 46 只 + 港股 1 + 美股 3，**三条串行**） | **1.57 s** |
| 脉搏计算（`load_store` 读盘 26ms + `build_state` 58ms） | 0.08 s |
| **单轮 `refresh` 主线程占用** | **约 1.65 s** |
| 刷新周期 | 3.0 s |
| **主线程被占用的时间占比** | **约 55%** |

**Tkinter 只有一个线程跑事件循环**，而 `refresh()` 在主线程里同步做网络请求。**请求期间 `<B1-Motion>` 全部排队，窗口不跟鼠标走——这就是卡住。**

**而这只是网络正常的情况**：`_fetch` 的超时是 8 秒、三条串行，**最坏一轮阻塞 24 秒**。

**为什么偏偏拖动时明显**：平时价格数字反正在跳，卡半秒不会注意；**拖动是连续动作，跟不上立刻能感觉到**。

**不是 8/19 那次改动引起的**——同步取数在主线程是原有设计。但那次把拖动手柄从时间标签换到了池子脉搏标签，**而后者正是每轮 refresh 都要重新 config 的那个控件**，感知上更明显。

### 修法（崔扬选了甲）：取数搬后台线程

新增**模块级纯函数 `collect_snapshot(codes, pulse_day)`**，取数与脉搏计算都在里面、跑在后台线程；结果放 `queue.Queue`，**主线程只读队列、只碰控件**。

原来的 `refresh()` 拆成两个循环：

| 函数 | 周期 | 做什么 |
|---|---|---|
| `refresh()` | 3 s | 只负责起后台线程；**上一轮没回来就跳过本轮**，避免慢网络下请求堆积 |
| `drain()` | **200 ms** | 检查队列、上屏。周期比取数短得多，所以数据一回来就显示 |

**两条守线程安全（不是守功能）的测试**：

- **`test_collect_snapshot_touches_no_widget`**：用 `inspect` 读源码，禁止出现 `.config(`、`self.`、`winfo_`、`.after(` 等。**做了变异验证**——塞一个 `self.pulse_text.config(...)` 当场红。
- **`test_collect_snapshot_is_module_level_not_method`**：它必须是模块级函数而不是方法，**因为方法能拿到 `self` 就能碰控件，上一条源码检查就形同虚设**。

理由是 **Tkinter 的规则很硬：后台线程碰控件不一定当场崩，可能过几天随机崩一次**，那种 bug 极难查。

## 4. 经验与教训

### 连续两天在「事件日期」上出错，判据是必须交叉验证

**8/19**：把 Fabrinet 8 月 17 日发的财报说成「今晚」，据此给中际旭创定减仓。**我把周历上「本周财报」的排期误读成了当日。**

**8/20**：写「Jackson Hole 今日开幕」，而今天查到的日期是 **8 月 27–29 日**（主席 Kevin Warsh 的首次主题演讲在 8/28 周五上午）。

**两次都是从搜索结果里直接读日期、没有交叉验证。** 而且今天那次搜索结果还把「今天」说成周四（实际是周五）——**说明搜索工具对日期的判断本身就不可靠**。

**判据：引用「今晚有 X」之前，要单独确认 X 的日期，而且不能只靠一个来源。两个来源冲突时如实说存疑，不当高等级事件。**

### 「兜住异常」和「不留痕」是两件事

那个 `except Exception` 把 NameError 静默吞掉，导致查了三轮。**兜住是对的（后台线程里抛异常没人接，界面会静默停止刷新），不记日志是错的。**

**判据：每一个 `except` 都要回答「出错时留下了什么线索」。** 只有 return 没有 log 的 except，等于把故障变成静默降级。

### 函数搬家时要检查它引用的名字在新位置存不存在

`import market_pulse as mp` 在 `_build_app()` 内部，而我把用 `mp` 的代码搬到了模块级。**Python 不会在定义时报错，只在运行时 NameError。**

**判据：把代码从函数内部搬到模块级（或反之）时，逐个检查它引用的每一个外部名字在新作用域里可见。** 这类错误配合一个吞异常的 except，能藏很久。

### 守线程安全的测试要防「绕过」

`test_collect_snapshot_touches_no_widget` 用源码检查禁止控件操作。**但如果那个函数是个方法，它能拿到 `self`，源码里写 `self.xxx.config()` 才会被抓，而写 `getattr(self, "x").config()` 就绕过去了。**

**所以补了第二条测试：它必须是模块级函数，不能是方法。** 两条一起才守得住。

**通用形式：一条基于源码文本的守卫，要配一条「让那个绕过路径不存在」的结构性守卫。**

### 「这两个项目都要用到本体」不等于「它们是同一个项目」

我把 prove 的取数纪律（口径必须有四种出处之一）套到用户画像上去论证。**崔扬明确纠正：用户画像是另一个项目。**

**判据：在 A 项目的目录里调研 B 项目的事情时，A 的纪律不自动适用于 B。** 引用一条纪律之前先问它属于哪个项目。

### 术语选型的判据用对了、但对象搞错了

「选格式的判据是要在它上面做什么任务，不是哪个表达力强」——**这条判据是对的**。

**但我把它用在了错的对立上**：JSON 和 RDF 不是平行选项（JSON-LD 既是 JSON 又是 RDF）。**要拒的是「把一条陈述拆成三元组」这个数据模型，不是某种文件语法。**

**判据：说「不选 X」之前，先确认 X 是一个和备选项同层的东西。** 语法和数据模型不同层，拿它们对立会得出错误结论。

### 五组不是四组——读结构时要数完

8/20 我记「GUMO 的 25 个属性分成四组」，**实际是五组**（主体部分那五个也算一组：subject、auxiliary、predicate、range、object）。

**判据：25 除以 5 是整数，四组装 25 个本来就该起疑。** 报结构数量时做一次除法自检。
