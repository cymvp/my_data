### 三个词的精确定义（cuiyang 明确纠正过，以后统一按这个用）

cuiyang 说「semantic_points 叫语义点，key_messages 叫关键信息，这两个是不同的东西，不要混淆」。

| 词 | 英文 / 字段 | 挂在哪 | 是什么 |
|---|---|---|---|
| **关键信息** | key message，`ConveyedInfo.Info`，数仓 `d_message` 一行 | 信息传递环节下 | 作者要学员讲出来的一条内容 |
| **语义点** | semantic point，`ConveyedInfo.SemanticPoint[]` | **一条关键信息里面** | 这条关键信息拆出的若干要点。**它是关键信息的组成部分，不是并列的东西** |

关系只有两条：**关键信息包含语义点**（语义点不跨关键信息）；**评分要点与关键信息无绑定字段**，评分要点作用于整个环节。

### Roleplay 的计分逻辑：两个互不依赖的任务

一个信息传递环节练习结束后固定跑两个任务，`evaluate_type` 只影响任务 A 的形状：

**任务 B · 语义点判定**（`RolePlaySemanticPointAnalysis`，两种情况都跑、跑法相同）
- LLM 只输出每条关键信息下每个语义点的 `is_mentioned` + 证据，**不给分**
- 代码算：每条关键信息的分 = `round(讲到的语义点数 ÷ 该条语义点总数 × 100)`（`overall_analysis_service.go:216`）
- 去处：报告逐条打勾 + 数仓 `dws_section_message_stat`。**不进环节分、不进练习总分**
- 有硬校验：`checkSemanticPointResults` 比对返回的关键信息条数和语义点条数，对不上直接 error（`:199-208`），**是硬失败不是降级**
- 有一道外层门：`req.Room.Theme.IsRoleplayChatbot()`（`:184`），**骚扰类 chatbot 的环节永远不跑 B**

**任务 A · 评分要点打分**（`RolePlayInformationTransferSectionAnalysis`）

| | 整体评估（`evaluate_type=1`，JP 99% / CN 91%） | 逐条评估（`evaluate_type=2`） |
|---|---|---|
| prompt | `value_demo_overall_eval_prompt` | `value_demo_detail_eval_prompt` |
| 输出 | **M 个分**（每个评分要点一个，对整个环节判） | **K × M 个分** + 每条关键信息一个汇总分 |
| 覆盖型要点的算法 | 分 = 全部关键信息合起来讲到的语义点数 ÷ 全部语义点数 × 100，prompt 要求**严格等于** `round(X/N×100)`、「不许浮动、不许打折」 | 对每条关键信息单独算，**允许 ±5 浮动** |
| 单条关键信息有没有来自 A 的分 | **没有** | 有 |

**四个必须记住的连带事实**：
1. **环节实得分 = `round(归一分 × section.Weight ÷ FullScore)`**（`:950-951`），练习总分是各环节实得分直接相加（`:1080`）。归一分本身是 0-100。
2. **逐条评估里每条关键信息的汇总分是代码算的，会覆盖 LLM 返回的值**（`:991` 赋值、`:997` 和 `:1078` 重新 marshal 回 `evaluate_result`）。**报告里那个数的来源是代码，不是模型。**
3. `evaluate_type` **枚举只定义 1 和 2**（`material/model/entity.go:28-29`），**0 未定义**。存 0 落逐条分支；**列是 NULL 时 `repository/covert/roleplay.go:49` 裸解引用空指针会 panic**（gorm 模型该列是可空 `*uint8`，无 nil 保护）。
4. **数仓两个盲区**（`chatbot_reporting` 的 `SectionEvaluationExplodeFn.java:37-48`）：只认 `section_type` 3 和 4，**8（事实对齐）、9（选项呈现）、10 的 message 级行被丢弃**；`section_type=3` 只取 `semantic_point_eval`，**逐条评估的 K×M 分从不进数仓**。叠加任务 B 的 ChatbotType 门，**骚扰类 chatbot 的 message 级数据在数仓里全空**。

**异议处理环节**：没有任务 B 的对等物，数仓取 `evaluations[*]`。每条异议除 K′×M 个要点分外，另有一个 `delivery_status` 三档标记（prompt `:100-122`）；汇总分同样由代码覆盖模型返回值，环节归一分按 `ObjectionInfo.Weight` 两层加权（`:1029-1050`）。

**评分要点的分类（两套 prompt 各自不同）**：整体评估侧四类（`value_demo_overall_eval_prompt:39-43`）——语义点覆盖类、动作类、态度类、**通用类**（如「关键信息与本次拜访目标相关」，也不看语义点）；逐条评估侧两套判法（`value_demo_detail_eval_prompt:29-32`）——A 套通用五档给动作/态度类，B 套覆盖率给覆盖型，判定规则是「`point_desc` 明说以覆盖度为核心的用 B，其他用 A」。

### 「切己迁移」是什么（prove 项目的核心概念）

**不是通行学术术语**，是 2026-08-20 那次会上定下的第一目的，出处在学员画像仓（`user_profile`）的文档里。

**含义**：把课上学的东西用到学员**眼下真实碰到的事情**上。Ethan 的原话是「切己一定要跟你最近碰到的事、你面临的问题相关」。「切己」取「与自己密切相关」之意，朱子读书法的「切己体察」用同一个词。所以它同时管两件事：**内容要贴着这个人当下的处境，而且要真的用出去**。

**判据靠布鲁姆认知层级补上**（当时只定目的没给判据）：迁移从「**应用**」这一级开始——能复述（记住）不算、能解释为什么有效（理解）不算、**能在自己下周那场谈话里用上（应用）才算**。出处 `user_profile/docs/spec/2026-08-23-受控词表-proposal.md:243-258`，完整讨论 `docs/ontology/03-调研成果-用户画像本体.md:724`。

**对本体建模的两条直接影响**：① 掌握程度这个关系的取值域用**布鲁姆六级**，不自己造「初级中级高级」——每级有公认定义和配套动词表，抽取时判断有依据；② 会上因此**重排了画像优先级**：学员现在的需求和他最近碰到的问题，比原先画像里的学习进度、掌握度更重要。

⚠**一个转写坑**：这个词在会议录音的自动转写里出现过三种写法（「借己迁移」「切己迁移」还有一种），`docs/ontology/04-会议卡点与文献对应.md:77` 记了这件事。cuiyang 先问的「切记迁移」大概是同一个源头的识别偏差。

### CSRS 的 token 用量：cuiyang 的前提是反的

## 4. 经验与教训

**结论下太早会被自己的后续观察推翻——今天在 A 股报告里犯了一次。** 早盘我说昨夜美光 +2.75% 强、博通/台积电弱，「值得留意会不会传导」；10:00 我说「**没有传导，两条链都在跌**」；到尾盘分化出来了（长鑫 +0.47% / 中际旭创 −1.77%）。**10:00 那句是把「30 分钟的读数」当成了「当日结论」。** 沉淀：盘中给的是观察，明确说「这是 N 分钟的读数」，不要用「没有传导」这种完成态的措辞。

**核对外部数据源的日期和时间，不要照抄。** 今天两处：
- 有条新浪快讯说「美联储将于 **9 月 14 至 15 日**召开会议」，我查了美联储官方日历，实际是 **9/15–16、决议 9/16 下午 2:00 ET**。那条快讯错了
- 我自己之前几份报告把 CPI/PPI 写成 **21:30 BJT**，实际是 **20:30**——美国 9 月仍在夏令时（EDT = UTC-4），8:30 AM ET 对应 20:30 BJT。偏晚 1 小时

**搜索返回的价格数字要去官方页核。** 查 gpt-5.2 定价时，第一批结果给了两个相差整 2 倍的报价（$0.875/$7.00 与 $1.75/$14.00），还附了一句「过去 90 天最低输入价降了 50%」。去 OpenAI 官方页核完发现标准价是 **$1.75/$14.00**，而 $0.875/$7.00 正好是它的一半——**那是 Batch API 的 50% 折扣价，被聚合站当成「降价」报出来了**。

**「同秒」不等于「同一次调用」。** 排查 CSRS token 用量时，rerank 的时间戳和 CSV 里 gpt-5.2 的行逐秒对上，差点得出「rerank 走了 gpt-5.2」的错误结论。真正的解释是**同一个请求内的不同调用**。识破它的依据是量级：rerank 送 40 篇候选，输入不可能只有 8800 token。**最后没有靠推断，打了一次真实查询把每次 LLM 调用记下来才定论。**

**服务自己记的账比外围导出更可信。** CSRS 有 `logs/token_usage.jsonl` 按请求逐条记 per-model 用量，**这比代理侧导出更细也更准**。以后查用量先找服务自己的账。

**用成交额筛板块会系统性歧视低换手率的蓝筹——这是今天挖出的一个真 bug。** cuiyang 问「今天银行涨得很好，你为什么都探测不出来」。核完事实（银行确实是全场最强，收盘同花顺行业第 1 名 +1.51%、涨跌家数 **42/0**、净流入 **+43 亿全场最大**），逐层查代码：抓取解析正常（银行在第 1 页第 2 名）、`EXCLUDE` 没匹配、`fetch_sectors` 没别的过滤。**根因是 `MIN_SHARE = 0.012`（成交额 ≥ 全市场 1.2%）**——银行占比只有 1.45%，**每天贴在生死线上**；证券 1.13%、多元金融 0.43%、保险 0.34%、燃气 0.49% **全在门槛以下**。
