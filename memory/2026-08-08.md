### 「自造枚举」的识别与拆除：用两个正交事实代替六个类别

用户的批评是决定性的：**「为什么声明会有 4 种 kind？measure 和 dimension 我能理解，但是 atomic_dataset、pre_agg_view 这两个，很像是硬凑出来的！」**

**他是对的。** 那六个类别（`measure` / `dimension_dataset` / `atomic_dataset` / `pre_agg_view` / `config_lookup` / `resolver_catalog`）是我为了描述「这条声明输出什么形状」而发明的名字，而它们其实是**两个独立事实的笛卡尔积**：

```python
{"aggregates": bool,        # DSL 里有没有聚合（要穿透 compose 与 from_query 两层壳）
 "row_grain": str | None}   # 不聚合时原样沿用源表 grain_kind；聚合时为 None
```

**关键的设计细节：聚合的声明不给 `row_grain`。** 因为它输出的行按 `group_by` 分组、粒度由声明自己定、和源表无关，**填源表的值是误导**。

**拆完之后形状分布与旧六值严格对应**：

| 新形状 | 条数 | 原来是 |
|---|---|---|
| 有聚合 | 39 | `measure` 39 |
| 不聚合 + `accumulating_snapshot` | 4 | `pre_agg_view` 4 |
| 不聚合 + `dimension` | 4 | `dimension_dataset` 1 + `config_lookup` 2 + `resolver_catalog` 1 |
| 不聚合 + `transaction` | 2 | `atomic_dataset` 2 |

**读法：第三行是关键——原先散在三个类别里的 4 条声明，现在统一是「不聚合、行粒度是 dimension」。** 其中「满分」「及格分」「考试清单」那三条留在原地、继续在路由候选里、直答能力不变，**所以用户之前那个「满分要不要支持直答」的产品决策也不用做了**。

**而且评测比拆之前更好**：

| | 拆之前（六值 `kind`） | 拆之后（两个正交事实） |
|---|---|---|
| catalog 总通过 | 40/43 | **41/43** |
| cq 拒答对 | 37/43 | **39/43** |
| catalog 拒答对 | 40/43 | **41/43** |
| 对账过 | 39/39 | 39/39 |

**沉淀出的判据：当你造出来的枚举值可以被两个独立问题的答案组合出来时，那个枚举就是多余的——应该暴露那两个事实，而不是它们的乘积。** 而且用户能一眼看出哪几个「像是硬凑出来的」，说明这种冗余是外部可感知的。

### findings 机制的漏洞：下标越界查得出来，挑错行查不出来

**这是今天在 demo 里发现的一个真 bug，而且它暴露了一个设计层面的洞。**

**机制是这样的**（`poc/chain.py` 的 `materialize_findings`）：**模型不写数据，只写「哪个指标的第几行」，真实数据由程序按下标从证据里搬。** 这个设计是为了让模型没有渠道打错数字——它唯一能写错的就是下标。

**实际出的错**：

```
"why": "学员 1325274 三次提交，首次未达及格线、后续达标"
"rows": [
   {"student_id": 1317581, "submit_count": 1, "total_score": 30, ...},   ← 另一个人！
   {"student_id": 1325274, "submit_count": 1, "total_score": 0,  ...},
   {"student_id": 1325274, "submit_count": 2, "total_score": 40, ...}
]
```

**三处对不上**：`why` 说学员 1325274，第一行却是 1317581；`why` 说三次提交，而 1325274 只有 2 行；凑成的「三次」是把别人的一行算进来了。

**代码注释里其实已经承认了这个洞**：「它唯一能写错的是下标，而越界是确定性可查的……**选错行仍然查不出来**，那是相关性判断」。

**gates 也拦不住**——因为那三行都是真实的证据行、里面每个数字都在证据集合里。**gates 验的是「数字有没有被篡改」，验不了「这几行是不是该配这句话」。**

**严重性要说准：数字本身没错**（分数、次数都是真的），**错的是证据溯源**——有人顺着这条 finding 去核对，会发现名字和 ID 对不上。对 demo 来说这挺伤，因为 demo 的卖点就是「每个数字可溯源」。

**判据很干净、可以机制化**：一条 finding 挑的行如果分属不同实体、而 `why` 只提了一个实体，就是错位。已实现并接进链路，和越界检查放在一起。

### `data_notes` 的十一种 status：「不静默降级」这条纪律的载体

**每条是 `{metric, status, note}`，记录取数过程中每一件「需要如实告诉用户」的事。** 分三个阶段：

**参数阶段**：`param_resolved`（参数由另一条指标查出来的）、`param_unresolved`（没查到，该指标被跳过、不用默认值硬算）、`param_corrected`（模型抽的参数被代码改正）、`missing_param`（缺必填参数，整条跳过）。

**取数阶段**：`no_rows`（正常执行但零行）、`insufficient_data`（探针命中，数据本身不足）、`scoped`（查询范围被限定过）、`sorted_full`（没被条数上限截断）、`sorted_truncated`（被截断了）、`enrich_missing`（补的展示列取不到值，且说明是源数据就空、不是查询出错）。

**派生计算阶段**：`compute_failed`（两次都失败，如实说算不出什么）。

**`param_resolved` 那条为什么重要**，举实例：「参数 `pass_score=40.0` 由指标 `exam_pass_score` 查得，不需要提问的人提供」——**及格线是口径，不该让提问的人拍脑袋给**。如果系统悄悄用了个默认值（比如 60），算出来的「通过人数」会全错，而**每个数字都来自证据、对账根本查不出来**。

**`sorted_truncated` 是最要紧的一条**：它是派生计算的前置条件——**被截断过的证据一律不许在上面计数**，数出来的是窗口内的数量、方向总是偏小。历史上两次错数（36 数成 34、又数成 33）都是数被截断的列表来的。

### LLM 输出被截断而代码不检查——一个「症状像另一件事」的 bug

用户报的现象是「周五新开的消息、当天没人回复的话，摘要就不会统计」，并举了 7/31 和 7/24 两个例子。

**根因和他的猜测完全不同：不是「隔天回复不收录」，而是 LLM 的输出撞上了 4096 token 的上限被截断，而代码没检查这件事。**

**为什么症状看起来一样**：摘要正文是按时间顺序写的，**被砍掉的永远是窗口最后几天**，所以看起来就像「周五的丢了」。

**证据是实测不是推演**：把输出上限抬到 16384 后，**同一份输入从 17 个话题变成 27 个**，大成建設 / ソラスト / 明治安田 全部回来了。

**修法**：新增 `LLMTruncatedError`，撞上限时抛错并**把该批对半切开重摘**，不再静默截断。

**这条经验值得记：当用户报的现象有一个「看起来很合理」的解释时，仍然要去验证真实根因——因为不同根因的修法完全不同。** 如果按「隔天回复不收录」去修，改的是抓取逻辑，而真正的问题在输出侧、一点都不会好。

### 按周补录与按天跑的行为差异：为什么补录要关掉回溯

**老逻辑有一条规则**：主消息落在窗内时，**它整条线程的回复全都拿，不管回复时间跑到窗外多远**。

**这条规则在按天跑时是对的、在按周补录时会造成重复**：

- **按天跑靠时间差**：8 月 1 号早上给 7 月 31 号做摘要时，8 月 3 号的回复还不存在，不可能包含它。等 8 月 3 号那天的摘要跑起来，回溯把 7/31 的原问题捞回来当背景、配上 8/3 的新回复——**这是补上原本会丢的东西，不是重复**。
- **按周补录是事后一次性跑完的，没有这个时间差**：每一周跑的时候所有回复都已经存在了，前一周已经把整条线程扫干净。

**举个例子**：一个项目 7 月 15 号立项、讨论拖到 8 月。你按周整理档案时，7 月 15 号那一周的档案盒里已经把这个项目从头到尾所有往来都收进去了（因为你是事后整理、能看见全部）。现在整理 7 月 27 号那一周，回溯功能又把这个项目 7 月底那几天的往来抄了一份放进来——**同一批材料在两个盒子里各有一份**。

**所以加了 `--parent-lookback-days` 配置：默认 14（日常定时用），补录传 0。** 用户报的「294 和 227 条的差别」就是这 67 条重复。

## 4. 经验与教训

### 用户今天做的纠正

**「为什么声明会有 4 种 kind？measure 和 dimension 我能理解，但是 atomic_dataset、pre_agg_view 这两个，很像是硬凑出来的！」** —— 直接指出了自造枚举。**他只凭名字就看出哪几个是凑的，说明这种冗余是外部可感知的、不是只有写代码的人才知道。**

**「可是这份 summary 是你修改『隔天回复不收录』的 bug 前生成的，为什么不会有这个问题呢」** —— 这一问逼出了真正的根因。**我原本准备按他猜测的方向去查，他自己发现时间线对不上，才转向查 LLM 输出上限。**

**「能不能加一个往前回溯查看多少天的配置，默认是 14 天；像这种总结历史周消息的场景，把这个配置外部传入 0」** —— 用户直接给出了正确的设计。**这条比我想的方案好，因为它把「日常」和「补录」两种场景的差异做成了参数，而不是两套代码。**

**「这个 demo 的重点是要让学习的人清晰理解整个链路过程，gate 的校验效果是其次的」** —— 明确了 demo 的优先级。**在「修 gate 漏洞」和「让页面讲清楚」之间，他要后者。**

**「你对通用设计的对抗式 review 的结果呢？」** —— 要求我对**自己刚做的改动**也做对抗式审查，不只是审旧设计。

### 我今天犯的错

**用文本匹配定位来改 YAML，插坏了文件。** 给评测题加 `forbidden` 字段时，第一次用 `s.index(问题字符串)` 定位，**结果命中了上方注释里的同名文字**，把 YAML 插到注释块里去了（已 `git checkout` 还原）。第二次改成按题面行匹配，但正则写错、0 道插入。第三次才发现真正的原因：**`expect` 是流式映射写在一行（`{ cq: ..., refused: false }`），没有独立的 `refused:` 行，所以内层循环永远匹配不上。**

**教训：改结构化配置文件不要用文本匹配定位，尤其当文件里存在注释、且注释会重复正文内容时。** 而且失败两次之后才去看实际结构，应该第一次失败就看。

**打错了一行常量名**（在实现 findings 错位校验时），测试直接报错才发现。

### 今天有效的做法

**用对抗方式审查自己刚做完的东西，并接受它推翻自己。** 原始 review 的主要交付（本体扩建四大清单）被判为「对 10 问零贡献、过度建模」，10 条 P0/P1 全部降级，一条被指控为「定制」的分档被平反（对抗 agent 去 Go 源码核到了具体行号）。**同时揪出了一条原始 review 根本没列的真问题。**

**判据是关键**：原始 review 按「理论上应该有什么」列清单，对抗环节按「**能不能构造出一个会算错数的场景**」检验。**后者能证伪，前者不能。**

**拆掉自己刚提交的东西时先跑评测确认没退化。** 拆枚举涉及 `poc/loader.py`、`poc/chain.py`、三个测试文件改名、四份文档，**拆完评测反而更好**（catalog 40→41、cq 拒答对 37→39）。

**用「形状分布严格对应」证明重构没丢信息。** 39 / 4 / 4 / 2 与旧六值一一对上，这比「测试都过了」更能说明等价性。

**发现 bug 时先区分「机制缺陷」和「呈现问题」。** demo 那四个问题里，「组织回答缺数据」其实是页面只显示了 `user` 那 34 个字符、而数据在 `system` 的 21804 字符里——**如果不查就改代码，会改错地方**。

**给非专业读者的材料，把「做不到」和「做得到」放同等篇幅，并且开头先给最难看的数字。** 这条是今天做那份材料时的核心判断。

**有问过但没答案的前提，就在材料里写明「还没核对」，不要替对方圆过去。** 总资产这个数问过四次没有答案，而它决定了整个仓位计划的前提是否成立——**把空缺写进给他太太看的材料里，比假装这个前提成立要诚实。**

**查根因时，「用户的猜测听起来合理」不构成证据。** 「周五消息丢失」的真实原因是 LLM 输出截断而不是抓取逻辑，两者的修法完全不同——**按错的根因去修，一点都不会好。**
