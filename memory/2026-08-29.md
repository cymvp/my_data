## 1. 今天获得的知识与技能

### Sciverse：一个能取到全文的学术文献检索工具

今天新装的 skill，名字就是 `sciverse`（全小写，无插件前缀）。它不依赖某个特定的工具协议，实现是**自带的 Node.js 脚本**，所以 Claude、Cursor、Copilot 都能用同一份。

四个脚本对应四件事：

| 脚本 | 干什么 |
|---|---|
| `list_catalog.mjs` | 看有哪些字段可查可过滤（title、abstract、doi、author、citation_count、topics 等几十个） |
| `search_papers.mjs` | 结构化检索：按作者、年份、期刊、DOI、领域筛 |
| `semantic_search.mjs` | 自然语言问题 → 论文片段 |
| `read_content.mjs` | 给一个 `doc_id` 和 offset，把原文拉出来 |
| `get_resource.mjs` | 取论文里的图和表 |

**两个实测得到的坑，下次直接用**：

1. **返回的键名是 `hits` 不是 `results`。** 第一次写解析代码时按 `results` 取，拿到空，重跑才发现。
2. **`is_content_accessible` 这个标记不准。** GUMO 那篇元数据标着「闭源、正文不可取」，**但 `read_content` 照样返回了全文 11209 字**。所以**要不要有全文得实测，不能信那个标记**。后来又实测了三篇最关键的，才确定哪些真取得到。

### 企业 SQL 数据库上，知识图谱对大模型准确率的影响（有公开基准了）

今天检索到的最有价值的一篇，作者是 **data.world 的 Sequeda 和 Allemang**——**Allemang 就是《Semantic Web for the Working Ontologist》那本书的作者**。

> **A Benchmark to Understand the Role of Knowledge Graphs on Large Language Model's Accuracy for Question Answering on Enterprise SQL Databases**（2023，DOI `10.48550/arxiv.2311.07509`）

**核心结论：同一批问题、同一个大模型，直接问 SQL 库准确率 16.7%，问知识图谱表示 54.2%。**

| 问题复杂度 × 表结构复杂度 | 直接问 SQL | 问知识图谱 | 倍数 |
|---|---|---|---|
| 简单问题 × 简单表 | 25.5% | 71.1% | 2.8 倍 |
| 复杂问题 × 简单表 | 37.4% | 66.9% | 1.8 倍 |
| **简单问题 × 复杂表** | **0%** | 35.7% | 从零到有 |
| **复杂问题 × 复杂表** | **0%** | 38.7% | 从零到有 |

**最后两行最要紧：表结构一复杂，不带语义层的直接问法准确率是零——不是「差一点」，是一道都答不对。**

**为什么这对我重要**：我们自己那份消融实验（14/15 对 10/15 对 7/15）之前**只有自己一家的数字**，没有外部对照。这篇是同一个形状的证据，而且**公开可引**。它的摘要原话也点出了这件事的处境：大模型在企业 SQL 上做问答有前景，「**但它到底能不能答准，一直不清楚，因为没有相应的基准**」。

### LOT：面向工业的本体工程框架

> **LOT: An industrial oriented ontology engineering framework**（2022，被引 169）

马德里理工那批人总结**二十多年、十八个项目**的经验做的，**专门面向工业项目**。主流程是「需求规格 → 实现 → 发布 → 维护」，按迭代反复走。

**为什么对我重要**：我们现在是**拿 SAMOD 加 METHONTOLOGY 的模板拼着用**，而那两个都不是为工业场景写的。

三处值得抄（第三处在 digest 里被截断了，只记下前两处）：

| LOT 的做法 | 我们现在 | 差在哪 |
|---|---|---|
| **需求可以有三种写法**：能力问题、自然语言陈述、METHONTOLOGY 那种表格，**不强制只用一种** | 我们只用能力问题（CQ 注册表） | LOT 原话是「**有些需求写成能力问题反而绕**」——三种混用是它**刻意的设计**，不是没统一 |

## 4. 经验与教训

### 元数据标着「不可取」不代表真取不到，要实测

Sciverse 的 `is_content_accessible` 对 GUMO 那篇标的是 False，**但 `read_content` 返回了完整的 11209 字**。如果当时信了那个标记就直接放弃，**今天最重要的那件事就不会发生**。

**推广成判据：一个「可用性」标记和「实际调一次看能不能拿到」是两件事，成本低的时候就实测。** 这和我记的那条「『有没有出现』和『有没有被使用』是两个问题」是同一类——**元数据是关于事实的陈述，不是事实本身。**

后来对三篇最关键的论文都做了实测才确定哪些真取得到，这个做法是对的。

### 新接口先确认返回结构，别按猜的键名写解析

第一次解析 sciverse 返回时按 `results` 取，拿到空；实际键名是 `hits`。**几分钟就能排掉，但如果解析代码写得复杂、空结果被当成「没搜到」，会白白得出错误结论。**

**做法：新接口的第一次调用，先把原始返回打出来看结构，再写解析。**

### 手工下载的材料不要放进自动化流水线独占的目录

见第 3 节。今天造成的具体后果是欠账数从 3 虚增到 9。

**这条的一般形式是**：**当一个目录被某个程序用作「状态」（这里是「还有多少活没干」），任何往里放东西的人都在改那个程序的状态。** 精读流水线的纪律①里其实已经写了「产物放错位置会让它一直报警」，但当时说的是产物，**没想到源文件侧也有同样的问题**。

### 改用户的配置文件前先说明并等确认，但要把话说清楚

装 sciverse 时需要写 `SCIVERSE_API_TOKEN` 到 `~/.zshrc`。我的做法是：**先说明「按规则改配置文件要先经你确认，而且 token 本身得你提供」，并给出两个选项（写 `~/.zshrc` 全局 / 写项目 `.env`）**，等 cuiyang 把 token 发过来才动手。

这个流程是对的。**同时要提醒的两件事也都说了**：新开终端才生效、token 明文存在 `~/.zshrc` 别提交进仓库。

### 密钥不往 memory 文件里抄

cuiyang 在对话里明文给了 token。skill 说「涉及人名/敏感信息照实记（这是私人 memory 仓）」，但**我判断 token 不适用这条**：memory 文件会 commit 进 git 仓库，**把密钥从 `~/.zshrc` 复制到另一个位置只会增加暴露面，不增加任何可用性**——要用时从 `~/.zshrc` 取即可。所以这份文件里只记「token 已配置在哪个变量、哪个文件」，不记值。

这和我在 my_scripts 那边一直守的那条（webhook 绝不写入公开仓库）是同一个判断。
