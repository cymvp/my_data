### 类表达式和公理的分界是「有没有自由变量」

崔扬今天连问了五轮这个点（「什么是类表达式？谓词算什么，算断言么？」「那 `I(R)` 也是类表达式了？」「`≤n R` 的类表达式怎么写？」「`∀y₀…∀yₙ. (R(x,y₀) ∧ … ) → ⋁ yᵢ=yⱼ` 这个不就是公理了么？？？」「我还是不明白，你用举例子来解释」）。

**最终定下的分界**：

| | 类表达式 | 公理 |
|---|---|---|
| **形式特征** | **有自由变量 x** | **没有自由变量**（x 被 `∀` 绑住了） |
| 它是什么 | 一个**集合**的描述，代入个体才有真假 | 一个**句子**，本身有真假 |
| 例 | `∀R.C` 展开成 `∀y. R(x,y) → C(y)`，**x 自由** | `课程 ⊑ ∀R.C` 展开成 `∀x. 课程(x) → ∀y. R(x,y) → C(y)`，**x 被绑** |

**同一串符号在两个位置上身份不同**：`≤1 授课` 单独看是类表达式（描述「至多有一位讲师的那些个体」这个集合）；写成 `课程 ⊑ ≤1 授课` 就是公理。

**崔扬的那句「这个不就是公理了么？？？」抓得准**：我给的展开式 `∀y₁∀y₂. (授课(x,y₁) ∧ 授课(x,y₂) → y₁=y₂)` 里 x 是自由的，**所以它还是类表达式；一旦在前面套上 `∀x. 课程(x) →`，才变成公理。**

**关于 `I(R)`**：崔扬问「那 `I(R)` 也是类表达式了？因为是对应一个集合！」——**不是**。`I(R)` 是解释函数的输出，是一个**实际的集合对象**；类表达式是**语法层的一串符号**。两者的关系是「类表达式经解释得到集合」，不是同一层的东西。

### `Course ⊑ ≤1 courseTaughtBy` 的含义（崔扬问「属于关系为什么还有个数限制」）

**这是基数约束（cardinality restriction）**，读作「每门课至多沿 `courseTaughtBy` 连到一个个体」，即**至多一位讲师**。

一阶展开：`∀x. 课程(x) → ∀y₁∀y₂. (授课(x,y₁) ∧ 授课(x,y₂) → y₁=y₂)`

**注意它和函数性（Func）的区别**：`Func(R)` 是对**关系本身**说「它全局是函数」，`C ⊑ ≤1 R` 是对**某个类**说「这个类的个体沿 R 至多一条边」。**后者允许别的类沿同一条关系有多条边。** 本方案用后者，因为关系名是全局共用的（基石 B2）。

### `rdfs:domain` 推理不合理的地方在「前提为假」

崔扬对我的解释不满意：「**这块你解释的更清楚一些，举的 domain 的例子，推得不合理的地方在哪里。** 另外『它做两件事我们都不要』，你也只说了这一件事情。」

**修正后的说法**：

`rdfs:domain` 的推理规则本身在逻辑上是**有效的**（valid）——「如果 P 的定义域是 C，且 x P v 成立，那么 x 属于 C」这个推理形式没错。

**不合理的地方在于前提为假**：写下 `title rdfs:domain Course` 这条前提，断言的是「凡是有标题的都是课程」。**本仓的 `title` 被课程、小节、考试、题目四条类的映射共用**，所以这条前提**是假的**。从假前提出发，有效的推理也会给出错的结论。

**「它做两件事我们都不要」，两件分别对到两条基石**：
1. **把属性绑死在一个类上** → 撞 **B2**（属性名全局登记，不绑定类）
2. **遇到不符的数据不报错，反而改数据** → 撞 **B5**（校验对数据报违规，不改数据）

### 类与类之间只有两种联系

崔扬对这一节骂了两次（「这章节内容写的不清不楚，到底类与类有几种关系？」「你写的还是乱糟糟的，逻辑不清晰」），**逼出了一个干净的两分**：

| 联系 | 形式 | 说的是什么 |
|---|---|---|
| **子类关系** | `A ⊑ B`（右边是**裸类名**） | A 的每个成员也是 B 的成员。**只在继承检验通过时登记** |
| **经关系相连** | `C ⊑ ∃R.D` 等（右边是**类表达式**） | C 的个体沿 R 连到 D 的个体 |

**第二种上面能立三类约束**（崔扬纠正过我的措辞，我原来写「两类规矩」，他说「应该是三类约束，『规矩』这个词你完全用的不对」）：

1. **至少一个** —— `C ⊑ ∃R.D`，SHACL 的 `sh:minCount 1`
2. **都是某类** —— `⊤ ⊑ ∀R.D`，SHACL 的 `sh:class`
3. **边数上限** —— `C ⊑ ≤n R`，SHACL 的 `sh:maxCount`

**另外两种情况归位**：**带值的关系**（「学员对知识点有掌握度」）走**物化**——关系本身成为一个类，相关的类用关系连到它；**关系之间的公理**属于 RBox，不是类与类的联系。

### Palantir 不能整体改用，原因只有一条但是决定性的

崔扬今天新提了一个此前没正面核过的问题：「**我们从来没有考虑过使用 Palantir 的体系，包括规范词、建模体系、底层约束。你看一下是否可以改用 Palantir。**」

**核对结果**：**建模概念一一对应，十条基石九条符合、一条中性、零冲突。**

| Palantir | 本方案规范词 | 对得上的程度 |
|---|---|---|
| 对象类型 | 类 | 一一对应 |
| 对象 | 个体 | 一一对应，**且对象就是行，与 B6 一致** |
| 属性 | 属性 | 对应，它的属性含枚举取值，**与 J6 的分界一致** |
| 链接类型 | 关系 | 对应，**多出两条：双向各有名字；多对多要有自己的支撑表** |
| 共享属性 | 属性名全局登记一次 | **就是 B2** |
| **接口** | **无对应物** | 一组属性和链接的形状要求，多个对象类型实现它 |
| 动作类型 | **无对应物，且明确不要** | 写操作；与学员画像的「动作」含义相反 |
| 函数 | 指标、`poc/compute.py` 的算子 | 本方案已有 |

**但不能改用，原因是底层约束**：

> **它的约束是 Foundry 平台的内置行为：没有一种可导出的约束语言，没有平台之外的校验器，没有公开的形式定义。**

**乙方案的三个理由在 Palantir 体系里一条都拿不到**：三套系统跑同一份检查单、本体定义本身可被检查、约束从代码变成声明。

**结论一句话**：把「Palantir 式」当第四条路放进选型比较，**它的位置是「基石全部符合，但每一条都要自己实现校验器，等于甲方案换一套词加几条做法」。**

**乙方案的价值不在基石符合得多，在于约束能以 W3C 标准形式导出并被现成工具（pyshacl）校验。**

## 4. 经验与教训

### 改文档之前，先问这些内容和目标读者有什么关系

崔扬今天开工前的那个质问（一阶逻辑的公式和 RDFS/SHACL 建模到底什么关系；如果没关系是不是就不该关注）**改变了整章的写法**。

**如果不先问这个，我会继续往 3.4 里堆公式和推导**——每一条单看都正确，合起来对「要建模的工程师」没用。

**固化**：写或改一份给人看的材料之前，先明确回答两件事——**读者要拿它做什么**、**这部分内容和那件事的关系是什么**。答不出「关系是什么」的内容，**要么删，要么明确标成背景**。

### 因果方向要查一遍，别把「需求」算成「贡献」

我把「校验能力」列成描述逻辑给这个方案的贡献，**崔扬指出因果反了**：是我们先立了基石，才需要一种能校验基石的方案；**校验需求来自基石，不来自描述逻辑**。

**这个错误的形状是：把「因为 A 我们才需要 B」写成了「B 给了我们 A」。**

**固化**：列「X 给了我们什么」这类清单时，逐条问一句「**如果没有 X，这件事还需要吗？**」答「还需要」的，就不是 X 的贡献。

### 同一串符号在不同位置身份不同，讲解时要把位置一起给

崔扬为「类表达式 vs 公理」连问五轮，最后的分界是**有没有自由变量**。

**我前几轮讲不清的原因**：我一直在解释「`≤n R` 是什么」，**而正确的答案取决于它出现在哪里**——单独看是类表达式，写在 `⊑` 右边就是公理的一部分。

**这和昨天 `sh:class` 那个错是同一类**：昨天我从 `sh:property` 块里摘出一行，语义就变了；今天我把一个类表达式单独讲，也丢了它的位置信息。

**固化**：解释一个符号或一段代码时，**必须连它所在的位置一起给**。「X 是什么」这个问题在很多情况下答案是「取决于 X 在哪」。

### 「推理有效」和「前提为真」是两件事

我原来说 `rdfs:domain` 的推理「不合理」，崔扬要求说清不合理在哪。

**正确的说法是：推理规则本身是有效的，不合理在于前提为假。** 「如果 P 的定义域是 C，且 x P v，那么 x 属于 C」这个推理形式没错；**错在「title 的定义域是 Course」这条前提**——本仓 title 被四个类共用，这条前提是假的。

**从假前提出发，有效的推理也会给出错的结论。**

**固化**：说一个推理「不对」时，要分清是**推理形式无效**还是**前提为假**。这两者的修法完全不同——前者要换推理规则，后者要换前提。

### 措辞被纠正三次，共同点是「用了不精确的日常词」

| 我写的 | 问题 |
|---|---|
| 「归位」 | 不是标准词，读者不知道指什么 → 改「变化」 |
| 「规矩」 | **完全用错**，它指的是约束（constraint）→ 改「约束」 |
| 「公理(约束)」「断言(事实)」 | **规范词和括号里的词不能画等号** |

**第三条最值得记**：我用括号给规范词加别称，是想帮读者理解，**但那等于宣布两个词同义**。「公理」和「约束」在本方案里不是同义词——公理是建模层的一条句子，约束是它在约束层的形态。

**固化**：**不要用括号给术语加别称。** 要解释就单独给一句定义；要给别名就明确标「别名」，并说清两者的关系。

### 讲义和方案文档要做一致性对齐，而且是双向的

崔扬问「**你其他的几个相关文档，也都对一致性进行修改了吧**」——这一问指向一个我容易漏的事：**讲义是从方案文档提炼的，但讲义里被打磨过的表述（更清楚的例子、更准确的措辞）也该回流到方案文档。**

今天的 `a6b134d` 就是这个回流：讲义里换掉的虚构例子（课程类型 → 题目主客观性）、统一的公理写法（`∃title` + `minCount 1`）、三类约束的说法，**全部同步回了方案、RDF 入门、样例三份文档**。

**固化**：从一份文档提炼出另一份之后，**打磨发生在哪一份，都要往另一份回流**。否则两份会各自漂移，而读者不知道该信哪份。

### 「零冲突」不等于「可以采用」

Palantir 的核对结果是**十条基石九条符合、一条中性、零冲突**——按这个数看，它似乎完全可行。

**但结论是不能改用，原因是一条基石之外的东西**：它的约束是平台内置行为，**没有可导出的约束语言、没有平台外的校验器、没有公开的形式定义**。

**乙方案的价值不在基石符合得多，在于约束能以标准形式导出并被现成工具校验。**

**固化**：核对一个方案时，**除了「它违反我的规则吗」，还要问「我选现方案的那几个理由，它能给吗」**。前者是排除条件，后者才是选择条件。**零冲突只说明它没被排除。**
