## 4. 经验与教训

- **cuiyang 极度反感文档里的模糊表述和箭头**：他明确说过正文禁用箭头（`→`/`←`），箭头只允许出现在代码块/图里。今天助手在指标模板里引入了 199 处箭头结构记号，被他抓出来要求全量清掉。类似地，"BI 侧"这种没指明具体表/字段的模糊词、"有过报名事件即算"这种没追生命周期的表述，他都要求改成精确指代。给他写文档时，任何概念第一次出现就要落到具体的表名、字段、file:line。

- **他要求指标命名有意义、不能随便起**：如果不确定合适的名字，要主动说"我们一起 review"，不要默默挑一个。同名不同义的指标（如带教和学习任务都有 task_complete_rate）要明确标出区别。

- **他要求文档有层次感**：涉及的表要分层（直接参与计算的表是第一级，上游生成表缩进为二级），不能平铺让人误以为多张表同时参与计算；取数逻辑要按血缘展示；口径差异用对比表格而非一段带圈号的文字。

- **"先写一个样板，我确认后再全量"是他偏好的工作节奏**：今天多次是助手先手写一个指标（by_action）给他验收，通过后才用 workflow 全量重写。不要一上来就批量产出。

- **校对/重写时容易沿用旧的口头结论而不重新质疑**：今天暴露一个教训——重写时校对 agent 核了 SQL 形状对不对，但没往前追一步问"这个 enroll_id 行会不会消失"，导致"有过报名即算"这个从早期口头表述沿用的错误没被抓出，是 cuiyang 一问才回代码发现取消报名是物理删。教训：核实一个断言时不能只核当前 SQL，要追数据的完整生命周期（写入、更新、删除）。
