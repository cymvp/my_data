## 1. 今天获得的知识与技能

**指标口径统一的正确认知（今天讨论最深的一块，纠正了此前的误解）**
- "统一口径"要统一的是**语义**，不是**算法个数**。同一个指标名只能指向一个明确的意思，但这条语义定义内部完全可以按内容类型分派到不同子算法。把不同算法物化到一个统一字段、下游只看这个字段，是标准做法（语义层的职责）。
- 业内权威依据：**Kimball 维度建模的"一致性事实"（conformed facts）**——同一度量出现在不同来源时，技术定义完全兼容才能同名并可比较/合计；不兼容就必须用不同名字来警示用户和 BI 工具（来源：Kimball Group 官方 conformed-fact 文档、PowerMetrics 最佳实践）。
- 判断"拆不拆成两个指标"的标准：**能不能写出一条"两种算法都算是在忠实实现它"的方法无关（method-agnostic）定义**。能→一个指标、一个字段、底层按内容分派、下游统一取数（不拆）；不能（两个意思本就不同、放一起会误导）→ 拆成两个各自命名的指标。只有"两算法号称算同一个量、输入也相同、结果却打架"才是 bug，才适用"废弃一个"。
- 关键澄清："不兼容"是个**判断题**（放一起加总/比较会不会误导用户），不是**是非题**（算法是否相同）。
- 语义层（dbt / Cube / Holistics / Atlan）屏蔽的是"计算的技术复杂度"（SQL、join、粒度），**不负责**屏蔽"语义不兼容"——把两个意思不同的量塞进一个名字是掩盖歧义，不是屏蔽复杂度。
- 配套原则：屏蔽 ≠ 抹掉。默认给下游一个干净指标，但每条数据带"来源/算法"标记可追溯（接"证据抽屉"设计）。

**HTML 讲解页方法论**（来自 Thariq《The Unreasonable Effectiveness of HTML》一文）：让 Claude Code 用全仓上下文生成 HTML 讲解页替代 GitLab diff 视图——调用链图 + 保真 diff + 意图注释 + 风险处置。核心是"人是否真的会读"，超过 100 行的 markdown 人就退出了决策回路。

**Claude Code 会话存储结构**：`~/.claude/projects/<项目编码>/<session-uuid>.jsonl`，每行 entry 带 UTC timestamp、message.content、cwd、gitBranch。跨 session 汇总当天工作可行。注意 `-Users-ycui-*` 项目目录是同步脚本建的软链接，指向 `-Users-cuiyang-*` 真实目录，扫描时要按真实路径去重。
