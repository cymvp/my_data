### 「市场预期被设在公司自己指引的上限之上」——一个被验证的风险判断

**这是今天最有价值的一次事前判断得到兑现。** 8 月 4 日算过闪迪（SanDisk）财报的风险点，今天应验：

| | 公司自己的指引 | 华尔街一致预期 |
|---|---|---|
| 营收 | 77.50~82.50 亿美元 | **83 亿美元** |
| 每股收益 | 30~33 美元 | **34.24 美元** |

**两项预期都高于公司指引区间的上限。** 也就是说，即使公司按自己给的最好情况交付，也达不到市场门槛。结果：闪迪收盘 −5.40%、盘后再跌 7.96%；西部数据收盘 −5.36%、**盘后 −11.73%**；希捷收盘 −0.91%、盘后 −2.23%。MarketWatch 08-05 21:25 的标题印证了归因：「Sandisk 股价下跌，因公司指引未能达到高预期」。

**可复用的判断方法：财报前把「公司自己的指引区间」和「华尔街一致预期」摆在一起比，如果预期已经高于指引上限，那么即使基本面正常也大概率被判「不及预期」——跌的不是业绩，是预期差。** 8 月 4 日的 AMD 是同一类：营收和 EPS 双超预期，却因毛利率 54% 低于预期 56% 而盘后跌 8.82%。

### Slack 摘要里一个只在真实历史数据上才会暴露的 bug

补录 `C099ESWHSUU` 频道时，产出里有 **3 个文件只有 3 字节**——内容就是一个「无」字。

**根因**：prompt 里写了「如果整天没有值得沉淀的内容，只回复：无」，但代码**只判断空白字符串**。「无」是非空白字符串，于是被当成一份正常摘要处理了。

**后果分两处，第二处更要紧**：

- **补录**：写出 3 字节的 `.md`，入库后知识库里多一条正文是「无」的文档；
- **日常任务**：会往频道发一张正文是「无」的卡片，**有人点「发布入库」就真进库了**。

**修法**：整段回复等于「无」及常见变体时，与空白同样处理（不发消息、不写文件）。**只在整段匹配才算**——正文里出现「无」字（比如「结论：无法恢复」）不受影响；分批时只丢「无」的那一批。加了 5 条测试，817 个单测全绿，3 个垃圾文件已删。

**最值得记的一点：这个 bug 在线上跑了 8 天没暴露，因为那几天恰好每天都有值得沉淀的内容。只有跑真实历史数据（一年多里必然有安静的周）才会碰到。** 这说明**补录历史数据本身就是一种测试手段**——它能触发日常流量碰不到的分支。

### Slack bot 的两个权限是分开的：能读消息不等于能读频道名

查私有频道 `C0BES6X7KL1` 的名字失败了。原因是**`groups:history`（读私有频道的消息）和 `groups:read`（读私有频道的元信息）是两个独立的 scope**，这个 App 只有前者。所以 **bot 能看见频道里聊了什么，却看不到频道叫什么名字**。

试过两条不需要新 scope 的旁路，都没结果：频道改名时 Slack 会在历史里留一条带 `old_name`/`name` 的系统消息（翻了 100 条没有，说明建群后没改过名）；别人提到频道时消息原文是 `<#C0BES6X7KL1|名字>` 这种带名字的格式（三个频道各翻 200 条，没人引用过）。

**结论：最快的办法是用户自己在 Slack 里打开那个频道看标题栏。** 加 scope 要重装 App、token 会变、配置要跟着换，为了查个名字不值。

**顺带一个重要事实：频道的 `name` 字段改不改、叫什么，对程序都没影响**——配置里那个 `name` 只是日志和 prompt 标签，**入库文件名用的是 channel_id**（`slack_summary_C0BES6X7KL1_20260720.md`）。

### launchd 的 `runs = 0` 不代表任务没跑

`launchctl print` 显示 `runs = 0`、`state = not running`，看起来像没执行过。**但 launchd 对 `StartCalendarInterval` 类型的任务是每次触发起一个新进程、跑完就退出、不常驻**，所以这两个字段本来就是这样。

**真正的证据是日志**——实测 5 次输出、5 个 HTTP 200：

```
2026-08-05 09:45 北京  → Slack 200
2026-08-05 10:00 北京  → Slack 200
2026-08-06 09:30 北京  → Slack 200
2026-08-06 09:45 北京  → Slack 200
2026-08-06 10:00 北京  → Slack 200
```

8/5 的 09:30 那一档没有，是因为 launchd 是 09:33 之后才装好的、已经错过。

## 4. 经验与教训

### 我今天犯的错

**早盘归因错了一次，尾盘已更正。** 把「AMD 财报后盘后 −8.82%」称为当天最重要的一条，但实际主导 8/5 光模块低开的是 FCC 拟禁止中国光模块进口的消息，媒体口径一致指向后者。而 AMD 的真相是**双超预期、跌在毛利率不及预期**，当成负面基本面信号也是误导。

**沿用了一周前的旧结论没有重新核实。** 在 csrs 那条线上说「bot 还没被邀请进频道」和「日常定时从未真实产出过摘要」——这两条是 **7 月 28 日部署当天**的结论，今天是 8 月 6 日，中间用户已经把 bot 拉进频道、日常闭环已稳定跑了 8 天。**教训：跨了一周以上的结论，引用前必须重新核实，不能凭上次判断直接说。** 这和 8/5 那次「用 5 行样本代表 3062 行」同源——**都是没用独立方式核实就下结论**。

**处理方式是对的**：发现后立即在回复开头给「当前有效结论」台账，把「我上一条说的」和「实际情况」并排列出，并说明哪条仍然成立（补录方案不受影响）。这正是 8/4 写进 CLAUDE.md 的第一条规则。

**差点漏提交一个文件。** `loop_tasks.json` 是在第一次 commit 之后才改的，所以没被带上、远端还是 6 条。**教训：commit 之后又改了文件，要再查一遍 `git status`，不能假设「刚提交过所以是干净的」。**

**探过一个不存在的路径就当成故障苗头。** 重启 demo 后探 `/trace` 得到 404，那是自己猜的路径、不是真实路由。**先查真实路由再判断。**

### 今天有效的做法

**主动对前几天给过的判断做事后对账，包括会推翻自己的那条。** 五条里三对一错一部分对，**而最有价值的正是那条错的**——它推翻了 8/3 那个「下跌趋势开盘往往是最高价」的结论，而那正是用户 8/4 清仓后悔的依据。**给可证伪的判断、并且事后真去对，比只给结论有用得多。**

**给判断时附一个具体的可观测信号，第二天就能验证。** 今早给的「如果下午跌回今开 901 下方，说明修复是反抽不是反转」和「如果涨跌家数变成 130/50 那种，说明是普涨」，两条都在收盘时得到了明确判定。**这比「我觉得可能会怎样」有用，因为它把验证权交给了用户。**

**时点不对就明说，不要假装在正确的窗口里。** 尾盘任务在 12:05 午休触发，照 prompt 做了但报告开头明确写「现在是午休、数据是 11:30 快照、下午还有两小时会变、建议 14:30 后重跑」。**日内流水线在 12:14 触发时直接不执行**，先实测兜底会拦住、再说明硬跑毫无意义。

**问题提了四天没动、且已造成实质后果时，直接写进任务 prompt 止血，而不是继续等确认。** KOSPI 数据源从 8/3 提到 8/6，今天它把「KOSPI 反向」告警发反了，性质从「数值偏差」变成「定性判断出错」。**同时要说清「改 prompt 是止血、不是修复」**。同理 `loop_checker` 的判据修改也直接做了，因为再不改 8 月 10 日那轮会全部任务集体消失。**判断标准是：如果继续等确认会导致不可逆的损失，就先做，然后把做了什么和为什么说清楚。**

**工具「有输出了」不等于「输出可用」。** 长鑫的 5 日波动率从「没有」变成「2.43%」，但那个值是被三天异常平静压出来的假值，而且和同组的「超 ±2% 概率 50%」自相矛盾。**发现两个派生数字互相打架时，那是模型没有可用样本的信号，不是精度问题。**

**抽查规则要覆盖整行而不是单点。** 8/5 那次单格只偏 0.90pp 没触发阈值，但同行四列都超了。今天扩成整行之后，立刻抓出 5 列超标且方向系统性一致。**单点抽查会漏掉系统性漂移。**

**用一次故意的失败测试证明保护真的生效。** 补录的重叠保护写好后，故意用 `--until 2026-08-02` 跑了一次，让它把冲突的 5 个文件列出来——**证明保护会拦，而不是只写了代码。**

**补录历史数据本身就是一种测试手段。** 那个「无」bug 在线上跑了 8 天没暴露，因为那几天恰好每天都有内容；只有跑一年多的真实历史（里面必然有安静的周）才会碰到。**以后上线新的生成类功能，可以主动拿历史数据回放一遍来找边界分支。**

**并发跑任务时先确认没有重复。** 担心新起的 runner 和原任务撞车，查完确认没有（runner 没活下来）。**而且发现「日志 0 字节」是 Python 输出缓冲的假象、不是任务没跑**——判断任务是否在跑要看产出文件，不是看日志大小。顺手停掉了抢限流额度的多余 dry-run。

**改动会影响启动的代码之后，先单独验一次加载再重启。** 改过 `poc/loader.py` 加了加载期校验，重启前先单独跑一次本体加载，避免启动直接崩。
