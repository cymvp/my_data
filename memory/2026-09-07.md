### 数仓迁移 OKR：一致性 99% 为什么没有分母

**这一条的形状是「同一个百分比套在两种量级上，含义完全不同」**：

- `exam_detail` 是**几十亿行**量级，**1% 就是几千万行**
- `task_data` 这类统计表是**百万行**量级，1% 是上万个错数字

**而且还有一个更根本的问题**：快照层从 T+1 定格变成实时之后，**双跑对比只要当天有组织变更就必然 diff**——这个 diff 是设计意图，**用一致率去量它，达不到和达到了都说明不了问题**。

**最终的解法是分层判定 + 换验收方式**：

| 层 | 一致性要求 |
|---|---|
| 统计层（`task_data`、`question_data`、`knowledge_point_data`） | **≥ 99.9%** |
| 明细层（`user_question_detail_data`、`exam_detail`） | ≥ 99% |
| 关键口径（正确率、答题数、任务完成率） | **100% 落在容差内** |
| **8 张快照表** | **不计入一致率**，改两条硬验收：视图 SQL 与 PHP `getData()` **逐字段语义等价核对通过**；同一时刻分别执行视图 `SELECT` 与 PHP `getData()` 的**定点回放结果逐行相等** |

**一致率的分母也定死了**：按各表 `unique_keys` 对齐后所有非排除字段相等的行数，**除以两侧行键并集**；排除 `create_ts` 与 `update_ts`；浮点按千分位容差。

**所有差异必须归入四类之一**：timing、已知语义变更、源差异、**bug**——其中 **bug 类恒为 0**。

### 「基线不用等补埋点，历史数据已经在日志里」——一个可复用的发现

数仓迁移文档原来的结论是「迁到 Flink 后无法与现状做耗时对比」，**这条被我撤掉了**，理由是：

- `Util::commandLogForCli` 每行前缀 `[Y-m-d H:i:s]`（`module/common/Util.php:1331`）
- `WorkspaceKnowledgePointReport.php:44-49` 在**每个企业 × 每个类**执行前打一行带 `snapshot_class` 和 `enterprise_id` 的 JSON

**相邻两行时间戳相减，就是那个类在那家企业上的耗时。** 只要拿到 cron 机器的 stdout 重定向路径，**能回溯出至少数周的分类基线，粒度比 `scheduled_task` 埋点表还细**——埋点表只有整个 subtask 的起止，日志有每企业每类。

**这条的普适形状是**：「要补埋点才能测」这个结论，**要先检查现有日志的时间戳精度**。带时间戳的逐步骤日志本身就是一份埋点，只是没被当成埋点用。

### 二阶算子的定义（本体 OKR 的 KR4 量错了东西）

崔扬给了一份二阶算子的文档（`~/Downloads/sales-visit-dynamics-faq_1.html`）。**二阶算子的名字来自两次时间差分**：

```
速度   v(t) = x(t) − x(t−1)      这周比上周涨了多少
加速度 a(t) = v(t) − v(t−1)      涨的速度在加快还是放缓
```

**KR4 的问题不是数字定高了，是量错了东西**——它用「准确率 90%」去量一个二阶量，而二阶量的正确性判定和一阶量不是一回事。

### 知识点分析任务的完整结构（今天核清的持久事实）

`cronjob_create_snapshot.php` 是知识点分析的 **T+1 离线统计入口**。每天跑一次，**14 个类按固定顺序写出 13 张表**，按 `eid % 10` 分 **10 个进程并行**，失败的企业收集起来 **sleep 120 秒后重试一轮**，再失败发 Slack。

**数据分四层**：`umu` 等 4 个业务库的原始表 → **8 张结构快照** → **5 张统计表** → **9 个 uapi 接口**。快照层回答「组织和知识点结构长什么样」，统计层回答「答得怎么样」。

**完整表级依赖图在**：`https://claude.ai/code/artifact/266f5d61-5f89-4f65-b896-70c336e092e5`（这是我自己发布的，可改）。崔扬另有一份 14 表拆解 artifact `1bd9b522`，**那份是别人写的、我改不了**。

**四处纠正过的常见理解**：

| 常见理解 | 事实 |
|---|---|
| 快照层是「只给统计层用的中间产物」 | **错。8 张里有 6 张是页面请求时直接查的**，部门树、成员列表、搜索、权限判定全靠它们。**删掉快照层页面直接瞎** |
| 快照是历史全量 | **错。** MySQL 模式下 `flashData()` 的删除条件**只有 `enterprise_id` 没有日期**，每次跑批把这家企业的历史行全删了再写，**任何时刻只有最新一份**。Doris 模式靠 `datekey` 留 3 天，但**每个分区都是当天的完整状态、不是增量**——留 3 天是为了「今天没跑完就退回读昨天」，不是存档 |

## 4. 经验与教训

### 改度量指标之前，必须先把基线摆出来

三份 OKR 我都是**先摸清「现在能测什么、有哪些现成数据」，然后才动指标**。记忆系统那份花了 21 次工具调用做这件事。

**理由一句话**：否则指标会写成拍脑袋的数字，**目标值没有参照点**。

**而且这个动作本身会发现问题**——记忆系统那个「口径错配」就是在摆基线的过程中发现的：把 hit@5=1.000 和 Zep 71.2% 并排放，才看出这两个数不是同一个指标。

### 「分母可以按结果反过来挑」是百分比指标的通用漏洞

本体 OKR 的 KR3 写「涵盖 > 80% 的相关应用」，但**相关应用一共几个、是哪几个，原稿没列**。

**后果**：做成 8 个就说总共 10 个，做成 4 个就说总共 5 个，**两次都是 80%**。

**固化成检查动作**：看到任何百分比指标，问三件事——**分母是什么？分母现在等于几？分母的清单在哪里能查到？** 三个答不齐，这个指标两个月后不可验收。

### 「口径陷阱」：分子分母的选法能让指标自动达成

数仓 OKR 的 KR1 是最干净的例子：**8 张快照视图化之后每日执行时间归零**。如果拿 14 张表的总耗时当分子，**这一个动作就独自完成了「缩短 50%」，而统计层可能一分钟都没快。**

**那样 KR1 就成了口径的胜利，不是工程的胜利。**

**解法是拆成两个数报告**：统计层 6 张表算比例，**快照层 8 张表单独报告、不计入**。

**固化**：定一个「降低 X%」的指标时，问一句「**有没有某一个动作能单独把这个数做出来，而它并不是我真正想优化的那件事？**」有，就必须把那部分单独拆出来。

### 「交付物」不是「度量」

三份 OKR 里都有这个毛病：「治理系统上线」「画像上线」「支持一个应用」「可实际支持 Learning Library 线上产品」。

**「X 上线」是交付物，不是度量。** 判据是：**两个月后有没有一个数能让双方都同意「达到了」或「没达到」？** 「什么算支持」没有定义，**两个月后谁都可以说做到了，也可以说没做到**。

**换成能数出来的量**：接入了几个应用、日均写了多少条记忆、抽取失败率多少、有没有 P0。

### 「同一个百分比套在不同量级上，含义完全不同」

一致性 99% 那条：`exam_detail` 几十亿行，**1% 就是几千万行**；`task_data` 百万行，1% 是上万个错数字。

**解法是分层定阈值**，而不是给一个统一的数。

**还有一层更细的**：如果某个层的语义本身变了（快照层从 T+1 定格变实时），**那个层就不该用一致率去量**——因为 diff 是设计意图，**达不到和达到了都说明不了问题**。要换成别的验收方式（语义等价核对 + 定点回放逐行相等）。

### 「要补埋点才能测」这个结论，先检查现有日志

数仓文档原来写「迁到 Flink 后无法与现状做耗时对比」，**这条是错的**——`commandLogForCli` 每行带时间戳，而跑批在每企业每类前打一行 JSON，**相邻时间戳相减就是耗时**，粒度比专门的埋点表还细。

**固化**：听到「没有基线，要先补埋点」，先问两件事——**现有日志有没有时间戳？有没有逐步骤的打点？** 有，就已经有基线了，只是要写个脚本去挖。

### 别人的 artifact 改不了，而且不该复制一份来改

崔扬给的 14 表拆解 artifact 标的是「shared with you, written by someone else」，**我改不了那个 URL**。

**当时有两条路，我推荐了「只产出度量节、由他或作者贴回原文档」**，理由是：**那份拆解是事实那一侧的正本，度量应该长在它身上**。发一份新的会让同一份知识变成两份，**之后各自漂移，哪份是正本会说不清**。

**这条和 CLAUDE.md 里「同一份知识如果被抄成多份，问哪一份是事实、哪些是用途，正本应当放在事实那一侧」是同一条。**

### 我今天又修正了一次自己的技术判断

我一开始说 `KnowledgePointResourceSnapshot` **含 PHP 业务逻辑搬不了**。**这个判断错了**——它调的 `getSpecifyExamBySessionIds` 就是一条 SQL，写进视图就是多 JOIN 一张表。

**根因是我看到「有个 PHP 方法调用」就假定里面有不可翻译的逻辑，没有点进去看那个方法体。**

**固化**：判断一段代码能不能翻译成 SQL，**必须读到最内层的实现**。中间那层是不是 PHP 方法不重要，重要的是它最终做了什么。

### 脚本的信号强度分类可能与具体标的不匹配

早盘那个 `morning_open_forecast.py` 按 `|NDX| < 0.5%` 判信号强度为「弱」，而今天 **NDX 只涨 0.21%、SOX 涨了 3.37%**。

**对光模块和存储链，SOX 才是更贴合的指数。** 今天的结果是 **SOX 那一侧对了**（中际旭创 +10.40%）。

**当时我的处理是对的**：把背离摆出来，**但不据此上调预测**——因为脚本的历史一致率是按 NDX 分档统计出来的，我没有 SOX 分档的历史数据，**换指数就等于换了一套没有回测支撑的判据**。

**固化**：发现脚本的判据与当下情形不匹配时，**可以指出，但不能私自换判据**——除非新判据也有回测支撑。

### 「涨多了该减仓」是方向判断，是被禁止的

写尾盘报告时我第一版想给中际旭创「减仓」，理由是「涨了 10% 了」。**这是错的**——「涨多了要跌」隐含方向预测，而 skill 明确禁止（收盘前方向预测经 117 个交易日回测为随机水平）。

**正确的做法**：报出「5 日波动率从 2.03% 被今天这根拉到 5.09%、预期跳空从 1.5% 涨到 2.4%」这个事实，给出「2.4% × 仓位 = 明早可能的波动金额」这个计算，**把决定交回给用户**。

**固化**：任何「因为涨/跌了多少，所以该买/卖」的推理都是方向判断。**只能报幅度、给计算，不能给方向。**

### 异动归因的时序要看清

花旗那条研报 14:29 才发，而股价从早盘就在涨。**如果不看时序，很容易把它当成全天涨幅的原因。**

**固化**：把某条消息当作某个行情的原因之前，**必须核对消息发布时刻与行情启动时刻的先后**。晚于行情的消息不是原因。
