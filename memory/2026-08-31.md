## 1. 今天获得的知识与技能

### 混合语言知识库的召回，出问题的地方和直觉相反

这是今天最有价值的一条，而且是实测出来的，不是推理出来的。

**现象**：CSRS 的知识库里有一篇文档，标题用简体中文写「大成建设：SAML 证书更新」，正文里保留了客户的日文原话「大成建設様/SAML証明書の更新」。同一个事实，中文提问答得出来，日语和英语提问答不出来（日语回「記載がありません」）。另一个用例更明显：问「大规模访问的报备阈值」，中文答 25000 人，日语答 8000 人/小时，英语也答 8000——三种语言召回到了不同的文档。

**我第一版解释是错的，被自己的实测推翻了。** 我先说是「字形对不上」：简体「大成建设」分词成 `['大成','建设']`，日文汉字「大成建設」分词成 `['大成','建','設']`，只共享一个词。这个分词差异是真的，但它解释不了现象——因为查库发现**那一段里两种写法都在**，日文原话就带着「大成建設」。

**真正的原因**（四步证据链，每步都是实测）：
1. 精确短语查库：含「大成建設」和「大成建设」的都命中同一段。所以字形解释不成立。
2. 中文整句提问时，这段关键词得分 29.41，排第 1。
3. 日语整句提问时，这段掉出前 5。前四名全是**日文写的其它文档**，得分 48–55。
4. **决定性验证**：把日语问题砍到只剩特征词 `大成建設 SAML証明書`，它立刻回到第 1（得分 30.62）。

**结论**：问题不是「一句话里混了几种语言」，恰恰相反——**混着写是帮忙的**。问题是库里有大量日文写的其它文档，用户用日语提**整句**问题时，「の・いつ・実施・推奨・ですか」这些日语常用词在日文文档里到处都是，每命中一次加一点分，累积起来把整篇日文文档抬到前面；而那篇中文文档只有一行日文原话，加不了几分。

**这条知识的可迁移形式**：关键词检索的排名是**累加**的，所以问句里的功能词（助词、疑问词）不是中性的——它们会系统性地偏向「整篇都是这个语言」的文档。一个只有一行目标语言的文档，永远竞争不过一整篇。

**对做法的影响**：要做的是让答案文档的主体语言和提问者的语言一致（所以 `summary_language` 这个能力有检索上的价值，不只是给人看着舒服）。不需要做的是担心一篇里混语言。可能还要做的是查询侧扩展（把问题翻成库里存在的各种语言分别查再融合），但那要动 CSRS 的检索链路。

**这条结论的边界我标清了**：验的是 ES 关键词检索这一条路，逐条看了排名。FUSION 还有向量、图、表几条路，向量那条我**没有单独测**。向量模型（qwen3-embedding-8b）是多语言的，理论上受语言影响小，但「同语种文档更相似」这个倾向大概率也存在。

### ES 的多语言索引不是配置缺失

顺便确认了 `csrs_chunks_*` 索引的 `text` 字段挂了三套分词器：`smartcn`（中文）、`text.ja`（kuromoji，日文形态分析）、`text.en`（英文词干），查询是 `multi_match` 同时打这三个字段（`csrs/stores/es_store.py:454-458`）。**所以这不是「忘了配日文分词器」这类问题**，配置是齐的，出问题的是打分机制本身。排查这类问题时不要先怀疑配置。

### docker compose 的一个坑：改 yaml 不重建容器

**配置文件在进程启动时读一次就进内存了。** mount 进容器的 yaml 改了内容，容器不重建的话进程还拿着旧配置。`docker compose up -d` 在镜像和容器定义都没变时**什么都不做**。

今天是这样发现的：8/27 就把 `C0AP1N8CH4Z` 的摘要语言改成日语了，但今早 09:01 那张卡片还是中文的。**定位的证据是抬头那个词**——「区间摘要」是代码按语言拼的、不是模型写的，所以它直接证明了生成时传进去的语言是 `zh`。再对时间：容器启动 08:40 UTC = 东京 17:40（今天下午我为别的改动做的 `--force-recreate`），而卡片是东京 09:01 发的——**发卡片的是上一个容器进程**。

**教训固化成规则**：只改 yaml、不改代码时，部署必须显式 `--force-recreate`。以后固定加这个参数。

### BEAVER 那把尺子：文本转 SQL 的五个瓶颈

BEAVER（arXiv 2409.02038）把「文本转 SQL」拆成五件必须分别做对的事，并且证明这五件事就是瓶颈：GPT-5.2 加最先进的智能体框架执行准确率 **10.8%**，把这五件事的标准答案直接告诉它变成 **30.1%**——三倍。

五个子任务：**多表检索**（该用哪几张表）、**连接键识别**、**列映射**、**领域知识抽取**、**查询分解**。

**为什么这对我重要**：它给了一把可以量我们 prove 系统的尺子。用它逐条对照读代码，得到的结论是——prove 把五个瓶颈里的**三个从结构上消掉了**：模型选的是指标不是表（`from` 已写死用哪几个实体）、join 路径在 `rbox.yaml` 里登记（16 条关系全是登记的）、列在 `mapping-registry` 的 `fields` 里逐列登记（29 个实体）。**模型根本没有机会选错表、连错键、映错列。**

这也解释了那篇 KG 基准为什么说「SQL 路线的错都是编造」——它们没有这三层，模型只能自己猜。

**这张对照表本身就是个有用的产出**：说明我们不是笼统地「用本体做了个语义层」，而是可以指着外部基准指认的瓶颈说消掉了哪几个。

### 评测题库可以形式化成本体，不是硬编码在代码里

data.world 那个 KG-LLM-Accuracy 基准的 GitHub 仓库**没有代码只有数据**（36 个文件 576 KB，一行执行代码都没有，评分流程跑在他们自己平台上）。但 `investigation/acme-benchmark.ttl` 那个文件很值钱，1137 行、44 道题 + 89 条参考查询，**它把题库本身建成了本体**：

```turtle
dwt:IQ_c340bd56...
    rdf:type       QandA:Inquiry ;
    QandA:expects  dwt:query-e610253b... , dwt:query-b4ca41e8... ;
    QandA:prompt   "Return all the policies and their policy holder by id" .
```

三样值得抄：**一道题可以有多条正确答案**（`expects` 指向多个参考查询，我们现在一题一个期望值）、**参考查询带语言标记**（SQL 和 SPARQL 并存在同一个题库里）、**题库是数据不是代码**（我们现在硬编码在 Python 字典里）。第一条最直接——同一个问题有多种正确写法这件事，我们的评测现在没有落点。

### 评分只比执行结果，还有三条豁免规则值得抄

| 不算错 | 算错 |
|---|---|
| 列的顺序不同 | 少了一列 |
| 列名不同 | **返回内部主键而不是业务编号** |
| 行的顺序不同 | —— |

**第二条正好是我们踩过的坑**（「标识符必须参与数字对账，学号不许从 gate 豁免」）。他们把它归类成「部分正确」的一种形态，还给了名字。

### 一道题跑多次，分数从布尔改成百分比

**理由是大模型不确定**：同一个问题这次生成的查询和下次可能不一样，所以一道题的分数不是 0 或 1，是「跑对的次数 ÷ 总次数」。

我们的十问验收和课程域评测都是**跑一次定生死**，这意味着**看不到「这道题是稳定对，还是碰巧对」**。改起来很便宜：加一个重复次数参数，结果从布尔改成分数。

### 失败要分类，而且两条路线的分类不一样

| 路线 | 失败类型 |
|---|---|
| 直接问 SQL | 编列名、编取值、编表连接 |
| 走知识图谱 | 路径接错、方向搞反 |

我们现在只记「对不对」不记「怎么错的」。加一层归类能看出问题出在路由、参数抽取、还是 DSL 编译。

### CSRS 的记忆模块和 roleplay 的记忆池，是两种不同的东西

这个区分是今天最重要的判断依据，值得单独记住：

| | CSRS 的 CE memory | roleplay 的 InfoPool |
|---|---|---|
| 是关于什么的 | 真实用户的长期事实 | 一场虚构对话的短期上下文 |
| 生命周期 | 数月，跨会话累积 | 一场练习，结束即弃 |
| 规模 | 上百上千条 | **几十条，每条 ≤20 字** |
| 真实性 | 真实 | **虚构或未核实** |
| 谁会管理它 | 用户自己、运营 | **没有人** |
| 提取用几次 LLM | 1 + N（1 次提候选 + 每候选 1 次 decide） | **1 次** |
| 去重怎么做 | 每候选一次向量检索 + 一次 LLM 判定 | 代码：字符 bigram Jaccard ≥ 0.7，同分类内 |
| 落在哪 | PG + Milvus + Neo4j | ADK session state → MySQL `adk` 库 |
| 读取延迟 | `/ce/assemble` 实测 p50 2.7s | 进程内字符串拼接，零延迟 |

**由这条差异推出的规则**：凡是只服务于「长期记忆管理」的能力（显著性衰减、相似记忆合并、跨会话聚合、记忆管理后台），在 roleplay 场景里都用不上，有几项用了反而有害。

### Roleplay 的 InfoPool 去重是三层，两种判据

之前我几轮里一会儿说「代码 Jaccard」一会儿说「LLM 自己挡」，其实是三层串起来的：

| 层 | 谁做 | 在哪 | 判据 |
|---|---|---|---|
| 一 | **LLM** | `roleplay_info_extraction_system_prompt` 第 33-36 行 | 语义相同就跳过，「犹豫时默认为重复」 |
| 二 | 代码 | `info_pool.go:105` → `:86` | 字符 bigram Jaccard ≥ 0.7，**同 category 内** |
| 三 | 代码 | `info_pool.go:154` | 同阈值，输出时再兜一次 |

**各自的盲区**：LLM 层能抓「HbA1c 降 1.8%」和「糖化血红蛋白下降 1.8 个点」是同一条，代码层抓不到（字符 bigram 几乎不重叠）；代码层只比同 category，而**category 名是 LLM 自己起的**，所以 prompt 里还得再写一条「优先复用已有分类名」来兜。这一整套是「自己造记忆系统」的产物，也是最脆的部分。

### ADK 的 session state 落 MySQL，但有三条丢失路径

落库链路：`persistInfoPool`（`coordinator.go:914`）→ 构造 Event，`StateDelta = {info_pool: JSON}` → `AppendEvent`（`:947`）→ `applyEvent`（`service.go:353`）→ MySQL `adk` 库的 sessions 表 State 列 + events 表。**四站点全部配 MySQL**，代码支持 `storage: memory` 但线上没用。

**所以「InfoPool 零外部依赖」是错的**（我前一轮说过，今天更正了）。但仍有三条会丢：

1. **模型调用失败就丢那一轮**——`coordinator.go:872-877`，一行错误日志然后 `return`，没有重试、没有补偿、没有标记。没有任何机制事后知道「第 7 轮的提取丢了」。
2. **落库撞乐观锁就丢**——`applyEvent` 有一道 stale check（`service.go:369-378`，`storageUpdateTime > sessionUpdateTime` 就报错）。提取是异步跑的，拿的是这一轮开始时的 session 快照；跑得慢、下一轮已经写过 session，`update_time` 就变新了，`AppendEvent` 直接失败，走同一条无重试的 `return`。**轮次越快、提取越慢，越容易发生。**
3. **进程被 kill 就丢**——代码显式剥掉了 context 的 cancel 和 deadline（`coordinator.go:856` 的 `WithoutCancel`），说明有人踩过「请求结束就被砍」的坑；但滚动发布时正在飞的提取没有保护。

**准确的表述**：不是「记忆不持久」，是**「持久化的是成功的那些，失败的那些无痕消失」**。

第 2 条的发生率**没有实测**，但日志里有 `info_extraction_persist_failed` 这个 key（`coordinator.go:901`），按 practice_id 聚合就能知道。这条值得测——如果发生率不低，那「客户失忆」的实际原因可能不是窗口滑走，而是提取压根没存进去。

### 「走到某个环节」这个概念，在 roleplay 当前实现里没有承载物

三个角度都指向同一结论：

| 角度 | 现状 |
|---|---|
| 状态字段 | LLM 输出 `current_stage_id`，`applyStageInfoUpdateFromRaw`（`state_manager.go:169-190`）**非空就直接赋值，不校验它是否在 `stage_details` 里**。可以填剧本里不存在的 `_3` |
| 客户表演 | Customer 在 value_demonstration 分支拿到的是 `FormatConcernStatus(全部关注点)`（`customer.go:163-170`），6 条一起给。**行为上不存在「现在只关心实例 1 那 3 条」** |
| 评分 | `RolePlayOverallAnalysis` 按 section 循环起 activity（`overall_analysis_service.go:137`），**每个 section 都会被评分，不管对话有没有走到它** |

**所以可以说每个实例都走到了，也可以说一个都没走到。** 而且编号基准本身没对齐过：剧本生成 prompt 举的例子是「第二个信息传递环节就是 `value_demonstration_1`」（听着 0 起头），代码初始化写死 `"opening_1"`（1 起头）。

**断点比这还靠前一步**：`generate_dialog_flow` 的输入里**有** `section_id`（值形如 `value_demonstration_8801`），但输出结构只保留三个字段（`:610-615`），`section_id` 在这一步被丢掉了。另一边 `generate_drama` 生成的关注点 `C01`-`C06` 是跨 section 拍平的、不带实例归属。**从 stage 实例回指 section 的钥匙根本不存在。**

### 判定和消费是两个角色，不能混在一句话里说

| | 谁 | 干什么 |
|---|---|---|
| **判定** | StageEvaluator | 决定这一轮是哪个环节、哪个实例，写进 `CurrentStageType` / `CurrentStageID` |
| **消费** | CustomerAgent | 读这两个字段，决定用哪段行为准则、往 prompt 里填哪些状态 |

一句话：**StageEvaluator 判出了实例 id，Customer 不读它。** 「走到实例 1」要有意义，必须体现在客户的表演上，而消费端拿的是全量关注点。

### 探寻环节比信息传递更没救：连可以补归属的东西都没有

剧本生成时两类内容各有来源门槛：`concernPoints` 只取信息传递类（`IsInformationTransferOrSimilarSection()` = Type 3/8/9，`entity.go:647-649`）、`keyObjections` 只取异议处理类（Type 4/10，`:651-653`）。**探寻是 Type=2，两个门槛都不满足**——运行时状态里完全没有探寻的痕迹。

所以 value_demonstration 的实例迁移「补一个字段就能判」，探寻**补数据也补不出来**，得从零设计一套「探寻进度」状态机。工作量差一个量级：那是接线，这是新建机制。

**能代码化的只有探寻的边界**：出现第一个 in-depth 关注点就说明离开探寻了（能）；「离开 opening 之后、还没有 in-depth 关注点」大概率是探寻（半能）；「问了有深度的、与你的情况很相关的问题」这个验收标准（不能，纯语义）。

### 两级评分合并：把已经做过的判断顺手输出

「两级」指**打分**和**明细**。现在一个信息传递环节为它们各调一次模型。**关键在于逐条评估内部本来就在逐条判语义点**——因为覆盖率类评分要点的分数就是「讲了的条数 ÷ 总条数 × 100」，要算这个数必须先把每条判过一遍，**只是没输出**。

所以合并 = 在逐条评估的输出里加一个语义点数组，删掉第二次调用。**不是新增工作量。**

顺带修掉一个已知问题：现在两次调用对「讲了」的判据不一样（明细那边「表达模糊」算没讲，逐条评估那边「意思对得上就算讲了」），所以会出现**分数按 6/7 给了 86 分、明细只勾了 5 个**的自相矛盾报告。合并后是同一次判断，物理上不可能矛盾。

**和 CSRS 召回不冲突，动的是不同维度**：合并减少**调用次数**，召回减少**每次调用的输入量**。四种组合的账（F=4000 整段转写，R=800 召回片段）：

| 组合 | token | 相比现状 | 负向判定 |
|---|---|---|---|
| 现状 4F | 16,000 | — | 可靠 |
| 只做合并 3F | 12,000 | 1.33 倍 | 可靠 |
| 只做 B（纯召回）2R+2F | 9,600 | 1.67 倍 | **不可靠** |
| 只做 C（召回+兜底）2R+3F | 13,600 | 1.18 倍 | 可靠 |
| 合并 + B  2R+1F | **5,600** | **2.86 倍** | 不可靠 |
| 合并 + C  2R+2F | 9,600 | 1.67 倍 | 可靠 |

**顺序有讲究**：先做合并（零新增依赖），基数变 12,000 之后再上 C 只剩 1.25 倍边际——**这个量级不足以支撑引入一个外部依赖**。所以合并做完，决策收敛成一个问题：能不能接受 B 的漏检风险。

### 日内查表手册的列映射：后四列是 up 1/2/3/5

这条是今天踩的坑，记下来防止再犯。`查表手册.md` 表 A 每行是 `趋势 | 振幅档 | n | 4 个跌幅列 | 4 个收高列`，我一开始把后四列当成 up 3/5/7/10，得出 33–41pp 的巨大偏差。**用同表已知的「下跌 4~6%」行做校准**（文档 75.3/53.6/36.1/16.6 对上实测 up 1/2/3/5 = 75.4/53.6/36.4/16.5，四列全吻合）才发现是 **up 1/2/3/5**。

### 审复用型方案，必须逐条问「这个能力我用得上吗」

**今天最大的一条，而且是用户直接纠正的。** 我把 CSRS 记忆模块的能力清单**直接抄成了收益清单**，中间少了一步。用户逐条驳回五项：

|---|---|
| 提取 + 向量召回 + 判定 | **用不上**。判重的库只有几十条、每条 ≤20 字，全量对照更简单也更准 |
| 召回相似项后单独判定 | **用不上**。而且比现在「全量喂一次判完」调用更多更绕 |
| 显著性衰减 + 相似记忆合并 | **用不上，而且有害**。练习结束整批丢弃没有衰减的时间尺度；合并的作用域是这个人名下的记忆，**会跨练习混** |
| 增删改查接口 + 变更痕迹表 | **用不上，而且变更痕迹表不存在**（只在 `feature/console-memory-admin` 分支，不在 master）。**我错了两层** |
| 跨会话聚合是原生能力 | **必须禁止**。我把一个要禁止的能力列成了好处，自相矛盾 |

**结论跟着从「可以做」翻成「不建议做」。** 真正用得上的只有 1 条（LLM 提取），第 9 条（断点续跑）可被自己加个重试抹平。

**固化成规则**：看这类方案先要一张「能力 × 用不用得上」的表，再谈收益。**「对方有」不等于「我能得到」。**

### 成本倍数要盯前提，不盯结论

评估侧那个降本数字今天被推翻**三次**，从 4.8 倍一路落到 1.25 倍。三次原因一样：**不是算错，是前提被换掉了**——调用次数、改造范围、两次调用能不能合并。

而且最省的做法根本不是引外部依赖，是把现有两次重叠的调用合成一次。**便宜的答案常常在自己这边：先看能不能少做一件事，再看要不要多接一个系统。**

### 「机制建全了但没接线」是这几个项目反复出现的形状

今天又撞到两处：CSRS 的 `SESSION` namespace（定义了、存储支持了、生产代码零消费者）、roleplay 的 stage 实例 id（判出来了、Customer 不读）。之前还有评分的自定义分级字段、客户台词里的模式标签。

**单看每一层都合理，合起来是空转。** 用户的做法：**review 新增的状态字段和输出字段时直接问一句「谁读它、在哪一行」，答不出来就当场定接上还是不加。**

### 「LLM 用什么判」和「答案由什么决定」是两件事

我一直在犯这类错：环节判定的标准是语义的，我就断定不能靠状态查表。**其实对话往前走状态也跟着走，状态是对话进度的一块刻度盘——判据是语义的，答案却常常被状态锁死。** 少问这一句，方向会整个反过来。

### 读代码前先确认自己读的是哪个分支

我上一轮读的是 `feature/slack-daily-summary`，那上面 `csrs/ce/` 停在 **2026-07-07**——是旧的。真正的记忆改动在 `origin/master`（到 08-27）和 `origin/feature/console-memory-admin`（到 08-31）。**因此有三条结论要更正。**

固化：跨仓库读代码时先 `git branch --show-current` + `git log -1 --date=short` 看这个模块的最近提交日期，不要默认当前分支是最新的。

### 实测能推翻自己上一轮的解释，要主动去撞

「日语召回不准是因为字形对不上」这个解释**听起来非常合理**（而且分词差异确实存在），但一查库就发现那一段里两种写法都在。**如果不去查，这个错误结论会直接进方案。**

固化：给出机制解释之后，问一句「这个解释有没有一个能直接查的前提」，有就去查。今天的前提是「库里那段没有日文写法」，一条精确短语查询就否掉了。

### 跨文档比对数字前，先用同表已知行校准列映射

日内查表手册那次，我把后四列当成 up 3/5/7/10，得出 33–41pp 的偏差就差点当成结论报出去。**用同表「下跌 4~6%」行校准**才发现是 up 1/2/3/5。

**判据**：如果偏差量级大到不像「文档过期」（几十 pp vs 几 pp），先怀疑自己的列映射，不要怀疑数据。

### 只改配置文件不改代码时，部署必须 `--force-recreate`

见第 1 节。**定位这个 bug 的关键是找到一个「只可能由代码按语言拼出来」的特征串**（抬头「区间摘要」），它直接证明了传进去的语言是 `zh`。**这个技巧可复用：想知道运行中的进程用的是哪份配置，找一个由配置决定、且不经过模型的输出特征。**

### prompt 里的第一人称会指向错的人——今天修了一个

用户指出 `/ycui-gen-work-summary` 生成的总结**从 agent 的角度写，不是从使用者的角度**。

**根子不是「第一人称」这个词没写清楚，是代词指的人和素材里的人不是同一个。** 文件里写「从**我**自己的角度写」，语法上「我」就是用户；但素材在会话记录里，而记录里动手的是 AI——代码是 AI 读的、脚本是 AI 跑的。**代词说的是用户，证据说的是 AI**，这个矛盾一出现句子就顺着素材滑过去。还有一层：「领悟到了什么新的认知」这种话，AI 没有跨会话的持续学习，以自己的身份写必然是编的。

**所以修法是两条，光说清「我 = 使用者」不够**：① 点名到人（`「我」指使用者 cuiyang，不是你（AI）`），② **给出素材转换规则**（「你查到了 X」→「我今天弄清楚了 X」；只有 AI 才会有的经历——调了哪个工具、跑了几轮、读了哪个文件第几行——一律不写）。

**参照物是 `ycui-daily-memory` 那个 skill**：它直接写「供未来 AI Agent 了解 **cuiyang** 的上下文」，点名到人、没用代词，所以没这个毛病。**以后写 prompt 类配置，涉及视角的地方一律点名，不用代词。**

**注**：这个修改**效果还没验证**——prompt 类改动只能在真实调用中看。下次跑如果输出里还出现「我读了 xxx.py 第 N 行」这类只有 AI 才有的经历，说明「素材转换」这段还不够硬，要加禁用句式清单。

### 命令目录里有 3 对完全重复的文件，是改名迁移留下的

`cmp` 逐字节确认相同。**后果是两个入口指向同一份内容，改了一边另一边不会跟着变**——这就是会各自漂移的副本。**待用户决定是否删除无前缀的旧副本。**

### 提交到公开仓库前，密钥核验要有明确的三项

my_scripts 是公开仓库，`loop_tasks.json` 有 `notify.slack_webhook_url` 字段。今天提交那两个 `.bak` 前核验：`hooks.slack.com` 出现 **0 次**、`slack_webhook_url` 的值是 `''`、`token|secret|password|api_key` 命中 **0 次**。**三项都干净才提交。**

### 跑完会覆盖本地文件的同步脚本，要交叉校验自己的改动还在

`backup-claude.sh` 是 backup → commit → pull → **restore** → push，restore 会把远端内容写回 `~/.claude/`。我半小时前改的 `ycui-gen-work-summary.md` 理论上可能被 B 机器的旧版本冲掉。**查了字节数和特征串确认没被覆盖。** 以后在 `~/.claude/` 下改完东西又跑 sync，都要补这一步。

### 分析类结论要主动说清边界

今天两处做对了：混合语言召回那条明确写「验的是 ES 关键词检索这一条路，向量那条没有单独测」；卡片竞态那条明确写「顺序点击的行为从代码逻辑确认，几乎同时点击没有实测」。**没测的就说没测，不要让读的人以为整条链路都验过。**
