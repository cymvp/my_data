## 1. 今天获得的知识与技能

### 提醒逻辑写反了：越彻底没隔离的反而越安静

原来的判据是「**承诺了**隔离，但这个通道给不了 → 发提醒」。**这个方向是反的**——压根没承诺隔离的指标反而一声不吭。

**改成只问一件事：本次编译出的查询里有没有企业条件。** 理由是：原因是通道不支持还是没登记，**那是我们的内部区分，不该由用户承担**。

另外加了一档：**只有一部分子查询有企业条件时单独说明**（比率类的分子分母口径不一致、数值偏低），**那种情况比完全没有隔离更需要提示**——完全没隔离至少是一致的，半隔离会给出一个既不是全量也不是本企业的数。

### 隔离注入够不着的两条编译路径

「分子隔离、分母不隔离」的根子不是声明缺失，**是 `_compile_set_union` 和 `_scope_sql` 都自己拼 SQL、从不走 `_compile_select`——注入按结构就够不着这两条路径。**

**补的时候还发现一个差点引入的连带隐患**：这两条路径的 SQL 原先不带 `ctx.joins`，而桥接注入会往里加一条 LEFT JOIN——不补的话生成的 SQL 会**引用一个不存在的别名**。

**钉住它的测试机械扫全注册表、不逐条列指标**：主查询隔离了，每一个子查询就必须也隔离。**这样下一条走新编译路径的声明也会被抓到。**

### 今天最重要的发现：两道守卫抓不到催生它们的那个病例

**C11：加载期校验和运行期提醒对 compose 半隔离都是盲的。**

构造一条半隔离声明（分子走有隔离的实体、分母走无隔离承诺的实体）：

```
加载期 isolation_consistency_errors  →  ★ 没被抓到
运行期 isolation_gap_note            →  ★ 判为「隔离到位」，不发提醒
```

**根因在判据的形状**，两处一样：

```python
parts = [主 SQL] + [各 union 输入] + [各 scope]
got   = ["enterprise_id" in q for q in parts]
```

而 **compose 的多个输入被编译成一条扁平 SQL 字符串**，既不进 `plan.unions` 也不进 `plan.scopes`：

```sql
SELECT a.n / b.m FROM
  (SELECT COUNT(*) FROM dwd_course_completion_df WHERE course_id=1 AND enterprise_id=1) a,  ← 有
  (SELECT COUNT(*) FROM dim_exam_setting_kv     WHERE exam_id=1)                        b   ← 无
```

于是 `parts` 只有一个元素、`"enterprise_id" in q` 为真、`any(got) and not all(got)` 不成立、**判定通过**。

**要命的地方**：`course_learning_task_user_rate` 和 `session_complete_rate` **恰恰都是 compose**。也就是说，**如果这道校验在修复之前就存在，它一条都抓不到——它抓不到催生它的那两个病例。** 「全注册表 48 条通过」不等于没有半隔离，**只等于没有 union/scope 形态的半隔离**。

**修法不是补一个 compose 分支**（那会变成「每加一种编译形态就补一次判据」，下一个新形态又漏）。**正确做法：让 `_compile_select` 每编译出一个 SELECT 层就往 plan 上记一条「这一层带没带企业条件」，判据改成读这个列表。** 编译器自己最清楚它生成了几层，不必让外面的人从字符串里猜——**这样 compose / union / scope / from_query 一次覆盖，将来加新形态也不用回来改判据。**

**这条的通用教训：当一个校验的判据是「从拼好的产物里 grep 特征串」时，它必然漏掉那些把多个部分压平成一个产物的形态。要让生成方在生成时记账，而不是让检查方从结果里猜。**

### 一次分歧的完整过程：一个理由成立、一个实测不成立

**实现方否掉了评审方「加进加载期校验」的建议，给了两个理由：**

**理由一（按实体声明查会误报）—— 成立，评审方撤回原提法。** `session_complete_rate` 的 `enroll_student` 没有直接承诺隔离，**但它的隔离是经 scope 传递的**（那一支带 `course_open_enroll` scope，报名配置维表登记了课程桥接，同实例下 scope 被内联进并集输入的 SQL）。**声明层的「承诺」有多条传递路径（直接字段、桥接、scope 内联），按声明查会把合法的传递判成不一致。**

**理由二（加载期用占位参数，注入必然成立、校验永远通过）—— 实测不成立，实现方自己撤回。** 用加载期真正用的那套占位参数 `_DummyParams(True)` 在数仓通道逐条编译：

```
course_complete_user_total          ['有']
session_complete_rate               ['有','有','有']   ← scope 传递被正确识别
exam_pass_score                     ['★无']
mentor_task_overall_complete_rate   ['★无']
```

**占位参数让注入在「已经接线的地方」成立，它不会让企业条件出现在「没接线的地方」。**

**最终形态：判编译产物、位置在加载期。而且理由换了。**

**新理由比原来的强，值得记住**：不是「测试查不出来」（测试机械扫全注册表、判据也对），**而是「测试守不住这个项目自己设计的工作流」**——项目原则是「改本体不改代码」，加一条指标只动 YAML；`load_ontology` 按 mtime 自动重载、演示站改完 YAML 就生效。**于是「加指标 → 演示站能用」这条路上 pytest 一次都不必跑。** 而这个项目所有其它横切约束（引用完整性、`grain_kind`、投影配伍、时效必填、YAML 布尔键）**全在加载期，唯独租户隔离例外——在安全属性上单独开口子，方向是反的。**

**实现方对分歧的处理方式值得学**：「如果仍判断不该加，我接受，但请把理由换成『代价大于收益』，**不要写成『加载期查不出来』——后者与实测不符**。」

### YAML 布尔键：文档里写过的坑还是会撞

`on:` / `off:` / `yes:` / `no:` **会被 YAML 当成布尔字面量**，于是声明看起来完全正常、读的时候悄悄拿到 `None`。

**已做成加载期校验，判据是「键的类型是不是布尔」，不是「有没有写 on 这个词」**——后者是关键词表，写 `off` 一样中招、枚举不完。配了自检：用那个错写法构造一次，校验必须抓住，否则它只是摆设。

**这个坑 CLAUDE.md 里写着，实现方还是撞了。文档里的坑靠人记，记不住是常态——所以要做成机制。**

### 测试的排除规则不能用「被测对象和被排除对象共用的属性」

原来的 JOIN 计数测试**按表名排除**隔离用的维表 join。评审方指出这很脆：**排除规则用的属性（表名）被测对象和被排除对象共用**——哪天有个 attach 合法地 join `dim_course` 去取课程标题，那次会被一并吃掉，**测试照样绿而要保护的性质已经坏了**。

**修法：`Plan.isolation_joins`——编译器把桥接时自己加的 join 别名记进 plan，测试按别名精确排除。**

**这个形状实现方之前在 `_allowance` 上栽过一次，这次是评审方指出来的。**

### 兜底异常的语义要分清：能力问题 vs 授权问题

四处 `except` 兜底原本会把 `_IsolationError` 一并吞掉。**判据一句话说清**：

> 那四处的 `except` 是为「这条指标在这个通道跑不了」准备的，**那是能力问题**；`_IsolationError` 是**授权问题**，两者语义相反，不该共用一个兜底。

**做法是四处各加一行 `except _IsolationError: raise` 前置，改动面就是四行。**

**配的测试要桩在 `_resolve_derived_params` 那条路上**——它是四条里唯一在主循环之前跑、失败后主循环仍会继续的，**最容易掩盖问题**。

### `except CompileError: continue` 是个已经骗过人一次的盲区

加载期隔离校验里那句 `except CompileError: continue` 意味着：**在数仓上编译不出来的指标会整条跳过隔离检查**。而「编不出来」的常见原因（缺绑定、缺字段登记）**恰恰与「没接隔离」高度相关——最可能漏检的正是最可能有问题的那批。**

**它已经骗过一次**：实现方配的「构造半隔离声明、校验必须抓住」自检第一次跑是红的，**不是校验失效，是构造用的实体（`mentor_complete`）没有 `learner` 字段、编译失败被这个 `continue` 吞掉了**。换成 `enroll_student`（唯一有 learner 却无隔离承诺的实体）才真正构造出病例。

**建议不要静默 `continue`，改成记一条「本条未参与隔离一致性检查，原因是数仓侧编译失败：<原因>」——不拒绝启动，但让盲区可见。**

### 判断用的编译产物和执行用的编译产物是两套，会漂移

`isolation_gap_note` 判的是一次**为判断而单独编译**出来的 SQL，不是真正执行的那条。

**评审方实测：两组参数逐条比对，判定不一致的条数是 0，所以目前没有实际漂移。** 代价也可以忽略（48 条各多编译一次合计 **1 毫秒**）。

**但形状确实是同一个**：今天两者一致，不代表明天一致——**只要将来有哪个条件的存废依赖某个定位参数，而隔离恰好挂在那个条件上，就会出现「提醒说隔离到位、实际执行的那条没有」。**

**不用测也能根除：改成判已经执行的那条 SQL。** `run_metric` 的返回值就是执行的 SQL，`queries[m["id"]] = sql` 已经存着，调用点就在同一个循环里、`sql` 在作用域内。

### market_pulse 的四块内容与它的边界

盘中判断「是我一只票在跌，还是整个市场在跌」的工具，今天用户问了怎么用。

**四块内容**：

- **【速度】** 每个窗口（15 秒 / 1 分钟 / 5 分钟）里涨跌幅变化了多少个百分点。**三列一起看能分出加速还是减速——三列都是负且逐列放大就是在持续下跌。**
- **【宽度】** 池内多少涨多少跌。**这是判定「独跌还是同跌」的直接依据。**
- **【相对强弱】** 持仓票 vs 池子中位数，以及池内排名。**超额单独看没意义，配上排名才知道强弱。**
- **【判定】** 独跌 / 同跌 / 同涨 / 分化。**只数人头，不设任何需要标定的阈值。**

**三条必须说清的边界**：不预测方向（「同跌」告诉你这是板块层面的事，但不回答会不会继续跌）；只覆盖那 38 只科技股（长鑫科技进不了宽度和排名的分母，云南锗业、高争民爆完全不在里面）；**盘中要看得先开悬浮窗**——速度需要历史快照，**命令行单跑一次拿不到，悬浮窗才是采集的那一路、命令行只是读它落的盘**。

**状态提示的读法**：`不可用（已采集 N 秒，需 300 秒）` 是刚启动的正常状态；`—`（长鑫那行）是池外票没有速度、永远这样；`样本不足` 是有效票少于 20 只、不出判定；**收盘后不采样**，所以晚上跑只会看到「不可用」。

**连带 CLAUDE.md 那条硬纪律「改完必须跑在线评测打 apolo 真数据」会失去对象**——apolo 走的就是分散原表通道。**这条纪律要跟着改，但在线上数仓可用之前不能简单删掉**，否则没有任何一条路能打到全量真实数据。评审方的建议是：按目标形态执行（新功能只在数仓承诺、隔离只在数仓验证），**但保留 apolo 评测作为「数据真实性」的验证手段，直到线上数仓可用**。**用户尚未答复，CLAUDE.md 那条暂不改。**

**裁定 1 的后果**：「不用管」理解为「不定性、不补数、隔离照常按课程归属做」，这样积分类指标在数仓上会把那批无归属行整批过滤掉、**数字变小且证据里看不见**。评审方建议在积分类指标的 caveats 里写一句实测口径（本次结果不含无企业归属的记录，**线上该表 31.3% 的行属于这一类**）——**这一句要不要加需要用户点头，因为改 caveats 也是改本体。**

### prove 的交付状态必须说准

**「设计已完成、验证环境可验证、生产路径仍然零隔离」——不是「租户隔离已落地」。**

今天真实在跑的是 apolo 分散原表通道，它的 `isolates` 是 `False`，**隔离一条都不生效**。

**生产上现在的改善是从「静默泄漏」变成「明示无隔离」——是实质进展，但不是隔离本身。** 这句已放进勘探报告（`docs/04-data/shared/enterprise-isolation-survey.md`）最顶部、做成引用块，第十一到十三节记了这一轮的三处遗漏。

**连带一条矛盾也写在同一块里**：隔离按设计碰不到 apolo，所以它的验证不能叫「打 apolo 真数据」。

## 4. 经验与教训

### 用户今天做的纠正

**「cd ~/projects/my_scripts && python3 market_pulse.py 这个程序应该是持续运行不停刷新的，而不是一次性的」** —— 说得对。**这是当初设计时的取舍，现在看是取窄了**：当时给过四个交付形态选项，用户选的是「挂到现有悬浮窗」，所以命令行做成了单次读盘。**结果是悬浮窗那一行太短放不下速度表，而完整面板又不会自己刷新，两头都差一点。** 要补 `--watch` 模式（每 15 秒原地重绘）。

**「我有好几只持仓票，你是看的哪一只的排名，算成第 38 名？」** —— 需要说清「排名的分母是那 38 只科技股，每一行就是一只持仓票」，而不是把多只票混成一个数。

**「我不需要你显示我的股票的排名。你只用给出池子里 38 只股票的平均涨跌幅和涨跌个数即可。」** —— 明确了他要的是**市场宽度本身**，不是自己票的相对位置。

### 我今天犯的错（prove 那条线）

**三个错都是同一类：做了一半就以为做完了。**

1. **漏登记 `assignment`**——而且自己的勘探报告里明明写着它有企业列 ✅
2. **注入只覆盖了主查询路径**，并集和 scope 两条路完全够不着
3. **`_course_of_exam` 只改了一处**——同名函数在 `poc/session.py` 和 `poc/chain.py` 各有一个

**前两个是评审方查出来的，第三个是端到端跑真实数据时炸出来的——单测和评审都没抓到，因为它在一条要真实数据才走到的路径上。**

**第三个直接违反了 CLAUDE.md 里那条「代码溯源时穷举所有调用方，不要看到一个路径就下结论」。** 已在 `poc/chain.py` 那个函数的 docstring 里写了指向和教训。

**另外两次「凭印象说」**：说「占位参数下注入必然成立」是凭对 `_DummyParams` 的印象、没跑；写测试时撞到 `_resolve_derived_params` 的签名不对（它收的是 `metric_defs: list` 和 `onto`，不是单条指标和 notes），**说明引用这个函数时也是凭印象——第二次犯同类错**。

**还有一次撞了文档里写过的坑**：YAML 布尔键（`on:` 被当成 `True`）在 CLAUDE.md 里写着，还是撞了。**结论：文档里的坑靠人记，记不住是常态，要做成加载期机制。**

### 今天有效的做法

**两个会话对打、互相推翻，而且都接受被推翻。** 评审方指出实现方三处遗漏；实现方否掉评审方一条建议并给两个理由；评审方复核后确认理由一成立、**自己撤回原提法**，同时实测证明理由二不成立、**实现方撤回理由二**；最后评审方**换了一个更强的理由**（测试守不住项目自己的工作流）坚持原位置。**四次撤回，每一次都是被对方的数据推翻的。**

**分歧处理的措辞值得学**：「如果仍判断不该加，我接受，**但请把理由换成『代价大于收益』，不要写成『加载期查不出来』——后者与实测不符**。」**接受结论、但不接受错的理由。**

**攻自己刚加的守卫。** 实现方加完两道隔离守卫，评审方立刻构造一条 compose 半隔离去攻，**结果发现它们抓不到催生自己的那个病例**。**新加的保护要用「催生它的那个原始病例」去验，而不是用一个随手构造的例子。**

**自检救了一次。** 「构造半隔离声明、校验必须抓住」这条自检第一次跑是红的——**不是校验失效，是构造用的实体编译失败、被 `except CompileError: continue` 吞掉了**。**如果没配这条自检，会以为校验生效了。**

**让生成方记账，而不是让检查方从产物里 grep。** 这是今天最通用的一条：`Plan.isolation_joins` 和「每编译一层记一条」都是这个思路。**判据一旦依赖「从拼好的字符串里找特征串」，就必然漏掉那些把多部分压平成一个产物的形态。**

**测试的排除规则不能用「被测对象和被排除对象共用的属性」。** 按表名排除隔离 join，哪天有个合法的 attach 也 join 同一张维表就会被一并吃掉，**测试照样绿而要保护的性质已经坏了**。

**交付状态要用「改善」和「解决」两个词分开说。** 「从静默泄漏变成明示无隔离——是实质进展，但不是隔离本身」比「租户隔离已落地」准确得多，**而后者会让人以为生产上已经安全了**。
