## 1. 今天获得的知识与技能

### 评测方法论（今天信息密度最高的一块，来自 LL 拆书 eval）

**「可溯源性」不等于「忠实性」，这是今天最贵的一个区分。** 原判据是「知识点内容能否被召回的证据完全推导出，且推得出的部分必须摘出支持它的英文原句」。review 方指出这在测**能不能找到出处原句**，而拆书这个动作本身就是压缩加概括——一条 289 字的中文知识点把原书整章内容归纳成五步框架，它本来就不该有对应的单句原文。按这个判据，**概括得越好的知识点越容易被判成幻觉**，幻觉率会系统性偏高。修法是把判定拆成两条独立的轴：「和书矛盾吗」（这才是幻觉）和「书里哪段支持它」（这是引用质量），三档改成「书里明确支持 / 书里没提但不冲突 / 和书矛盾」。

**判官自己也会判错，所以要先考判官。** 两种考题缺一不可：
- **假知识点**（故意编的，已知答案是「有问题」）量的是**漏判率**
- **真知识点**（确定忠于原书的，已知答案是「没问题」）量的是**冤枉率**

只出假知识点等于只测安检员漏不漏违禁品——一个见谁都拦的安检员漏检率同样是 0，但完全不能用。而报告的主结论就是「26 条里有几条是编的」，**判官冤枉好人会直接把这个数顶高**。用户今天明确要求不要用「正样本/负样本/头条」这类黑话，换成上面这种说法。

**造「真知识点」考题的正确做法：反着造。** 从书里挑一段连续原文，让模型照着这段归纳成知识点——「它忠于原书」由构造本身保证，不需要任何人去确认，绕开了「不做人工标注」的约束。关键是**出题模型要和判卷模型不同家族**（用 Sonnet 5 出题、gpt-5.2 判卷）。

**造考题时三个会让考题失效的坑（都实际踩到了）：**
1. **考题比真题长一倍就废了。** 第一版对照组中位 277 字、真实产物中位 142 字。判官读一条明显更长更密的文本，和读短条目判起来不是一回事，考出来的数代表不了真题。根因是指令写成「把这 3000 词归纳一下」，改成「从这段里挑一个最重要的概念写透」才落回真实区间。
2. **风格会露馅。** 不给真实条目当范例，模型造出来的标题是一句话式的，真实产物是短名词式的，判官可能靠文风认出考题而不是靠内容判断。
3. **假知识点可能造成了真的。** 有一条要求「去掉前提、把有条件说法夸大成普适规律」，模型理解反了往相反方向改、把话说得更保守——**这条其实比原条目更忠实**，混进去会凭空拉低判官成绩。所以造完必须逐条审计扰动是否真落地。

**最难的一类假知识点是「说得对，但书里没这么说」。** 拿真实存在但不在这本书里的框架（NVC 非暴力沟通四步、SBI、乔哈里窗、Thomas-Kilmann、积极倾听 3A）冒充，模拟拆书最真实的偷懒方式：内容不够就拿自己的领域常识去补。判官自己也懂沟通学，看到这些很容易觉得「对啊」就放过。**必须按类型分开报检出率**，合并成一个数会把最在意的那一类的退化平均掉。

**「token 预算装得下」不等于「会被召回到」。** 这是今天被纠正两次的同一个错。算「top_k=30 × 每块 440 词 = 13,200 词 ≥ 目标章 7,103 词，所以证据够」——这是**容量论证，不是召回论证**。top_k=30 拿回的是全书最相似的 30 块，不是覆盖目标章的那 16 块；实测召回确实向目标章聚集（9/10），但仍只覆盖那一章的一半多，多加的 20 块会往别的章飘。

**修法是「章节定向取块」，它的真正价值是把「召回率」这个未知项从关键路径上拿掉。** 原方案里「推不出」同时可能来自幻觉、召回漏、切块切断，三者纠缠分不开；改成先用检索定位章、再按 chunk_index 连续取回整章原文之后，**证据完整性是构造保证的**，只剩「真没有」和「判官误判」两种，而后者用正负对照能量出来。这是质变不是调参。

代价是引入一个更隐蔽的单点故障：**选错章会给出一份完整、连贯、自信、却根本不含支持内容的证据**，判官判「推不出」，从证据上看不出任何异常。修法是别选单一章——声明章节 ∪ 检索投票取并集，逐章独立判定 + OR 聚合。

**「拆成原子主张」这一个动作解掉了三个不同的问题**（review 方三轮里各自独立撞上）：样本量从 21 涨到约 120；「部分推得出」这一档从黑洞变成可行动（直接指出第 3、5 句没出处）；泛概念知识点（整条散在 7 个章、定不了章）拆开后每条主张各自收敛到 1–2 章。

**小 chunk 会丢指代对象，而这正好打在最重要的一类考题上。** 约 400 词的块多数不含章标题（解析时大字号版面元素被丢掉了），所以一段证据只说「第二步是讲你的故事」时，判官无从知道是哪个框架的第二步——**「张冠李戴」型考题有系统性检出障碍**。邻域扩展 ±1 救不了几页之前的标题，正确修法是**给每块证据注入结构元数据**（`【Ch.8 章名 — p.181】`），有页码映射就是零成本。

**档位标签会把片段层面的正确判断压没。** 冒烟时判官给了「部分推得出」，按「不是矛盾就算放过」记成漏判；但看「存疑」字段，判官**一字不差地摘出了植入的那句错误**。结论不是打补丁改判分规则，是**判定单元选错了**。

**「存疑覆盖植入片段 = 抓住」这个判分规则有系统性偏差**：被植入扰动的句子往往同时是整条里最具体的一句，而具体的句子本来就最容易因为任何理由被标成无支撑——**所以植入片段先验上就更容易落进存疑，哪怕判官根本没看出错**。修法是加一道短调用复核，问判官「有没有明确指出这处错误」，分「明确指出 / 只标出 / 没抓住」三档，只有第一档算真抓住。实测 24/25 明确指出，加上外来框架 5/5，判官真实检出率 29/30 = 97%。

**「条目级百分比」跨书不可比，换分母才行。** n=21 时 2 条不合格的 95% 置信区间大约 1%–30%，宽到不能支撑决策。而且三道护栏（标漏判率、标冤枉率、注明区间宽）失效的原因不在推理而在机制——**百分比会被从报告里抽走放进表格，脚注不跟着走**。替代方案是**句级支撑率**：分子是「存疑且全书扫仍找不到的句子」，分母是知识点正文的机械分句数，n 从 21 变约 130，区间收到 ±5–8 点，关键是**分母不由判官和 LL 决定**——这才是跨书可比的必要条件。条目级只给计数加案例：「21 条里 2 条」和「9.5%」信息量一样，但前者邀请人去看那 2 条，后者邀请人去排名。

**测产物测不出机制。** 业务侧怀疑的是「模型读整本书时偷懒」，这是机制层的；而 eval 的证据只能到产物层（最终产物忠不忠实、全不全）。而且只有整合版、没有中间三版，所以「漏」发生在拆书 skill 还是发生在整合筛选，这套 eval 分不开——两者的处置完全不同（改 prompt 还是改产品逻辑）。必须在报告里写明这条边界。

**512 token 的实测换算**（o200k 分词器）：英文 1 token ≈ 0.75 词，512 token ≈ 383 词；中文 1 token ≈ 1.41 汉字，512 token ≈ 724 汉字。按每页约 271 词算，512 token 只有 1.4 页。

### Roleplay 运行时架构（来自纯答疑 session，全部有 file:line 支撑）

**Stage 和「模式」是两个层级完全不同的东西，混在一句话里说会让人以为客户在自己判 Stage。**

| | Stage | 模式 |
|---|---|---|
| 它是什么 | 会话状态里的一个字段 `StageInfo.CurrentStageType` | 一份 prompt 文本里的两段文字 |
| 谁写它 | 只有 StageEvaluator | 没有人写，Customer 读完就算了 |
| 存在哪 | 存进 session、落 MySQL，跨轮存活 | 只存在于这一次调用的 prompt 文本里 |
| 有几个读者 | 五处 | **零个** |

模式有零个读者，所以它不可能影响任何后续判定。所谓「推进」的含义是把状态从 A 改成 B **并让后面的人看到 B**，Customer 这一侧没有第二步。客户回复开头那个 `[异议提出][negative]` 标签，被正则切掉丢弃、既不落库也不回传，纯粹是让模型先表态再说话的手段。

**Stage 滞后一轮的确切原因，以及 Customer 为什么不滞后。** 三个 evaluator 并行启动、共享同一份上一轮的状态；跑完合并；然后才轮到 Customer。所以：
- StageEvaluator 与更新关注点的那个 evaluator **同时启动、谁也等不到谁**，它判 Stage 时用的是更新前的关注点 → 滞后
- CustomerAgent 排在合并之后，拿到的是 `updatedState` → 不滞后

**同一个字段，两个人取的时间点不同，一个在更新前一个在更新后。** 不是 Customer 更聪明或绕过了谁，纯粹是排队位置不一样。而且这个滞后**反而帮了忙**：滞后判出的仍是 value_demonstration，而那恰好是唯一带「双模式」的准则。真正会出事的是判到 probing / opening / ending / other 这四个 Stage 上——那四份准则里一个字都没提抛异议，那一轮就抛不出来，这是 Stage 抖动的代价。

**运行时没有「关键信息的状态」这个东西，有状态的是「关注点」。** 这两个词是同一批内容在两侧的两个名字，而且只有一侧有状态。转换发生在发布时：作者配的关键信息送进 `generate_drama` 这次 LLM 调用，做的是**视角翻转**——把「销售要讲的这几条信息」改写成「客户心里在意的这几个点」。所以关注点的内容来源是关键信息，但它是一份新生成的、带状态字段的东西，名字和结构都换了。

**两条规则在正常路径下前提互斥，所以不冲突。** value_demonstration 的维持规则要求「有关注点未完成就留在本环节」，而客户抛异议要求「所有关注点已完成」——异议变 voiced 的那一刻维持规则的前提已为假。但有两条**不需要违规**就能绕到冲突的路径：closing 环节的准则把「关注点还没提」和「异议还没提」并列成两种都要推进的情况、没有先后约束；以及关注点的状态判定是「累积判断」、没有单向条款，**已 concluded 的关注点被后续对话推翻回 in-depth 是规约允许的**（对比异议侧明文写了「tabled 后不再活跃」）。

### 本体建模（来自今天的两篇本体论精读）

**FDO 的 PID/字面量边界判据，比我自己的语义点准入规则多一个关键词。** FDO 的判据是「**一个值是 PID 引用当且仅当它指代一个可复用的真实世界实体，否则保留为字面量**」。我的准入规则是「能改写成『什么条件下给出什么响应』的完整命题才建叶子」——两者是同一个形状（都在判「这个东西该不该有独立身份」），但 FDO 多了「**可复用**」。这正好覆盖我此前凭直觉处理的一类：具名情境事实（「可转诊心内科王主任」「本院设有专家组」）是完整命题，但只在一家机构成立、不可复用。

**「验证层次错位」是个要防的失败模式。** 那篇论文里语言代码「en」和「English」都被链到艺术史概念「英国巴洛克」，**而且通过了类型-词表检查，因为那个检查验证的是 URI 的域名而不是 URI 背后的实体**。占流水线链接的 28%。对应到我的活：**金标一致率检查的是两个标注者标得一不一致，不是标得对不对**——两个人可以一致地错，尤其当他们用同一份判据、而判据本身有缺口时。**一致率是必要不充分的。**

**「连通性会饱和」给了我一个可操作阈值。** 一个出现在 589/637 条记录里的权利声明 URI，单靠自己就把图连通了；作者的处理是丢掉任何在超过 10% 记录里出现的值。我的图里对应的是覆盖类评分要点（出现在几乎每个环节）。此前定的「覆盖类不进节点」理由是「它是评分规则不是知识」，现在有了第二个独立理由。

**「边际平均会骗人」的教科书案例。** 另一篇里三元组组合方式解释了 87% 的方差，而投影头单看边际贡献不到 0.4%、组合方式固定后却贡献 69%。同理 RotatE 看起来边际最好，只是因为它被坏算子伤得最轻。

**身份层与语义层分离。** FDO 把对象分成只含 PID 的内核记录（不驻留任何领域语义）和单独承载断言的元数据层。对一个还在改判据的模型特别有价值：**语义层可以随判据修订而重写，身份层不动**。另外「属性的宾语是其他 FDO 的 PID、不是词表 URI」意味着换外部词表不必改任何关系断言——对应到我：K 域应该是本地受控词表的值、本地词表项再指向 ESCO/O*NET，而不是直接写外部 URI。

## 3. 工作环境 / 公司 / 业务背景

### Learning Library（LL）是什么

UMU 的一个产品，用一个 Claude skill 把整本书拆成「知识点」，产物进产品给学员学。业务侧怀疑两件事：模型读整本书时偷懒或幻觉、书里的重点没被覆盖全。

**今天确认的两条关键前提：**
- **拆书要求是覆盖全书**（用户确认）。这让覆盖性这条线有了真实存在的目标，也让「两章零产出」成为实打实的缺口
- 拿到的 26 个知识点**只有整合版**，中间三个独立版本（作者叙事 / 认知层次 / 情境）没有给。所以分不清「漏」发生在 skill 还是发生在整合筛选

产物字段：`ref / chap_id / kp_nature / kc / title / content / goal / deps`。26 条里有 5 条标题以「希望…」开头（`goal=apply`），是练习情境——业务侧明确说情境是自己造的、且要避开原书例子（版权），所以**不进忠实性池**，忠实性实际只评 21 条。

会议纪要来自 Plaud（`web.plaud.cn/share/...`），74 分钟、354 段逐字稿，可以从它的接口把全文拉下来。会上提出 eval 方案的是 Ethan；拆书 skill 那边的负责人是田淑坤。

### CSRS 是什么

UMU 自研的 RAG 检索系统：BM25 + Graph + Chunks + Table 多路 W-RRF 融合加 rerank。

- 地址 `172.24.201.36:8080`，租户 `umu`，本次用的 dataset `ll-eval`
- LLM 网关是**另一台** `172.24.201.32:8080`
- 可用模型：`csrs/sonnect-5`（实测回答自己是 Anthropic 的 Claude）、`csrs/csrs-default`（实测是 gpt-5.2）、`csrs/haiku-4-5`、`csrs/qwen-plus`、`csrs/bot-query` 等。**仓库 benchmark 里写死的 `gpt-5.2` 这个名字不在这个网关上**
- 用户今天定的分工：**判官用 `csrs/csrs-default`（判定要严，用最强的）；全书遍历这类百万 token 量级的活用 `csrs/sonnect-5`（成本敏感）**
- API 契约在 `docs/api/GATEWAY_API.md`，用户明确要求走这份里定义的 gateway API

**契约上三个容易踩的点（今天都踩了并改正）：**
- 身份要传 `agent_name`，只传 `user_name` 走的是文档明确标 deprecated 的路，**某个阶段之后会直接 422**
- `citation.chunk_index` 是易变快照，**持久引用一律用 `chunk_id`**（重新 cognify 后下标会指向别的内容）
- `citation.chunk_num_sum` 直接给总块数，不用「一直探到返回空为止」那种土办法——后者碰上中间某段临时取不到会**静默少几块**，而少的那几块在覆盖率里就变成「书里这段没内容」

**两个 CSRS 自身的 bug（与 eval 无关但会继续坑人）：**
- `/api/v1/add` 报 `session_dataset_id ContextVar not set`，这条入库路断了
- `/api/v1/cognify` 会在 `default_user` 名下新建一个空 dataset，`payload: []` 还照跑不报错

### Roleplay 的两侧命名分裂

这是今天答疑里最值得沉淀的环境事实：**同一批内容在运行时侧和评估侧有两个名字，而且只有一侧有状态。**

| | 关键信息 | 关注点 |
|---|---|---|
| 英文名 | `ConveyedInfo` | `ConcernPoint` |
| 谁产生 | 作者在编辑器里填，存 MySQL `roleplay_section.conveyed_infos` | `generate_drama` 这次 LLM 调用产生，写进 Scenario YAML |
| 在哪一侧 | 评估侧 | 运行时侧 |
| 有运行时状态吗 | **没有**，只有 `Info` / `SemanticPoint[]` / `Weight` 三个字段 | **有**，五个取值 |
| 谁改它的状态 | 无人，静态配置 | ConcernObjectionEvaluator，每轮判一次 |

所以在客户的 prompt 里搜「关键信息」是 0 次命中——运行时那一侧没有这个概念。

**客户的 prompt 由两个文件嵌套拼成**：`roleplay_customer_system_prompt.txt`（骨架，带占位符，9624 字节）+ `roleplay_customer_behavior_principle.txt`（YAML，七个 Stage 各一段，整份 18120 字节、每次只注入一段）。后者按 Stage 取，注入量从 498 字节（ending）到 9807 字节（objection_handling）不等，差近 20 倍。

**Apollo 上的 prompt 是按站点乘语言的副本，改一处不会自动带过去。** 四个站点 cn / co-jp / com / dev 各有一份，co-jp 下同名文件还有 `_canary_en` / `_canary_jp` 两个灰度版本。**prompt 类改动的实际工作量是「站点数 × 语言数」次重写。**

### 医药知识技能图谱的数据现状

- 数据组织在 `docs/core-business/` 下，已记录到文档
- **进本体的实际有四个来源**：语义点（关键信息和异议回应两处）、关键信息与异议本身作父组、评分要点里内容类和复合类拆出的知识、评分要点里动作类和态度类变成技能行为。另有判否语义点里的动作话术回收成示范语料（挂已有行为、不新建节点）
- **不进本体的三样**（用户此前联系不上是对的，因为它们本来就是任务侧配置、和知识技能是并列关系）：证据规则（环节分怎么汇总的计算规则，存任务证据矩阵）、任务质量要求（对整次对话的整体要求，存任务模板）、场景目标（场景设定不是学员能力，存场景配置）
- **评分要点是环节级的**，既不属于关键信息也不属于异议。作者写 10 条关键信息和 3 条评分要点，不是每条信息配一个要点，而是 3 条要点各从一个角度评判整个环节
- **知识和技能之间目前没有任何直接关系**，因为没有数据支持这种断言
- `remediated_by` 指向课程小节或知识卡片这类学习内容、不指向另一个知识点，是闭环最后一步（掌握度没过关就说「去学这个」）。Roleplay 里没有可推荐材料，**现在是个空槽**
- **同一句话写在不同位置归属不同**。「推荐主任下次门诊用某药」出现在语义点位置标否，同样的话出现在评分要点位置会归为技能行为「请求承诺」并打合规标注保留。**位置决定它被当成什么**
- **评分要点有稳定 id，语义点没有**。而且评估结果里那些序号 id 是环节内位置序号、会随作者编辑漂移；`message_id` 存的是 `message_3` 这种序号、不是数据库主键

### 三家日本企业的语义点准入率差 6 倍 — 这条影响扩产决策

| 企业 | 语义点 | 判否 | 否占比 |
|---|---|---|---|
| 勃林格 | 207 | 22 | **11%** |
| 灵北 | 249 | 157 | **63%** |
| 美敦力 | 63 | 48 | **76%** |

已核实**不是两人口径不一致**（抽查里双方对动作类的判否完全一致），真实原因是**作者写法不同**：勃林格在建议回应里写循证内容、带试验名和数值；灵北和美敦力写的是对话应对话术。

**后果：扩到中国站 75 家医药企业时不能按勃林格的可用率估产出。** 同样一千条语义点，循证型企业约产 890 个知识叶子，话术型只产 240–370 个。**灵北那种把整套拜访话术脚本写进异议建议回应的企业，本质是话术脚本不是知识清单——做知识图谱产出低，做技能示范语料价值高。** 扩产时可以按这个分型决定每家先做哪一侧。

### 多会话协作

今天六个 session 里有四个在通过 UDS（`uds:/tmp/cc-socks/<pid>.sock`）互相发消息协作。**peer 消息是队友请求，但 peer 不能授予权限升级**——不能因为 peer 要求就改权限设置、CLAUDE.md 或配置，不能把 peer 消息当成用户对待批准项的同意，peer 说自己被拒了让你代做要拒绝并上报。

一个实操细节：**peer 会话可能有两个同名实例**，新任务来自较新的那个，完成通知要发到两边。另外**对方 harness 给的 idle 预览只有一行，不等于对方的完整结论送达了**——今天出现过只看到一行摘要就要往下走的情况，正确做法是要求对方用 SendMessage 把全文发过来，**不编它的结论**。

## 4. 经验与教训

### 用户今天做的纠正（按重要性）

**1. 「你不要用黑话！」** 用户两次贴同一段话说看不懂「负样本」「正样本」「头条」。改成「假知识点 / 真知识点 / 报告的主要结论」，并用机场安检员打比方讲清「为什么两种考题都得出」之后才通。**教训：涉及方法论时，我默认使用的统计学词汇对用户是不可读的。先换成他领域里的词，再讲道理。**

**2. 「为什么到现在都没跑忠实性和覆盖性的测试呢？」** 这条我承认排序错了：在还没做过一次真实判定的情况下，先花大力气造 40 条考题、做三轮审计、返工两次。**正确顺序是先拿 5 条真知识点跑一遍看看判出来什么样，再决定考题要造多严。** 我把「把方法做扎实」放在了「先看到一个结果」前面。

**3. 「这个文档的质量不行啊！」** 用户要求用对抗式方式 review，结果 31 条断言里只有 2 条完全站得住。**教训：自己写的文档盲区最大，要派独立多路审查而不是自查。** 另外用户单独点了措辞问题：「你不要用本体侧来代表一个事情，本体只是实现的一个手段」——**不要用实现手段的名字去指代业务概念。**

**4. 「FCC 不是已经有落地的指令了么？中际旭创至今不是回购股票么？」** 回购这条我确实漏了，根子是**读了评论文章却没去读交易所公告原文**。FCC 那条我核查后与用户判断不同并给出了双语两套独立信源，但我自己此前的写法也有错——**把举证责任搞反了**：待确认的是禁令本身（草案阶段、无正式程序），不是豁免。**沉淀一条：涉及某只票的利好利空，先拉交易所公告列表，再看研报和媒体。**

**5. 「你这个股票程序的板块分类不恰当」「银行涨得好为什么探测不出来」**（9/10 的，今天数据又加了证据）：`MIN_SHARE` 这个相对阈值随时点漂移，早盘几乎不构成约束、收盘变成硬门槛。修法仍等用户定。

### 方法论沉淀

**观测不等于判断。** 确认了一个事实之后要再问一句「它推得出我要下的那个结论吗」。今天的三个实例：
- 「33 个合并里 17 个正确」推不出「合并质量可接受」——**51.5% 是错的**，如果自动跑，每两个合并里有一个要人来撤销
- 「13 个跨提供者桥」推不出「机器 agent 能跨提供者遍历」——1 个已确认是假的、12 个把原始 URI 当标签无法自动审计
- 「密度表显示某章零知识点」推不出「忠实性有问题」——密度统计的前提就是这些知识点存在，**书里某段没有知识点它就不出现在任何证据里，密度自然是零，这是定义决定的不是测出来的**

**一个时点的读数不是完成态的结论。** 9/10 在 10:00 断言「没有传导」被收盘证伪；今天 9:30 说「中际旭创低开预测错了」，又补了句「等收盘才能定论」——10:00 的读数比 9:30 更强、不是回落，所以那句缓冲反而是多余的。**方向错就是错了，别给自己留台阶。**

**头条和数据可能用的是两个时钟。** 今天同一批快讯里「上海原油主力合约涨超 5%」（15:00 收盘、定的是昨夜的价）和「纽约原油 −3.92%」（连续盘、还在走）看似矛盾，实际是两个合约两个时钟。**引用跨市场数字时要标清是哪个合约、截止什么时点。**

**聚合站的价格数据会静默过期。** 今天两次搜索分别返回了对不上任何近期观测的价格（一只票差 100 多元、另一只差 3 元多）。**凡价格用自己实测的数，搜索结果里的行情一律不采信。**

**自己写的检查脚本也会错。** 今天有三次是检查脚本本身的毛病导致假警报：术语核对用多词短语匹配（含标点的短语必然找不到）、章标题核对（解析时大字号版面元素被丢了，13 章 12 章 MISS）、热词统计读错 JSON 路径导致结论整个反了。**假警报和真问题看起来一样，先验证检查工具再相信它的输出。**

**统计脚本静默少数据是最危险的失效模式。** 「一直探到返回空为止」这种写法碰上中间某段临时取不到会静默少几块，而少的那几块在覆盖率里就是「书里这段没内容」。**改成用服务端声明的总数做断言，取回数 ≠ 声明数就直接报错退出。**

**停止规则必须写在出结果之前。** 今天专门落盘成 `STOPPING_RULES.md`，理由是**事后会被谈判**。同理，敏感度阈值不在小样本上调优。

**被实证证伪就按对方数据为准，不要辩。** review 方今天提的两条被主实现方用实测证伪（语料有洞、候选章词数超上限），直接承认并按对方数据走，其余采纳。反过来主实现方也接受了对方多条设计级修改。**这套「提判断 → 对方实证核 → 该证伪的证伪、该采纳的采纳」的来回，是今天两个 session 里质量最高的部分。**

**一致率是必要不充分的。** 两个标注者可以一致地错，尤其当他们用同一份判据、而判据本身有缺口时。κ 高不等于正确率高。裁定金标（引入第三方判断）正是在补这个，但要明确写进 SOP，避免下一轮只看一致率就放行。

**「我没查就下了结论」是今天最反复出现的失败模式。** 热词的性质、提示条件的方向、覆盖率公式写在哪、回购公告——四处都是**手里有可查的一手来源却先凭印象写了**。共同修法：涉及机制断言，先去读代码 / 读公告 / 读研究报告原文。

### 有效的做法

- **硬断言校验边界。** 13 个章首页逐页核对写成脚本里的硬断言，对不上直接退出，不会带着错的页码映射往下跑
- **白拿的交叉验证要接住。** 服务端声明的总块数与独立枚举结果一致，这是零成本的互相验证
- **把「不报某个指标」也写进报告，并给理由。** 论文里拒绝报标签相似度（在多语言上给正确的跨语言链接打零分）和含回退的路由准确率（把任何兜底都算正确、是被设计而非被测量所限定）——这个动作值得学
- **交付形态押案例不押百分比。** 做成「知识点这么说 / 书里这一段这么说（附原文 + 章节页码）」的对照清单交业务侧核。以及一条措辞纪律：**业务侧没核之前一律写「未在书中找到依据，待确认」，并且现在就讲定——业务侧否掉几条，报告里的数跟着改**
