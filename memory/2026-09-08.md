### 「知识点」在 UMU 公司内至少指三样不同的东西

这是今天最重要的一条认知，也是统一建模的起点。三者**没有任何字段级关联**：

| 名字 | 在哪 | 是什么 | 回答了哪一问 |
|---|---|---|---|
| **学习平台知识点** | MySQL `umu.knowledge_point` 及派生表 | 企业自定义的标签，只有一个名字，绑在题目和课程上用来算正确率 | 只回答「是什么」，且只有名字 |
| **能力模型（capability）** | MySQL `capability_jp` 库，15 张表 | 岗位级能力，有分类、有等级、有岗位期望、有补差学习方案。UMU 的 i18n 文案里 `'capability' => 'Skills'`，所以产品上它就叫 Skills | 「是什么」+「学到什么程度」 |

### LL 的三个核心字段：kp_nature、kc、decorates

LL（Learning Library）是 UMU 的一个产品，用大模型把书拆成课程；一门课是一个 JSON，含 `title / author / domain_id / kps[]`，每个知识点 17 个字段。今天读的两份产品设计文档给了字段定义表，加上 42 门课、883 个知识点的实际 JSON 做校验。

**`kp_nature`（结构性 / 装饰性）**
- `structural` 结构性：课程主线上的知识点，Coach 要教、`kp_status` 判定器要判它有没有掌握。721 条。
- `decorative` 装饰性：挂在某个结构性知识点上的辅助素材——可选场景、情境练习、核心类比、延伸阅读、某个实验（比如 Thorndike 猫的迷箱）。162 条。它们的 `checkpoint_after` 几乎全是 false（13/162），即不当段末考核点。
- 一句话：**结构性是「要学会的东西」，装饰性是「帮你学会它的东西」。**

**`kc`（knowledge category：cognitive / skill）**

| | cognitive 认知型 | skill 技能型 |
|---|---|---|
| 指向 | 概念理解 | 行为操练 |
| 掌握等级刻度 | aware → recall → explain（知道有这回事 → 能说出核心 → 能用自己的话解释） | mirror → apply → transfer（几乎相同场景下模仿 → 类似场景下使用 → 自身场景下迁移） |
| Coach 教学法 | 隐喻式，用学员熟悉的事物做类比 | 示范、操练、切己迁移，逐级增加陌生度 |

### 前端不构成安全边界（prove session 的整场讨论）

起因：cuiyang 问 `ycui-apolo-query` 这个 skill 的原理，得知它是把 apolo 网页版发给后端的 HTTP 请求原样重发（四个 POST：`/login/` 拿 csrftoken、`/authenticate/` 登录、`/getdbNameList/` 列库、`/query/` 跑 SQL），于是追问「那岂不是无法强制用户只能在 UI 上操作」，再追问「任何软件的 UI 其实都能绕开？比如微信」。

沉淀出的判断：

**「强制用户只能在 UI 上操作」这个目标本身不成立。** 凡是跑在用户机器上的检查（按钮置灰、前端 JS 校验、隐藏表单字段），用户都能改掉或绕开。能成立的目标是另一个：**限制这个身份能做什么，并且留下痕迹。**

CSRF token 和 Referer 校验**挡不住脚本**——脚本自己就能取到那个 token、照填那个 header。这两条常被误解成安全兜底，实际不是；它们挡的是「别的网站借你已登录的浏览器偷偷发请求」。真正服务端认的只有一条：**身份必须真**（不登录拿不到会话 cookie）。

**绕过成本的三个台阶**（爬的是成本，不是性质——三个台阶上服务端都仍是唯一判断者）：

| 台阶 | 例子 | 服务端要求带什么 | 拿到协议的代价 |
|---|---|---|---|
| 一 | apolo | 明文表单 POST，会话 cookie + 自己就能取的 CSRF token | F12 看一次 Network，十分钟 |
| 二 | 一般 App / 后台 | 加一个客户端算出的签名参数（参数排序拼密钥做哈希） | 反编译找密钥与拼串规则，几天到几周 |
| 三 | 微信 | 私有二进制协议、加密信道、设备指纹、加固原生库算出的校验值 | 持续逆向，对方每次更新就要重做 |

微信在客户端上花的功夫（混淆、加固、反调试、白盒加密、设备绑定）**是一道成本墙不是一道锁**——判据很简单：那个校验值是在用户手机上算出来的，算法就在那台手机里，能跑就能被观察。历史上那批基于微信网页版协议的第三方库，微信的应对不是把客户端做得更绕，而是**关掉网页版登录能力 + 持续封号**——应对方式本身就说明边界在服务端。

**最要紧的一条**：绕过 UI 从来拿不到超出自己账号的权限。用脚本调 apolo 用的是本人账号密码，权限和网页上点出来的一模一样，一分不多。所以真正该问的不是「有人绕过了 UI」，而是「这个账号本来能做多少」。「绕过 UI」的后果分两种、性质完全不同：**自动化自己的账号**（成因是客户端可被模仿，和 UI 有关）vs **拿到别人的数据或做无权操作**（成因是服务端鉴权授权有漏洞，和 UI 无关，UI 做得再严也堵不住，因为 UI 不在那条判断路径上）。

要限制，四层里第一层最硬：**把危险能力从服务端整体移除**（平台连库用只读账号，无论谁从哪发请求写操作都执行不了）；其次**按身份授权不按来源授权**（判「请求是不是从网页来的」没有意义，请求头全是客户端说的话）；再是**审计与告警**（对内部平台通常比堵更实际）；最后**限流**（防拖垮从库）。厂商通常还给第三条路——开官方 API（公众号/小程序/企业微信/开放平台），把不可控的逆向引导到可控通道上，走官方要注册应用、拿密钥、按范围授权、受配额、可审计可吊销。

**一个留下的未验证问题**：apolo 服务端有没有也卡住非 SELECT 的语句。脚本第 71 行那道 SELECT 检查是**客户端的**，只约束用这个脚本的人，换个 curl 就没有了。真正的只读保证必须在服务端——要么平台代码校验语句类型，要么平台连库账号本来就是从库只读。**没有实测**（那要在生产平台上真发一条写语句，不该做），**这一条要问 apolo 负责人，不能靠猜**。

### 两篇本体论精读带来的概念

**「运行时拼身份」**（AI-ready data 那篇）：同一个人在 CRM 是字符串 ID、计费系统是整数、客服工单是 UUID，agent 只能猜哪些记录属于同一个人，「那个错误会直接流进你的下游决策」。本该在建模时解决一次的事，变成每次查询都要解决一遍，而且每次都可能解错。

**「推理记忆」（reasoning memory）**：三层记忆里长期（业务知识）和短期（进行中对话）是常见说法，**第三层不常见**——agent 试过的计划、调用的工具、观察到的结果、**以及第一次失败后你给它的纠正**。「每个决定都成为图中一条可追溯的路径。」这正是 cuiyang 这几天手工在做但没有机制的事（属性和关系的分界改了三次、`rdfs:domain` 被撤回、B8 被修正、J6 的确立，全在 markdown 里，不在任何可查询的结构里）。和 9/6 读的 Document Intelligence 路线图里的「Context graph」是同一个缺口，**两篇独立提到说明不是洁癖**。

**「治理不能只依赖提示词」**：写在 prompt 里的规则模型可能忘、可能被绕过；写成约束的绕不过，**因为它不是一条指令而是一个约束**。

**一个权威出处**（第一篇的主要价值）：美国国防部《数据、分析与 AI 采用战略》规定了层级顺序——高质量数据在底、分析在中、负责任的 AI 在顶，原话是「所有分析与 AI 能力都需要可信、高质量的数据」，而可信数据的一个特征是**它是链接的**。作者据此推出**「关系是一等数据资产，需要被相应地存储、治理和查询」**——这句话正好是 prove 项目里 `rbox.yaml` 存在的理由，而且它来自使用方不是供应商。

**数字要打折扣**：IDC 那个「幻觉率平均降低 44%」没给样本量和对照组，且 IDC 是分析师机构、这类研究常由厂商赞助；Klarna 那个「废弃 1200+ SaaS 系统」不该归因给图谱，那主要是采购和流程整合的结果。

## 3. 工作环境 / 公司 / 业务背景

**`capability_jp` 库 —— 今天新发现的一套系统**：15 张表，2024 年建、2026 年 6-8 月仍在更新。模型是三个闭环：岗位 → 能力期望 → 能力 × 等级；员工 → 评估 → 能力 × 等级；能力 × 等级 → 学习方案 → 课程。合起来是「岗位能力标准 + 员工评估 + 补差学习」。i18n 里 `'capability' => 'Skills'`。**backend 这个 PHP 仓库里只有一个功能开关名和 chatbot 的 goapi 调用，维护它的是另一个服务。**

**Megrez 和 Merak 是两个 Go 服务仓库**（本地在 `~/projects/umu/Megrez`、`~/projects/umu/Merak`）。今天确认：知识点答题汇总的 goapi 实现在 **Megrez** 的 `logic/knowledge_point.go`，Merak 里没有相关代码。`goapi\exam\Api::getUserSubmitQuestionList` 对应 Megrez 的 `KnowledgePointUserSubmitQuestionList`。

**`is_scored` 的准确含义**（今天纠正过一次，见第 4 节）：**`is_scored = 0` 表示「这道主观题到现在一次评分都没有」**。Go 侧逐条提交累加、按（学员 × 题）汇总：客观题每次都计入分子分母、`not_scored` 恒为 0；主观题这次已评分（`subjective_status = 1`）计入；主观题这次未评分则**跳过**（不进分子也不进分母）；只有所有提交都未评分时 `not_scored = 1`。PHP 把 `not_scored` 反过来存成 `is_scored`（`UserQuestionDetailData.php:116`）。**即：未评分的提交逐次剔除；只有整道题一次都没评过分，整道题才不进正确率。**

**知识点绑定的两层混存及其后果**（报告第 7 节第十条）：`knowledge_point_resource` 一张表同时存定义层（`obj_type` 1 题库题、5 小节模板题、6 课程模板）和实例层（2 考试题带 `session_id`、3 课程、4 每日一考题）。两层靠**一次性复制**连接不是引用：建固定试卷时 Go 侧发 type 2 绑定，若题从题库拉的，`bindResource` 当场从 type 1 复制一份（`KnowledgePointResource.php:232-235`）；课程↔模板之间 `cloneGroupKnowledgePoint` 整行复制。复制之后各走各的——题库题改绑定，`bindResource` 只 diff `obj_type=1` 的行，已生成的考试实例不跟着变。1,447 万行 type 2 就是这么来的。

**后果：统计有两条解析路径，同一次答题归到哪个知识点取决于考试是哪种出题方式。**

| 出题方式 | 读哪一层 | 代码 | 绑定是什么时候的 |
|---|---|---|---|
| 固定考试 | 实例层 type 2 | `ExamDetail.php:74` | **冻结**在建考试那一刻 |
| 题库随机考试 | 定义层 type 1 | `ExamDetail.php:242` → `KnowledgePointResource.php:449` | **跑批当晚的最新值** |

随机卷只能走定义层，因为 Go 侧 `if !questionRandom` 才发实例绑定——随机组卷根本没有实例级记录。叠加「统计分区每天从头重建」：今天把某道题库题的绑定从 A 改成 B，明早分区里昨天走随机卷答这题的人全归到 B，走固定卷答同一题的人还在 A。同一道题、同一个学员、两种规则；而且随机卷那位学员的报表会**在两天之间自己跳**。

**数仓侧的建法（推荐拆两层 + 拉链，理由是正确不是便宜）**：不复制，改记历史——建绑定历史表做 SCD2（`valid_from` / `valid_to`），答题事实按 `exam_submit_time` 做 as-of join。这样所有出题方式一条规则，「答题时的绑定」和「当前绑定」两种口径都能算、由查询决定。这张历史表不用人工维护：`knowledge_point_resource` 的 binlog insert/delete 事件天然就是这个历史。它要多建一张拉链表，但同时消掉千万级的实例复制，**存储反而省**。
**实例层不能完全去掉**——老师在固定试卷里直接手写的题没有题库来源，它的绑定只存在于实例层，是真实的事实不是复制品，干净模型要给它打「无题库来源」标记而不是删掉。

**统一模型 spec 已写定的几个设计判断**（cuiyang 后面给新产品资料时对着看是否成立）：
- `unit_type`（cognitive / skill）是核心维度，来源只有 LL 的 `kc`；能力模型固定为 skill；学习平台没有，需推断或补标
- `kp_nature` 放在「课程 × 知识单元」**关系表**上，不放实体上——同一个案例换一门课角色会变
- 掌握度**不做跨量表换算**，`learner_unit_state` 带 `scale_id`，换算留给分析层。理由：正确率是连续值、能力等级是整数、LL 是两套三档刻度，语义不同，硬换算会压出一个假的数
- 跨产品的 `same_as` 边现在**没有任何自动来源**，这是第一难点
- 四张表草案：`knowledge_unit`、`knowledge_relation`、`course_knowledge_unit`、`mastery_scale` + `learner_unit_state`
- spec 的结构是按「逐个纳入产品」的节奏搭的：第 2 节每纳入一个产品加一小节、第 4 节字段映射总表每次加一列、第 7 节变更记录每次一行

**backend 仓库里没有「SKILL」**：全仓库搜 `skill` 只命中文案和 prompt 常量，没有表、没有 DAO、没有逻辑类。名字里带 knowledge 的有三套，只有一套是知识点——另两套是 uAsk 知识库（`uask_knowledge_*`，问答文档库）和 AGL 课程认知层（`agl_course_knowledge`，AI 建课的学习地图 JSON，知识点 id 是 `kp_xxx` 字符串，**和 `knowledge_point.id` 没有任何关联字段**）。

**`list-for-course-data` 这个接口特殊**：直查 umu 业务库不经统计层，所以后台「知识点课程数据」tab 是**实时**的，和另外两个 tab 数据时点不同。

## 4. 经验与教训

**「某个东西有没有用」不能靠感觉，要看它服务的那个状态还存不存在。** `sync_doris` 和 DataX 这两条搬运单看代码都合理，顺着 git 时间线才看出它们是 2025 年 8 月「读侧先切、写侧没切」那七个月里的补丁，2026 年 4 月写侧直写之后就没有对应场景了。判断一段逻辑该不该留，不是看它跑得顺不顺。

**线上数据比代码更诚实。** 企业 668 那 29 万行停在 1 月 14 日，代码里看不出任何异常、跑批每晚正常结束。以后核链路，光读代码不够，**得去库里看最新一天的数据是不是真的在更新**。

**产品文案和代码口径会悄悄分叉，而且没人故意做错**——是两边各自演进后没人对过。所以「对口径」这个动作要主动做，不能等出问题。

**数据里的模式不等于规则——今天在这上面被纠正了一次。** 我先说「装饰性知识点是 skill、结构性是 cognitive」，还从一对记录（`I05s` 情境练习 decorates `I05` 学习型对话）读出「先认知再操练」这个机制。cuiyang 追问「你如何识别的过程是这样」、「structural 一定是 cognitive 么」，一数分布就翻了：
- 162 个装饰性里 **113 cognitive / 49 skill**（多数装饰素材是案例、类比、延伸阅读，这些是认知型）
- 721 个结构性里 **476 cognitive / 245 skill**（三分之一是技能，标题长这样：「从确信转向好奇」「分离影响和意图：先说影响，再问意图」「绘制贡献系统」）
- 装饰与被装饰的 kc 组合**四种都有**：认知配认知 76、认知配技能 37、技能配技能 34、技能配认知 15
- 那句「先懂再练」我用了三个信号拼出来，**但只有 `deps` 是顺序信号**，`decorates` 和 `kc` 都不是；而 `deps` 这条在整批数据里并不普遍——162 个装饰性里只有 38 个把被装饰对象列进自己的 `deps`

**准确的说法是：`decorates` 只表达「附着在谁上面」，教学顺序要看 `deps`。** 沉淀的原则：**`kp_nature` 和 `kc` 是两个独立维度，四个格子都有数；建模前先数一遍分布，比看几个例子可靠。** 把一对记录的特征说成机制就是过度推断。

**同一天在同一个 session 里第二次被纠正：`is_scored` 的含义。** 我先说「有一次没评分就整题剔除」，读了 Megrez 的 Go 实现（`logic/knowledge_point.go:437-515`）才发现是**逐次剔除**，只有整道题一次都没评过才整题不算。教训和上一条同源——先给结论再找证据，方向就容易反。cuiyang 的追问方式（「解释一下这句话，is_scored 到底是什么意思」）每次都精准打在没验证的那一环上。

**建模时把「实体属性」和「在某个场景里的角色」分开。** LL 里结构性/装饰性看着像知识点属性，其实同一个案例在这门课是装饰、换一门课可能是主线，它是「知识点 × 课程」关系上的属性。学习平台的绑定表把定义和实例放一张表，代价是随机卷和固定卷的归因规则不一样。**层次一混，下游口径就跟着散。**

**回答「某列有没有被使用」必须按结构判，不能搜字段名。** 「表里有这个列」和「接口真的把它读出来给了页面」是两回事。今天的做法是三步：先把统计表所有数值列列全，再看每个读方法实际 SELECT 了哪些列、返回了哪些字段，最后对到接口。结论（30 多列写了、12 个被读走）只有这样才站得住。

**在生产平台上做元数据查询也要估代价。** `knowledge_point_resource` 按 `obj_type` 分组那条跑了 **14.8 秒**——`information_schema` 估 824 万行、实际 1,455 万，覆盖索引扫描比预估重。已记进报告备忘：**这张表以后不做全量聚合。**

**本体论流水线的那个 30 秒动作继续奏效**：开工前先提取每份已有产物的第 1 页、映射到它的源文件，产出一份真正的「还没做」清单，再动手。今天靠它准确定位「8/23 只欠 1 篇、8/24 欠 4 篇」，一次清掉一个欠账日。这个动作是 9/4 重复做了一篇 digest 之后固化的。

**早盘那两条数据完整性发现值得复用为检查项**：① `gb_` 接口的时间戳每次都要看——美国假日休市时它会安静地返回旧价，不报错；② 引用回测准确率之前，先确认「一个外盘交易日 → 一个 A 股开盘」这个映射今天成不成立。假日之后的第一个交易日，这个映射一定是断的。
