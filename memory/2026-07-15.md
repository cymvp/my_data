## 1. 今天获得的知识与技能

- **本体论驱动的数据问答（ontology-driven QA）是 Prove 项目的核心方法**。所谓"本体"，是指用规范化的 YAML 文件把业务里的概念（如"知识点""学员""答题"）、概念之间的关系、以及硬约束（公理）显式登记下来，形成一层"统一语义层"，让大模型能准确理解企业数据的业务含义再回答问题。它对 cuiyang 重要，因为这是他要向 PM/Ethan 汇报、并决定产品走哪条技术路线的当前主线工作。

- **问答链路的六步结构**（Prove 验证一实际跑的路径）：用户提问，大模型从登记好的业务问题清单里选中一条（命中 CQ），系统召回这条问题登记的本体与指标，执行注册中心里固定的 SQL 模板取数，把概念定义、口径卡、公理原文、查询结果组装成上下文发给模型，模型只负责组织语言，最后一道对账 gate 把回答里每个数字逐一和查询结果比对。要点是：大模型全程不写 SQL、不碰表结构，取哪些指标是人在建模时评审登记的，运行时照单全取，没有"从本体推导选指标"这个推理步骤。

- **CQ（Competency Question，能力问题）**：预先登记评审过的一条业务问题，连同"用哪些指标、怎么算"一起被裁定。一条 CQ 是一族问题——带上参数（时间窗、知识点关键词）后，"华东区上季度哪个知识点最弱"和"新员工这个月哪个知识点最弱"是同一条 CQ。

- **两种"有本体"的消费形态，最终结论是双模式并存**：
  - **问题驱动**（原代号 L1，14/15）：业务问题连同答法整个被登记评审，大模型只选问题、抽参数、组织语言。适合高价值高频、要拿去汇报的数字。
  - **目录驱动**（原代号 L2，10-11/15）：登记的是积木（度量 × 维度 × 过滤条件目录），大模型现场组合出查询计划 JSON，确定性编译器按白名单校验后编译成 SQL，目录外整单拒绝。适合长尾和探索，失分形态全部是"诚实拒答"而非"安静出错"。
  - 结论：两者建在同一个语义层上，只是本体以什么形态喂给模型（问题级裁定 vs 积木级裁定）不同。市面主流产品（Snowflake Cortex Analyst 的 YAML 语义模型、Databricks Genie 的 metric 目录、ThoughtSpot）走的都是目录驱动，没有一家走裸表直接 NL2SQL 的路线。

- **消融实验（ablation）方法**：固定"同 15 题、同企业、同数据库、同模型、同评分尺"，唯一变量是给大模型什么上下文，每次只拆掉一个部件看掉多少分。这是判断"统一语义层到底值不值"的证据来源，cuiyang 非常看重实验细节的可复现和可核对。

- **消融的四个对照组含义**（务必记住，cuiyang 反复追问过）：本体链路（A）给的是 CQ 注册表+口径卡+公理+模板执行结果；裸表-选好表（B1）给正确的两张表原始 DDL 让模型自己写 SQL；裸表-全库（B2）给全库 51 张表 DDL 自己找表；注释对照（B3）给 B1 的两张表但把口径知识翻译成表注释——"只给知识不给结构"，用来把本体的价值拆成"知识"和"结构"两半分别称重。

- **B3 实验得出的核心认知："知识可搬运，结构不可搬运"**：口径知识（官方算法、只算客观题、样本阈值、字段要 CAST 等）用注释携带就能把成绩从 10 拉到 13，说明差距大头是知识；但剩下的差距输在结构——① 结构是强制、注释只是建议（一句"把主观题也算进去"就能诱导注释版删掉过滤条件重算，而本体把 `is_subjective=0` 焊在 SQL 模板里模型改不动）；② 默认口径（"这期培训"没给时间窗时用什么范围）是决策不是知识，注释携带不了；③ 注释没有数字对账，写错数没人拦；④ 注释是口径的复制品散落各表，会随业务变化安静地漂移、教错模型，而注册中心有版本、评审、引用校验。所以注释对照不是语义层的替代品，是它的降级投放形态。

- **G 组实验（全局语义层 vs 局部注释的针对性对照）结论：本体赢 2 输 2 平 1**，很诚实。赢在口径强制性（G2 诱导题）和取数确定性+数字对账（G4 三连跑一致性）；输在 CQ 覆盖度和意图路由（G1 复合问句被错误路由到只挂单表的 CQ、G3 缺一条"这个数怎么来的"溯源类 CQ）。得到的原则：本体的血缘、统一定义优势真实存在，但必须有产品出口才能被用户感知。

- **指标（metric）挂在哪个本体概念上的判别法**：挂在"这个指标是关于谁的陈述"的语义主体上，不是数据来源、不是影响它的活动、不是它回答哪个问题。机械判别法：看指标 SQL 的 `GROUP BY`，去掉租户/时间这类通用维度后剩下的业务对象就是挂载对象。三件容易混淆的事：挂载不等于数据来源（血缘走 `source` 字段）、不等于影响关系（影响方可以有多个，走单独的 influences 关系）、不等于回答哪个问题（走 `answersCQ` 关系）。

- **"关系实体化"建模手法**：考试分数不需要造二元组，因为"那次考试尝试（ExamAttempt）"本身就是个实体，分数是它的属性——事件天生就是关系的实体化。但掌握度（张三对知识点 X 的掌握度）没有天然事件载体、又要携带置信度/档位/证据集合/计算版本，所以必须人为造一个实体（KnowledgeMasteryEstimate）。检验属性归属的钥匙："对象不变、换个搭档，值变不变"——知识点不变、把张三换成李四掌握度就变，说明它不是知识点的属性。个体判断要造实体，聚合统计（全员平均掌握度）才是挂在知识点上的指标。

- **公理（AXP）不是一个独立校验函数，而是被编译进链路不同环节**：AXP2"正确率只算客观题"在取数层是 SQL 里的 `AND is_subjective=0`（poc/l2.py:100），在 prompt 组装时又以原文形态附给模型让它能解释给用户。五条公理各有落点：AXP1/AXP2/AXP5 编译进 SQL 的 WHERE/HAVING，AXP3 是加载层引用完整性校验（悬空即拒绝启动，poc/loader.py:67），AXP4 是回答后 gate 数字对账（poc/gates.py，对不上直接 fail 不降级）。公理落在哪，取决于系统里"最怕出错的东西"从哪经过。

- **Claude Code 界面行为的两条准确事实**（当天查证）：① Recents 列表按"界面 + 项目目录"分别维护，CLI 起的会话不进桌面/web 的 Recents，反之亦然；空会话不落盘。② Desktop 和 CLI 不能自动互通对话历史，官方唯一支持的桥接是 CLI 里运行 `/desktop` 把当前 CLI 会话单向搬进 Desktop（搬完 CLI 退出），反方向没有入口。它们共享的只是配置和项目记忆（CLAUDE.md、settings、MCP、hooks、skills），不是对话记录。
