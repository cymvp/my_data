## 1. 今天获得的知识与技能

### multipart/form-data 里的数组要传重复字段，不能逗号拼接

这是今天那个 bug 的技术核心，也是一条值得记住的通用知识。

MinerU 解析服务的 `lang_list` 参数在 OpenAPI schema 里是 `type: array`。**multipart/form-data 传数组的正确方式是重复同名字段**（`lang_list=japan&lang_list=ch&lang_list=en`），而 CSRS 把它拼成了一个逗号字符串。服务端于是**把 `"japan,ch,en"` 当成一个语言名去查表**，查不到就返回 409。

实测对照很干净：

| 传法 | 结果 |
|---|---|
| `lang_list='en'` / `'ch'` / `'japan'` | HTTP 200 ✅ |
| `lang_list='japan,ch,en'`（逗号字符串） | **HTTP 409** ❌ `Language japan,ch,en not supported` |
| `lang_list=['japan','ch','en']`（列表） | **HTTP 200** ✅ |

**MinerU 本来就支持多语言，是调用方传错了。** 代码注释「逗号分隔传给 mineru-api → pipeline 模型按区域选最优」里，**设计意图是对的，实现时把列表拼成了字符串**，所以那条多语种兜底路径**从引入那天起就没有一次成功过**。

### 三个让日志说谎的机制

这个 bug 难查不是因为它复杂，是因为**日志把真相盖住了三层**：

| 现象 | 真相 |
|---|---|
| 错误写「Docling conversion failed」 | 那是**包住整个 loader 函数体的兜底 `except Exception`**（`document_loader.py:338-341`），它给**任何**异常都贴 docling 的标签——包括 MinerU 兜底抛出来的 |
| 字段 `parse_engine: docling` | 记的是**请求时声明的**引擎，**不是实际用的那个** |
| 409 里没有服务端的错误正文 | `httpx.raise_for_status()` 只抛状态行，**服务端写的 `Language ... not supported` 被丢掉了** |

**三条合起来的效果是：真正的失败点（MinerU 的语言参数）被伪装成了 docling 的解析失败。**

### 两个 bug 串联，缺一不发作

### 触发 OCR 的是解析方法，不是语言数量

这条是纠正自己的断言。原先说「三种语言会各跑一遍 OCR，白花时间」，实测：

| | 耗时 |
|---|---|
| 单语言 `[en]` | 3.6s |
| 三语言 `[japan,ch,en]` | **3.5s** |
| 三语言 + 强制 OCR | 4.7s |
| 单语言 + 强制 OCR | 5.0s |

决定走不走 OCR 的是 `parse_method`：`auto`（默认）**只有扫描件页才 OCR**，有文本层的 PDF 直接抽文本、`lang_list` 根本用不上；`ocr`（`ocr_mode=force`）才全页强制 OCR，这时语言影响的是**选哪个 OCR 模型**，MinerU 是按区域选模型而不是逐语言重跑。

### CSRS 的解析链路（今天完整查清的）

这条链路此前没人完整写下来过，今天是靠一步步实测拼出来的：

```
gateway parse_upload
  → docling 解析（DOCLING_SERVICE_URL，一台真正的 docling-serve）
  → MD 质量门：检查 docling 是不是丢内容了
      ├─ 没丢 → 成功                    ← 8 页小文件走这条，34.5 秒
      └─ 丢了 → 兜底 MinerU              ← 334 页大书走这条
                 → 10.121.6.98:8000/file_parse
                 → lang_list 参数出错 → 409
```

几个要点：
- **`10.121.6.98:8000` 上只有 MinerU**。它的 `/v1/convert/file`（docling 的接口）返回 404，只有 `/file_parse`、`/health`、`/tasks`
- 真正的 docling-serve 是**另一台**，由 `DOCLING_SERVICE_URL` 指向
- 质量门的开关是 `md_quality_gate_switch_engine`，代码在 `csrs/loaders/document_loader.py:218`
- 服务的 `max_concurrent_requests: 3`，且**不支持列任务**（`/tasks` 看不到别人提交了什么），所以排查时无法从服务侧看 dev 发了什么参数

### 用户今天的纠正，按主题归类

**主题一：文档要从读者视角写，不是从做事者视角写。**

这是今天最集中的一类，用户说得也最完整：

> 「论述 eval 的可信性的时候，你可以从**你做了哪些实验来验证**的角度写，不要『先考判官，再看它的判决』『考题和真题打乱盲评，判官不知道哪条是考题』这种**没头没尾的话，其他读者根本看不懂**。**你出发的角度是读者不知道上下文，要通过读这个文档来了解结果并要知道前后的因果推导关系。这是写文档很重要的点，你看下是不是应该写到输出内容/文档的 skill 里。**」

**主题六：不要为每个输入写定制逻辑。**

> 「**不需要让程序来实现每个 PDF 都可能不一样的定制的逻辑。你先不要着急动手，先 review 一遍目前应不应该让程序补逻辑。**」

配合前一天那条「解析目录的方式太定制了」，这是同一个要求的第二次出现。用户还从另一个角度问过：「这种方括号的匹配是定制的逻辑么？**换句话说，换一本书后的代码还能生效么？**」

**沉淀**：写解析逻辑时的自检问题是「**换一个输入这段还成立吗**」，而不是「这个输入能跑通吗」。

**主题七：能测就别推。**

> 「切词的逻辑都在 CSRS 的代码里，**你测试一下不就行了么**？」

同类：「i01 那条，应该是让程序+LLM 来进行判定的啊，**为什么是你核错了呢？给我 root cause**」——用户要的是根因，不是道歉。

### 今天自己犯的错，按形状归类

**形状一：拿自己复现出的错误去解释别人的错误。**

这是今天最贵的一个。我直连解析服务**没传 backend**、触发了一个 VLM 未配置的 409；dev 那边也报 409。**我就拿手边这个 409 去套 dev 的那个**，从而认定「VLM 没配、所有文件都解析不了」。

实际上它们是**两种完全不同的 409**。之所以套得上，是因为 `raise_for_status()` 把服务端的错误正文丢了，日志里只剩状态码——**当证据被截断时，最容易发生的就是拿一个已有的解释去填那个空。**

**沉淀：同样的状态码不等于同样的原因。在拿到服务端的错误正文之前，不要给 HTTP 错误码归因。**

**形状二：没验证就断言。**

「三种语言会各跑一遍 OCR、白花时间」——说完之后用户追问「触发 OCR 的条件是什么？」，一测才发现耗时几乎相同（3.5s vs 3.6s），**触发 OCR 的是解析方法不是语言数量**。

这和昨天记的那条是同一个毛病的不同表现。**沉淀：凡是带「会导致/会变慢/会跑 N 遍」的因果断言，要么给出实测，要么明确标成推测。**

**形状三：git 操作里的「先合并再覆盖」。**

`.env` 冲突那一段：手工合并好了 → `git add` 暂存（不该暂存）→ 取消暂存时用了 `git checkout --ours` → **把刚合并好的内容覆盖掉了，用户的配置行丢了**。

`git checkout --ours` 在冲突场景下取的是**冲突前的一方**，不是「我刚编辑好的工作区版本」。要取消暂存应该用 `git restore --staged`，它只动索引不动工作区。

**沉淀：任何会写工作区文件的 git 命令，在手工合并之后都是危险的。取消暂存用 `git restore --staged`，不要用 `git checkout`。**

### 今天有效的做法

- **验证测试本身是否有效。** 加完 6 个单测后，特意回退修复再跑一遍，确认 5 条会失败——**不做这一步，测试可能根本测不出东西**。
