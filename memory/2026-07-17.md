## 1. 今天获得的知识与技能

**"赔率"作为投资决策语言。** 在 ai-berkshire 的报告里，"赔率"不是单个数字，而是三情景（乐观/中性/悲观）结果的不对称程度：押对能赚多少 vs 押错会亏多少。好赔率是"赚的空间大、亏的空间小"。cuiyang 今天专门问了"赔率越高越好还是越低越好"，答案是越高越好，但必须补两点：一是赔率高不等于该买，还要乘以胜率才是期望收益；二是赔率是价格的函数不是公司的属性，同一家公司股价跌一半，赔率就从差变好。巴菲特的"安全边际"用这套语言就是"只在赔率明显偏向你的价格出手"。这条对未来帮 cuiyang 分析任何标的都适用。

**核心-卫星投资组合策略（core-satellite）。** cuiyang 今天不熟悉这个概念，问了"什么是卫星仓、核心仓"。核心仓（core，占 50-60%）放最有把握、波动小、能长拿的标的，求稳；卫星仓（satellite，占 25-35%）放确定性略低但弹性更大的标的，增强收益；此外还有期权仓（5-15%），放可能归零但赔率最高的高风险标的。三档关系是确定性递减、弹性递增、仓位递减。注意"期权仓"是仓位分层的比喻（借用期权"损失有限、潜在收益大"的特征），不是真的股票期权合约——cuiyang 一度误解，以为报告说某人持有期权合约，需要澄清。

**量价分析框架（放量/缩量 × 涨/跌）。** cuiyang 问"放量缩量结合涨跌怎么判断该不该跑"。四象限（放量上涨=资金真进、缩量上涨=惜售、放量下跌=最需警惕、缩量下跌=失血或洗盘）之上，最重要的维度是"位置"：同样的量价信号在高位和低位含义完全相反。高位放量下跌是主力出货（风险最高），低位放量下跌往往是恐慌最后一跌（抛压衰竭）。最该跑的组合是"高位+放量大跌+跌破关键支撑"。这套框架提高胜率不提供确定性。

**Claude Code / Anthropic 计费认知。** 模型看不到自己会话的计费统计，精确 token 数要用户在 CLI 里跑 `/cost`（或 `/context` 看上下文占用）查看。多 Agent 调研任务里 input 远大于 output（通常 90%+），因为每次工具调用要把累积上下文重发给模型，大部分走 prompt cache（按 cache read 计费，单价约为普通 input 的十分之一）。看成本要看美元金额而非 token 数。

**变更数据捕获（CDC）vs 应用层事件的可靠性差异。** 这是今天 umu/prove 最有价值的技术认知：数据库 binlog 是写库的自动副产物（写成功 binlog 必然产生，Canal 抓取后 at-least-once、可从 offset 续读、最终一致，可靠性高）；应用层发 Kafka 消息是 best-effort（不在数据库事务里，写库成功但发消息失败就永久丢，还有主动降级开关在大流量时直接不发）。两条通道输入同一个事件，平时都能送达所以结果近似，但可靠性等级根本不同。

## 4. 经验与教训

**工程师的口述架构必须逐条对代码核实。** 今天课程组工程师口述的五条架构描述里三条与代码有出入（"两表都消费 binlog"错——action 表是 Kafka 应用事件；"两表每行为一条记录"错——completion 是每学员一行的聚合表；"action 表只 insert 不 delete"错——有物理删除路径）。但纠错过程反而挖出了最有价值的差异（取消行为导致参与被收回）。教训：别把口述当事实，也别急于下相反结论——AI 自己上一轮有两处判断也需要收回，读了 Merak/Megrez 后才闭环。

**口径治理的判据："稳态收敛"。** cuiyang 拍板了"数字可不等、业务定义相同即同口径"的标准，AI 补充了可检验的判据：两条路径在稳态下（无结构变更、消费追平、无降级）应收敛到同一数字——收敛则同口径合并（差异是时效），稳态下也不收敛则是定义分叉必须异名。配两个护栏：合并登记必须附两侧判定式的 file:line 证据（防"看名字像就合并"）；合并指标的回答模板强制带来源+时效声明（用户拿语义层答案和页面一比对不上会以为 AI 答错）。cuiyang 认可这是语义层建模的正确方向，但要求把规则升级成可检验形式而非靠感觉。

**cuiyang 会追问判断依据，要能拿出数值实证而非只从代码推。** 他问"方法 A 和方法 B 读不同表，你如何判断口径一致"，AI 的完整论证是三层：同表血缘（B 是 A 输入表的派生聚合）+ 同一判定谓词（file:line 对照）+ 稳态收敛数值实证（逐学员对账全等）。之前只从代码推、没做数值实证的那一环被他问出来后当场补了实测。教训：涉及口径一致性的结论，代码推断不够，要有真实数据对账。

**实测环节永远给意外信息。** apolo 实测发现常用验证企业 2614 从没触发过进展趋势配额导入、BI 明细表对它全空，导致评测企业选型要重新定；还发现人均时长分母（822 人）> 参与人数（814 人），时长埋点是独立采集通道含纯浏览者。这些不跑真数据根本发现不了。教训：不基于文档/schema 假设，跑真实查询。
