## 1. 今天获得的知识与技能

- **本体（Ontology）是什么、在数据问答里干什么**：本体是"表之上的一层说明书 + 索引"，它不搬数据、不替代数据表，读数据的永远是打到原表的 SQL。本体负责回答"某个业务概念的数据在哪张表、字段什么含义、口径怎么算"。cuiyang 当天从"刚接触本体概念的程度"深入到能独立评判架构，这是今天最大的知识增量。
- **本体的五/六件套 YAML 结构**（cuiyang 现在能看懂）：TBox 是名词表（业务里有哪些概念，每个概念带 layer 分层标注离原始事实多远：L0 原始事实、L1 结构化抽取、L2 派生判断，层级即证据强度）；RBox 是语法（哪些概念之间允许发生什么关系，带 domain/range，且必须能解析到 TBox 里真实存在的概念）；Enums 是每个概念的合法取值；Axioms 是铁律（每条公理带 enforced_by 指向代码里的校验函数，没实现的用 pending 哨兵占位）；CQ registry 是"这套本体必须能回答的问题清单"，等于验收标准；Profile 是"拿这套本体去干一件具体活的合同"。
- **CQ（Competency Question，能力问题）的两种用法**：在 Monster Revenue（固定流程产品）里，CQ 只做设计验收，等于对系统自动生成产物的质量要求，落成回归测试（改了 prompt 或本体导致产物缺东西，测试就红）。cuiyang 的 Prove 把 CQ 多用了一层：用户的自然语言问题在运行时匹配到某条 CQ，用作问答路由。
- **指标（Metric）作为本体一等公民**：指标不做成 TBox 的属性，而是独立概念，因为一个指标会被多个本体影响，指标自身还要挂维度。每个指标在 metric-registry 里绑定一个确定性 SQL 模板（表、字段、聚合方式、可下钻维度），LLM 只选指标、不写 SQL、不产生数字。
- **apolo 数据查询通道**（新掌握，已沉淀成全局 skill）：`https://apolo-aws.umu.work/sqlquery/` 是 Django 做的运维查询平台，登录后走 `/query/` 接口 POST（集群名 + 库名 + SQL）返回 JSON，可脚本化调用。关键限制：它是 AWS 海外侧入口，集群只有 JP/COM/TW/US，**没有 CN**。账号 cuiyang@umu.com / 密码 Umu_1012（存在 prove/.env，未进 git）。
- **Claude Code 会话的存储与迁移**：会话按"工作目录编码后的路径"归档在 `~/.claude/projects/<路径编码>/<会话id>.jsonl`。把会话迁到新项目目录，就是把这个 jsonl 复制进目标项目对应的编码目录，再 `cd 新目录 && claude --resume <会话id>`。`/compact` 不会换会话 ID。判断哪个会话文件正在被写，看文件修改时间 + tail 最后一行。

## 4. 经验与教训

- **对照实验要防"评分器冤枉基线"**（cuiyang 自己在心得里强调的原则）：消融实验第一轮基线更难看（6-7/15），复查发现是评分器把回答里的千分位逗号（"42,715"被拆成两个数）、企业号 2614 误判成编造数字。修掉这些伪影再下结论，数字变好看了但可信了。做任何 A/B 对照，先确认失分是真失分还是评分 bug。
