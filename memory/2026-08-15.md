### csrs：崔扬提的方案（a），在三个月前被他自己的反例否决过

崔扬为图检索隔离提了两个方案：(a) `agent_id` 数组化、(b) 把隔离上下文放到边上。

**查历史文档发现，方案 (a) 在 2026-05-14 就被评估并否决过，而否决理由正是崔扬自己提的反例**（`2026-05-14-todo13-c1-revision-spec.md` §1.1 原文）：

**但方案 (a) 里的兼容规则是真正的亮点**：存量记录全是单值，按规则全部放行 → **graph 路立即从 0 恢复，不需要停机回填**；新数据逐步累积成数组开始真正过滤。**这等于给出一条可以今天上线、又不把长期方向锁死的路径**，比单纯删掉判定更有演进空间。

**方案 (b)** 与 `2026-05-14-graph-isolation-context-on-edges-brainstorm.md` 同源（也是崔扬提的，当时评估工作量 weeks、列了 7 个 open question、决策为「未排期，待独立 spec 化」）。**它的主要障碍是存量无法可靠回填**：Entity 到 Entity 的关系边**没有记录任何创建来源，反推不出是哪个 agent 建的**。

### Slack 链接是拼出来的，不需要逐条查

**结论：链接完全由消息的时间戳和频道 ID 拼出来。**

每条 Slack 消息带一个 `ts` 字段（如 `1785114801.010269`），它既是发送时刻（Unix 时间戳，精确到微秒），也是这条消息在这个频道里的唯一编号。网页链接规则是：

```
https://umu-cn.slack.com/archives/C09A15KCZ6U/p1785114801010269?thread_ts=1785114801.010269&cid=C09A15KCZ6U
└──── 工作区域名 ────┘└─ 频道 ID ─┘└─ p + 去掉小数点的 ts ─┘└──── 打开线程用的参数 ────┘
```

四块我们手上全都有：**工作区域名**启动时调一次 `auth.test` 拿到并缓存；**频道 ID** 配置文件里就有；**时间戳**抓消息时 Slack 一起给的；**两个查询参数**是固定写法。

**实测对比过 `chat.getPermalink` 的返回值**：对线程首条消息，它给的路径和两个查询参数与我们拼的**完全一致**（三个频道各取一条真实消息验证）。所以不再逐条调 API——一周几十个话题就是几十次问询，省下来很值。

**举个例子**：图书馆的书用「第几层第几排第几本」定位。你已经知道楼号（工作区）、房间号（频道）、这本书的编号（时间戳），那「3 楼 A 区 12 号」这个位置说明你自己就能写出来，不用跑去问管理员。之前担心的是 Slack 的写法有没有额外花样（比如编号还要做转换），所以先拿三条真实消息问了「管理员」，发现一模一样才决定不再问。

**域名不是写死的**，是启动时问 Slack 要的（`auth.test` 返回 `url = https://umu-cn.slack.com/`）。将来工作区改名或换域名，程序自动跟着变。

### 不能让模型写 URL：拆成「打编号」和「换链接」两步

**模型写 URL 必然把时间戳编错**——那是 16 位数字，它没法记住也没法推导。所以：

1. 交给模型的对话记录里，每条讨论的**首条消息**前面打一个编号 `[S1]`、`[S2]`（线程内的回复不单独编号，一段讨论只需要一个入口）。prompt 第 9 条：每段末尾写一行「来源：[S1] [S3]」
2. 代码把这些编号换成真链接

**三条实现细节都是防错的**：

- **编号在整份摘要里唯一。** 消息多到触发分批时，第二批接着往下编——否则两批各自的 `[S1]` 指向不同讨论，替换时必然张冠李戴
- **模型偶尔会编出记录里没有的编号，那种直接丢掉**
- **整段一个都对不上就把这行删掉——绝不留打不开的链接，也不留裸标记**

### 学习任务那一族要分四道题问，因为它最容易出的错是分母认错

| 口径 | 分配 | 完成 | 完成率 |
|---|---|---|---|
| **人** | 719 | 618 | 0.86 |
| **任务** | 2167 | 1881 | 0.868 |

**这张表怎么读**：两行的「完成率」都叫「学习任务完成率」，而一个是 618÷719、一个是 1881÷2167，**分母根本不是一回事**。

**合成一道题问的话，系统答哪一个都能算过，分母认错就测不出来了。** 所以拆成四道单口径的题。

### 一个判据可以「看起来对」而其实在搜文案

给「复合提问被误拆」写靶子时，第一版把判据写成「文案里有没有『个问题』」，**测试也全绿**——因为拆开时的文案正是「这句话里有 2 个问题」。

**区分办法**：把普通拒答那条测试的文案换成「无法回答这个问题：缺少课程 ID」——**「这个问题」里就含着「个问题」三个字**，判据一旦退回搜文案当场红。

**正确的判据是看结构**：链路拆句子时会把子问题标成 `sub_question` 类型，看这个，不看文案。

**另外，拒答有四五种，只有「复合被拆」是缺陷，其余都是正确行为。** 所以报告只写「拒答」不够，要说清是哪一种。

### 「间歇通过」既不适合进评测集，也不适合标 known_fail

复合提问那道题没有顺手加进评测集，理由：

- **进评测集**：它会是一道会抖的题，而 2026-08-04 正是为了这个把复合原题拆成两道单句题
- **标 `known_fail`**：那个标记通过时报 XPASS，提示「有人修好了」——**而间歇通过两者都不是**

### 「先测再设计」推翻了一个已经排好的修法

c46/c47 两道题原本的计划是给目录路由加可达性守卫。实测三轮之后发现**原来的方向对不上现在的病**：

- **c46**：一轮正确作答、**两轮反问**（让用户在两个参与人数口径之间选）——**那两轮其实是正确行为**，同名多口径判不清该反问，这是崔扬定过的。所以它差的是**期望值该放开**，不是差守卫
- **c47**：三轮全拒答
- 而可达性守卫管的是「指标够不够得着问句点名的对象」。**现在既够得着、参数也补得出，那道守卫接上去也不会红**

试了一个修法（把补参声明从通用表改成按本次问句算好的三态，省掉模型自己做连接那一步），**没有改善**——c47 从 1/3 变 0/3（n=3，不当结论）。

**但拒答理由现在很清楚，而且自相矛盾**：

> 当前给定的是 exam_id……course_id 仅能由 exam_id 补上（**不包含由题干给的测评小节 ID / ExamSession 概念补课**），因此无法结构化定位到具体 course_id

**它先说给定的是 exam_id，又说题干给的不是 exam_id。载荷里两段都写明了、它也都读到了，还是拒答。**

**举个例子**：像给人一张纸条写着「你手上的是 A 号钥匙」，再给一张写着「A 号钥匙能开 3 号门」，他念完两张纸条，然后说「可是我不确定我手上这把是不是 A 号」。**再写第三张纸条没用。**

下一步的候选是**在路由之前就把能补的 ID 真的查出来**，让模型看到具体的值而不是一条规则。**这件事等崔扬拍。**

## 4. 经验与教训

### ⚠️ my_data 是公开仓库，而我一直默认它是私有的

**实测确认，不是推测**：匿名 curl（不带任何凭据）能直接下到 `memory/2026-08-14.md`，HTTP 200、35151 字节全文返回；同一条命令请求一个不存在的仓库返回 404。

**我的错在哪**：`loop_tasks.json` 里明确标着「my_scripts 是公开仓库，会被 Slack 扫描吊销」，**我把这句反推成「my_data 不是公开的」——这个反推从来没有验证过。** 而 `/ycui-daily-memory` 这个 skill 自己也写着「涉及人名/敏感信息照实记（**这是私人 memory 仓，用户自己看**）」，**那句话的前提是错的。**

**后果**：memory 目录里 8/04 起的每日文件已经全部公开，含 UMU 内部系统架构、数据库与表名（`Doris_JP` / `jp_umu_slave` / `mycat_jp` / `prove_dw` 等）、**一个尚未修复的隔离缺陷的完整利用路径**、内部评测数字、汇报对象与同事名字。今天又多了专利事务的当事人、编号、代理机构联系电话。

**因此今晚做的两个决定**：① 没有按 `/ycui_sync` 的 `git add -A` 提交新出现的 `专利/OA2答复/`（7.9 MB、10 个文件，**尚未提交的专利答复草稿，推到公开仓库等于公开发表**）；② **这份 memory 文件只写在本地，没有 commit、没有 push。**

**通用判据：涉及「发布到外部」的动作，仓库可见性这类前提必须实测一次，不能从相邻事实反推。** 一次 `curl -o /dev/null -w "%{http_code}"` 就能确认，成本几乎为零，而推错的代价是不可逆的。

### 「先测再设计」今天推翻了一个已经排好的修法

c46/c47 原计划是加可达性守卫，实测三轮后发现守卫接上去也不会红——**病和药对不上**。而且发现 c46 那两轮「反问」其实是**正确行为**，它差的是期望值该放开。

**判据：修法排进计划之后、动手之前，先跑一次实测确认病还在、而且还是原来那个病。** 计划是几天前写的，而这个仓库每天都在变。

### 「等你确认」的清单也会过期

上一轮报「spec A 等你确认」是照着 08-12 的交接文档说的，**而那份文档写在实施之前**——实际上 08-13 已经全部做完、崔扬也已经拍过三个决定。

**判据：向对方报「等你拍」之前，先核一遍这件事是不是已经被拍过或已经做完了。** 尤其当依据是一份交接文档时——**交接文档记的是交接那一刻的状态，不是现在的状态。**

### 三个月前被否决过的方案，今天又被提了一次

崔扬提的 `agent_id` 数组化方案，2026-05-14 就被评估并否决过，**而否决理由正是他自己当时提的反例**（配对信息丢失）。

**这不是谁记性不好的问题——是这个仓库的决策记录没有被检索到。** 有效做法：**给出方案对比之前，先搜一遍 `specs/` 和 `brainstorm` 类文档里有没有同名或同源的讨论**，今天就是这么发现的（`2026-05-14-todo13-c1-revision-spec.md` 和 `2026-05-14-graph-isolation-context-on-edges-brainstorm.md`）。

**而且发现之后的正确处理不是「你这个提过了」，是把当时的否决理由和今天的场景差异写进 spec**——今天的差异是配对维度从 (user, agent) 变成了 (dataset, agent)，**结论仍然成立，但要说清为什么仍然成立。**

### 判据可以「看起来对」而其实在搜文案

把「复合提问被误拆」的判据写成「文案里有没有『个问题』」，测试全绿——因为拆开时的文案正好是「这句话里有 2 个问题」。**测试绿不代表判据对。**

**验证办法：构造一条文案里含关键词、但结构上不该命中的用例**（「无法回答这个问题：缺少课程 ID」——「这个问题」里含着「个问题」）。判据一旦退回搜文案，这条当场红。
