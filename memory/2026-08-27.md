## 1. 今天获得的知识与技能

### 「把 LLM 判断蒸馏成查表」这个思路，以及它的适用边界

cuiyang 提出的原话是：离线收集大量 trace，摸清 LLM 在各种**状态变量取值组合**下会把状态判成什么，然后把这个映射写成程序；下次遇到同样的组合直接出结果，不走 LLM。目的是**省成本 + 提速**，不是提升准确率。

他明确排除了两个常见反驳：一是不担心组合数爆炸——只要实际运行落在有限几种组合里就有命中率，只做那几种；二是「LLM 会偏离 prompt」是另一件事，跟蒸馏分开解决。

判断某个评估器适不适合这个场景，看两个量：**可枚举的状态变量多不多、要读的对话文本多不多**。变量多、文本少的适合（StageEvaluator），靠自然语言判定的不适合（ConcernObjectionEvaluator 的状态推进）。这是 cuiyang 自己给的判据。

### roleplay 的一轮对话有 5 次 LLM 调用，只有 2 次与 stage 有关

这是今天弄清楚的事实（代码在 `coordinator.go:393` 的 `runParallelEvaluations`）：

| 调用 | 产出 | 和 stage 的关系 |
|---|---|---|
| StageEvaluator | `current_stage_type` / `current_stage_id` | 直接产出 |
| ConcernObjectionEvaluator | 关注点、异议的状态 | 是 stage 判定的**输入** |
| TrustEvaluator | 信任分 + 进展摘要 | **不参与**（stage prompt 6 个占位符里没有 trust） |
| CustomerAgent | 客户台词 | 不产状态 |
| InfoExtraction | InfoPool | 不参与 |

两个结构性缺陷也一并确认了：

- **信任只经由对话文本间接影响 stage**，不经由状态字段——信任低 → 客户演得更冷淡 → 下一轮 stage 从对话记录里读出来。
- **ConcernObj 的输出落后一轮才被 stage 看到**，因为三个评估器并行跑，传进 stage 的是合并前的状态（`coordinator.go:294`）。

### 一个可复用的坏味道：已声明的事实被丢弃，再由另一个 LLM 重新推断

roleplay 里发现的具体形状（记为「发现 A」）：Customer 的输出格式要求带模式标签，`[信息传递]` 或 `[异议提出]`（customer prompt 第 91 行）。代码用 Apollo 配的正则识别这个标签，**目的是把它切掉**，切完标签就被丢弃——Go 代码里除了这个正则再没有任何地方引用「异议提出」四个字。然后**下一轮 ConcernObj 从对话记录里重新推断「客户提出了异议」**，把状态从 `unvoiced` 改成 `voiced`。

同一个事实：Customer 明确声明 → 代码识别到 → 扔掉 → 另一次 LLM 调用从自然语言里再推一遍。改法是把切掉的标签存进本轮状态。

### 「本质是计数器」和「本质是布尔」的语义判据，可以退回代码

- `stalled`（关注点卡壳）的 prompt 判据是「销售**一直未能**命中兴趣点」——这是跨轮判断，**代码算得比 LLM 准**，因为代码有完整历史而 LLM 只有 5 轮窗口。第 12 轮时 LLM 根本看不到这个关注点在第 3 轮就已经 activated。
- `value_demonstration` 和 `objection_handling` 的**全部**进入/维持/完成条件都是布尔运算（`len(concernPoints)==0`、「全部为 concluded 或 stalled」、「所有异议均为 resolved 或 mitigated」）。

一句话收束：**stage 评估器现在这次调用里，大部分工作是替代 if 语句，小部分是真判断。**

还有一个比省钱更重要的发现：那几条一次性达成的语义验收标准（如 opening 的「确认了议程、时长和目的」），**在 5 轮窗口滑走之后 LLM 已经无法复核了**——所以该做的不是「换成代码」，而是**把一次性达成的语义事实固化成单调标记**。这是正确性缺陷，不只是优化机会。

### GUMO：通用用户模型本体，以及它的字段该怎么用

GUMO（General User Model Ontology）是学员画像项目参照的本体，有 25 个元字段。今天争清楚的核心是**四个位置各装什么**，对照的是 GUMO ch4 第 60 页那个「发色」的例子：

```
auxiliary（辅助词） = has property   ← 动作
predicate（谓词）   = hair-colour    ← 属性名
range（取值域）     = hair-colour-range
object（取值）      = red
```

cuiyang 反复纠正的一点，最终成立：**在 GUMO 里，辅助词代表动作，谓词代表属性名（他表述为「宾语」那一侧），不能用谓词代替动作。** 我一度提议把 `scale` 改名叫「属性」，被「我在公司的职级是技术经理」这句话证伪并撤回——「哪一项属性」是谓词的活，`scale` 对应的是 `range`，只装取值域。

`field` 这个列名也被否了：它是个数据库词，意思是「一列」，**只说了这一列在表里的位置，没说这一列装什么**。这一列装的是动作，名字得说出来。

### 三重冗余的识别方法

拆「我在公司的职级是技术经理」这句时暴露出来：`field`、`predicate`、`scale` 三个位置说的是同一件事，**只有取值带信息**。谓词填了常量（「岗位」）而不是属性名（「职级」），就是它空转的直接证据。改法是谓词改填属性名，词表两条：`岗位`、`职级`。

### 「取次数最高的一条」这类消解策略的两种失效

- 在**每个宾语本来只有一条**的类别上（学情），这条策略什么也没做，是空转。
- 在**同一宾语下真有多条互不矛盾规律**的类别上（教学适配规则），它会**丢数据**：「先给具象引入 / 概念性 / 有效 / 5 次」和「先给具象引入 / 程序性 / 无效 / 2 次」是两条不同适用条件下的规律，二选一会让教练在讲程序性内容时拿到错的结论。

由此引出一个定位修正：既然五个类别的默认几乎都该是「全返回」，**消解机制真正管的不是「多条里挑哪条」（判重已经保证一个键只有一条当前版本），而是「别往提示词里塞太多条」**。后者要的参数是条数上限加排序，不是策略。

### 本体论精读的两篇（都在 arXiv 2026-08-25 提交）

**CES-PK（arXiv 2608.24824，正式版在 KI 2026 / LNCS 16830）**：给 KGQA 的答案挂一层事后符号校验。不做完整语义解析，只从问题抽**必要条件**去否证候选答案。核心是**三值语义**（满足/违反/**未知**）——开放世界下「图里查不到」只能算 unk 不能算假，否则正确答案会因图谱缺边被误删。三类约束分工完全不重叠：**排除约束 `¬R(x,y)` 是唯一能产生「违反」的**，承担几乎全部过滤；**关系约束 `R(x,y)` 在开放世界下永远产生不了违反**，只能在被满足时提供支持分。Hetionet 上 Q2 精确率 0.17→0.62，召回恒为 1.0——但这是受控实验，候选集是人工掺假造的。

**Meor（arXiv 2608.24273）**：指出持续学习领域一类性能下降**被长期归错了因**。大家把历史性能下滑记在「灾难性遗忘」头上去修参数，但图谱每进一个新实体，它就自动进入所有兼容查询的候选集，历史答案会掉名次——**哪怕分数没变、相对所有老实体的排序也没变**。作者命名为**候选集干扰**，判别方式是同一 checkpoint 上把同一查询在「旧宇宙」和「当前宇宙」各评一次，差值 D_MCI 就是纯由入场造成的损失。最值得记的一句：**当前宇宙评测能暴露这个效应，但它不提供任何控制它的训练规则**——会测 ≠ 会治。

## 4. 经验与教训

### 产物是「成功」的证据，不是「运行」的证据

这条是 8/26 沉淀的，今天第 4 次故障又验证了一遍。`pulse_store.jsonl` 停止写入不等于程序停了——`collect_snapshot` 在 fetch 失败时**不写 store**（这是对的设计，不写脏数据），所以界面静止如实反映了「取不到数据」。诊断必须**同时取成功证据（store）和运行证据（进程、网络连接、日志）**。

### 四次同症状、四个不同根因——所以要改的是可观测性，不是加 watchdog

stock_watch 界面不动这个症状出现了 4 次：① 8/24 macOS Tk 重绘冻结（后端完全健康）② 8/25 延迟感知偏差（实测 0.58–0.75s 正常）③ 8/26 sina 单点路径退化（TCP 连得上、SSL 握手挂住）④ 今天本机出口网络抖动（连 DNS 都解析不出，最后一条错误是 `[Errno 8] nodename nor servname provided`）。

**我 8/24 提的 `_fetching` watchdog 方向提错了**，因为四次里没有一次是「线程卡死永不返回」——线程每次都正常返回，只是返回的是失败。真正有用的是**在界面上显示「上次成功更新时间」或失败标记**。今天已向 cuiyang 修正了这个建议，等他批。

### 我诊断时说错过一次，纠正的方式值得记

我用 `dig` 查不到就推测「DNS 挂了」。实际上那只是 `dig` 直查企业内网 DNS（172.24.200.9）不响应，而**系统解析器当时是好的**（`socket.gethostbyname` 正常返回）。真正证明程序侧遇到 DNS 失败的是日志里 11:08:53 那条 `Errno 8`。

**我测的时点和程序失败的时点不重合，这本身就是「抖动」而非「持续故障」的证据**——同一分钟内我 curl 5 次全超时、几分钟后 6 次全部 200。**采样稀疏会得出错的结论，这已经是第二次踩到**（8/24 那次 lsof 4 秒采样一次，因为连接活不到 1 秒而全部空手；改成 0.5 秒采样后 20 秒内命中 7 次）。

### 单位口径不一致会算出荒谬值，要当场发现而不是报出去

尾盘算大盘量水平时，用指数的 `f[8]` 除以腾讯日K的成交量，得到 **48.26** 这个明显荒谬的值。原因是两个数据源的成交量单位不一致。**换成同一数据源（都用腾讯日K）重算才得到 0.89。** 判断标准很简单：量水平这种比值应该在 0.5–2 之间，48 一眼就是错的。

### 校验命令能否真跑通，要在写进文档之前做

改 `ycui_market_advisor` skill 时，13 个数据源代码全部实测通过后才写进文件。`hf_CAD` 返回 14260 不像铜价，**无法确认它是什么就不写**——宁可少一个指标，不能写一个自己都不确定的接口进去。

### 分开报 vs 平均成一个数

今天新加的有色金属一节第一次跑就证明了为什么要分开：**中国稀土 +8.53%（中重稀土）vs 北方稀土 +2.12%（轻稀土），差 6.4 个百分点**；纽约金 +0.17% 几乎没动，而湖南黄金 +10.02% 涨停。如果按板块平均报成一个数，这些分化全部丢失。**紫金矿业是金铜双主业，单列不能代表金价**——这也是同一类问题。
