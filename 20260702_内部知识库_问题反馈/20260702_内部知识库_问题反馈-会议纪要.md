> 术语说明（首次出现先解释，方便没参会的人看懂）：
> - **CSRS**：本次讨论的内部知识库系统，把代码仓库和文档导入后，供团队用 AI 问答和排查问题。
> - **MCP**：一种让外部工具/数据源接入 AI 的标准接口（connector）。
> - **RAG 召回**：先从知识库里检索出相关片段，再交给大模型生成答案的流程。
> - **chunk（创格/切块）**：把文档切成的小段，检索的最小单位，当前约 1000 字符一段。
> - **rerank（精排/金牌）**：对召回的候选片段用模型重新打分排序，取分数最高的若干个。
> - **LSP**：语言解析器，用来分析代码里函数之间的调用关系（call graph）。

## 核心议题

### 1. 知识源接入：Google Doc 与 Wikia
- **讨论内容**：客户/团队的部分文档在 Google Doc 和 Wikia 上。Google Doc 发来的是 URL（指向 HTML 文档），无法像本地文件那样直接入库；且 Google Doc 内容多、后续还要维护更新，手动下载不现实。Wikia 面临同样问题，但公司绝大部分文档在 Wikia、量相对可控。
- **结论/决策**：优先调研 Google Doc 是否提供 MCP/接口来拉取内容（现在 SaaS 服务基本都在做 MCP connector），不一定走 UI 或手动下载。Wikia 因文档少，必要时可手动下载上传。
- **Action**：调研 Google Doc / Wikia 的接入方式（MCP 或接口）。

### 2. Slack 集成到知识库
- **讨论内容**：团队与中国、日本客户界面的绝大部分知识（产品逻辑、问题排查）都沉淀在 Slack 消息链里，工单系统只是统计，真正的知识在 Slack。希望把这些内容接入 CSRS。争议点在业务而非技术：是把所有聊天原样抓过来，还是只收经人工审核过的总结（避免聊天中间的错误状态污染知识库，类似写代码时中间的错信息会带偏后续结果）。
- **结论/决策**：
  - 采用「**每日 AI 总结 + 人工确认发布**」的方式：用 Slack 的 workflow（参考"木木"里已有的 workflow 做法）每天生成一份频道总结，团队早上看过没问题后点发布，系统再抓取入库；忘了也没关系，隔两三天弄一次即可。
  - 历史积压（已沉淀一年多）：写脚本调 Slack API 把过去的内容按天做 summary 补进来。
  - 后续可考虑入库后还能像文档一样编辑修改，但**近期先不做编辑功能，优先把数据打通**（数据打通最重要），先做出一个能用起来的雏形。
- **Action**：调研 Slack API/workflow 的每日总结与抓取；历史内容 summary 脚本（找会帅一起看）。

### 3. Slack 问答形态：频道模式 + 单轮对话先行
- **讨论内容**：原方案是每人一个 group 单独问答。Eason 要求改成所有人在**一个频道（channel）**里问答，主要动机是让团队能看到客户界面同事问的问题和 AI 回答，避免回答不准确却被当成正确答复给了客户、没人纠正。随之带来上下文与权限问题：
  - **权限**：频道里的人默认都有提问权限，后端不再单独做权限调研（加进频道即有权限）。提问时需要 @ 机器人（Slack app/后端注册的应用，未来可能换成 agent）触发。
  - **多轮上下文**：多人在同一频道混聊会互相干扰上下文。可通过 Slack thread（消息串）区分——一个主题开一个 thread，相关追问在 thread 内继续，机器人通过 Slack 接口能拿到该 thread 的前若干条对话作为上下文。但这对用户使用习惯有约束。
- **结论/决策**：
  - 形态从 group 改为 **channel**，加人进频道即自动获得提问权限（不做额外权限管理）。
  - **先只做单轮问答**（用户每次把上下文说清楚），多轮对话后续再看怎么做，先推着上线出雏形。
- **Action**：实现 channel 模式；单轮问答先落地；多轮/thread 上下文方案后续评估。

### 4. 前端代码库导入
- **讨论内容**：客户经常问前端相关问题（如支持哪些文件格式），需要看前端代码逻辑来排查，因此要把前端 codebase 也导入 CSRS。目前后端 backend、考试相关库基本已导入；7-11 等定制化的也放了，MEDIA 那个暂时没放（可先不放）。前端核心库位置还不确定——游泳说在 USD 组下，具体哪个是核心库需再确认。
- **结论/决策**：把前端 codebase 加进来；先确认核心库是哪个。
- **Action**：婷婷/评评确认前端核心库（问游泳），然后导入。

### 5. 代码库版本与分支管理策略
- **讨论内容**：CSRS 导入代码时是对仓库当前状态做**快照**，同一文件只保留一个版本（默认跟踪最新 master）。7-11 是客户本地化部署、单独拉了分支、这两三年基本没动，需要按历史版本单独查；而 master 会随功能演进不断覆盖文件（即使某文件本身没改，也可能因被引用的代码变化而间接变化），无法保留 7-11 当时的样子。
- **结论/决策**：
  - **7-11 单独做一份静态隔离**（相当于物理拷贝一份，通过给仓库添加分支信息隔离），与 master 完全分开、各查各的；主线仍以 master 为主。目前只有 7-11 这一个客户需要这种定制隔离（本地化部署、很特殊）。
  - **增量更新按发版节奏**：CO 与 CN 差两周、以 CO 为主，CO 每两周发版就同步更新一次；更新范围通过查 git 确定，需让开发方提供每次发版的 release version（版本号）。
- **Action**：与开发对齐 release version 提供方式；按两周节奏做定期增量导入。

### 6. Go / PHP 缺少调用关系（影响召回质量）
- **讨论内容**：Go 和 PHP 目前没有 LSP 解析出的函数调用关系。增量导入本身能做（识别到文件更新就删旧节点、导入新节点），但因为这些节点没有调用边、都是孤立的"孤儿节点"，不影响导入流程，但**严重影响召回质量、答案不准确**——而回答不准对客户问答影响很大。
- **结论/决策**：尽快补上 Go、PHP 的函数调用关系解析。
- **Action**：婷婷/后端尽快补 Go、PHP 的调用关系（call graph）。

### 7. 全量大仓库导入卡住
- **讨论内容**：后端约 20 个仓库，全量导入大仓库时经常卡住（并发/阻塞问题）。
- **结论/决策**：排查并解决全量导入的卡顿问题。
- **Action**：后端解决全量大仓库导入卡住的问题。

### 8. Cloud Code 使用与代码权限
- **讨论内容**：客户界面团队目前用 TRAE（字节的工具，内部集成了 Cloud Code）或 Cloud Code，通过 MCP 接入 CSRS 查询（用 to_query 加自己写的查询逻辑）。公司规定客户界面团队**不应看到后端代码**。当前只在 prompt / Skill 层做了软性限制，没有硬限制——理论上通过"代码调用链路"等提问仍可能看到代码内容。Skill 目前一个 Skill 对应一个 Repo，检索时每次现找、比较慢。
- **结论/决策**：
  - 代码可见性目前靠 prompt/Skill 软约束，硬限制尚未做（后续可能在 PostIngest 生成的 Skill 侧加限制）。
  - 优化方向：把库的文档信息预加载进 Skill；做一个**索引所有 Repo 的 Skill**（说明每个 repo 是什么），加快检索，避免每次慢查。
- **Action**：婷婷做 Repo 索引 Skill 并分享给评评；完善库文档并预加载。

### 9. UAS 客户反馈——问题三：文档引用不全 / 召回不稳定
- **讨论内容**：客户（药企，如柏林格，对准确性要求极高）反馈同一问题连续问两次，返回的引用文档不一致。根因分析：
  1. 某药品的"适应症"信息同时存在于多个文档，其中一份是 100 多页的完整说明书、另一份是约 10 页的简要说明。完整说明书里该信息在第 109 页、位置靠后。
  2. 文档按约 1000 字符切成 chunk，目标信息只占某个靠后 chunk 里的约 100 个字符，chunk 整体与问题的相似度被大量无关内容拉低，排名靠后。
  3. 召回是一个**漏斗**：从 ES、向量库、Neo4j 等多数据源召回约 70 个 chunk → 粗排到 40 个 → rerank（用 GPT-4.1）精排到 10 个 → 交给 UAS → UAS 给大模型生成答案，并只把与答案相关的 chunk（可能仅 4 个、对应 2 个文档）作为引用返回给用户。
  4. 该目标 chunk 的 rerank 分数正好在第 10/11 名的边缘，而 GPT-4.1 有概率性，所以有时选进前 10、有时落选，导致引用文档不稳定。
- **结论/决策（缓解方案，按优先级讨论）**：
  1. **换更好的 rerank 模型**：现用 GPT-4.1（图快、便宜），可试更强的模型（只能缓解、非根治）。
  2. **更细粒度切分**：按段落切分，把无关内容分出去，让目标 chunk 的相似度分数更高、更精准（团队倾向不轻易改现有切块大小）。
  3. **让客户自定义文档切分**：把文档给客户，由客户决定从哪切到哪（参考阿里百炼已有的类似功能）。客户花少量时间调整切块，噪音变小、召回分数变高，效果提升明显；对医药类高准确性要求场景尤其有用。默认准确率已较高（目标 95%），个别不准的可做微调。
- **Action**：评估 rerank 换模型；调研/实现按段落切分与客户自定义切分功能（正华/智华 + 后端）。
